## F-1 · `_build.bat` 产物对照表实际不可读（阻塞级，因为它是 R-1 的唯一交付物）

**实测复现**（主控在 `D:\_Progs\02Business\AsWish` 直接跑 `_build.bat`，exit 0）：

```
============================================================================
  bin/AsWish.exe          = GUI<乱码> CLI <乱码>?
'li' 不是内部命令或外部命令，也不是可运行的程序或批处理文件。
请检查名称的拼写，然后再输入。
============================================================================
```

三个后果：

1. **中文全是乱码**。`_build.bat` 是 UTF-8 **无 BOM** 且含中文，`cmd.exe` 按
   GBK/ANSI 解码，直接吐 mojake。
2. **CLI 那一行整行消失**。`echo   cli/bin/AsWish.CLI.exe  = CLI（headless 命令行）`
   没有被 echo，而是被 cmd 当成命令执行，才打出 `'li' 不是内部命令...`。
   隔离复现已定型（`@echo off` + `echo.` + `echo ===...` + 两行产物 + `echo ===...`，
   每次必现）。
3. **一次成功的构建看起来像失败**。exit code 仍是 0，但日志里有硬错误行、两行
   产物只剩一行。这张表存在的全部理由（R-1：防止操作工把 GUI 当 CLI 用）恰好
   被它自己打掉。

**根因**：`cmd.exe` 按 ANSI 代码页解析批处理，UTF-8 中文字节被当作 GBK lead/trail
处理，字节流错位后把后续行内容推进了命令解析路径。不是终端显示问题——隔离复现里
落盘的字节本身就是错位后的结果。

**修法（二选一，主控定默认路线 A）**：

- **A（默认）**：把产物表改成**纯 ASCII**，中文说明移到表上方的 ASCII 注释或
  AGENTS.md。例：
  ```bat
  echo ============================================================================
  echo   bin/AsWish.exe          = GUI  (desktop; do NOT pass CLI arguments)
  echo   cli/bin/AsWish.CLI.exe  = CLI  (headless command line)
  echo ============================================================================
  ```
- B：给 `_build.bat` 加 UTF-8 BOM 并 `chcp 65001`。**不推荐**——`chcp` 改的是控制台
  输出码页，不改 cmd 解析批处理文件的码页，错位与"整行被当命令执行"不一定消失，
  已实测 BOM 对该路径无确定效果。

**硬验收**：

1. `cmd /c _build.bat > log 2>&1` exit 0，且 `log` 末尾至少 6 行产物表区域
   **同时**含 `bin/AsWish.exe` 与 `cli/bin/AsWish.CLI.exe` 两行标注；
2. `log` 中**不含** `不是内部命令`、`请检查名称的拼写` 任一字符串；
3. 产物表区域不含 U+FFFD 替换字符；`log` 每条非 ASCII 行都必须能被 GBK 与 UTF-8
   之一**无替换字符**解码（防 mojake 换个形态回来）；
4. 顺带扫一遍仓库里其他 `.bat`/`.cmd`/`.ps1`：凡含中文的，要么转 ASCII，要么确认
   其输出通道不经过 cmd 的批处理解析。列表随报告附上，不要默默跳过。

## F-3 · `--gui-verify` 失败时控制台一个字都不出（静默失败）

**实测复现**（主控，`cmd /c bin\AsWish.exe --gui-verify dogfood_gui_site_final`）：

```
EXIT=1
stdout: 0 字节
stderr: [1001/221111.342:ERROR:ui\gfx\win\window_impl.cc:172] Failed to unregister
        class Chrome_WidgetWin_0. Error = 1412     <- WebView2/Chromium 自己的日志
```

应用自己的原因（`GUI-VERIFY-NO-WEBVIEW: WebView2 Runtime is not created ...`）
**只落在 `dogfood_gui/gui-dual-surface.txt` 里，没有上控制台**。

这正是 WO-0064 立项要治的病（静默吞掉），只是换到了 `--gui-verify` 这条路径上：
操作工或 CI 拿到 exit 1 + 零诊断，只能去翻证据日志。fail-closed 行为本身是对的
（WO-0061 守卫确实拦住了，exit 1、证据日志有因），**缺的只是控制台播报**。

**根因**：`src/app/AsWish.MainForm.pas:1955` 的 `ConsoleError` 只写 `STD_ERROR_HANDLE`，
没有 `AttachConsole(ATTACH_PARENT_PROCESS)` 兜底；而本单新写的
`TAsWishCommandLine.OutputConsoleError`（`src/core/AsWish.CommandLine.pas:35`）有。
GUI 子系统 exe 从 `cmd /c` 启动时 std 句柄可能无效，`WriteFile` 直接写进虚空。

**这不是平台限制**：同一个进程里 WebView2 的 Chromium 日志能到 stderr，说明控制台
是可挂上的。

**硬验收**：

1. 把 `MainForm.ConsoleError` 改为复用 `TAsWishCommandLine.OutputConsoleError`
   （或给它补上同样的 `AttachConsole` 兜底），不要复制第二份实现；
2. 在本机（无 Evergreen WebView2 Runtime）跑 `bin\AsWish.exe --gui-verify
   dogfood_gui_site_final`，**stderr 非空**且含 `GUI-VERIFY-NO-WEBVIEW`，
   exit 仍为 1，`dogfood_gui/gui-dual-surface.txt` 内容不回归；
3. 单测（`tests/Test.AsWish.CommandLine.pas` 或同批新文件）：桩掉 `GetStdHandle`
   返回 0/`INVALID_HANDLE_VALUE` 的路径，断言消息仍被写出（即兜底分支被走到），
   **先贴 RED 再贴 GREEN**；
4. 已知限制写进报告：有 WebView2 的宿主上无法本地跑到 12/12 断言，标注
   `unverified_on_this_host`，不得据此宣称 GUI 验证通过。

## 顺带记录的睿智工作流缺陷（主控本轮亲测，供优化工单取用）

1. **门禁覆盖范围与构建脚本脱节**（即 F-2 根因）：门禁按源码目录白名单扫文件，
   而构建入口在仓库根。任何"构建入口自身"的缺陷都天然逃离门禁。建议门禁的
   `source_files()` 改为按 manifest 的 `gates[].command` 反查被执行的构建脚本，
   而不是维护一份手写目录白名单。
2. **exit code 0 被当成"产物正确"的证据**：H2.compile-build 只问 returncode，
   于是 F-1 这种"构建成功但日志里带着硬错误、两行产物只剩一行"的缺陷一路绿灯。
   建议对 `_build.bat` 类门禁增加输出断言（必须出现预期产物标注、禁止出现
   `不是内部命令`）。
