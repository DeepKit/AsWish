## (b) Self-approval / self-signing hole in H4 waiver or approval policy

**Finding B1 — HIGH / area: H4 policy / governance durability**
- Description: The stated anti-self-signing enforcement ("`submitted_by == approved_by` causes immediate RC=1 gate failure") is declared as a rule but is not evidenced by any counterfactual, exit-code check, or negative test in the recorded material. The current ledger has `total: 0`, so the rule is **untested** in this run — the zero-waiver baseline means a self-approval hole cannot manifest now but also cannot be shown to be closed.
- Evidence: `"anti_self_approval_rules": ["Self-signing (submitted_by == approved_by) causes immediate RC=1 gate failure", ...]` and `"authorized_approvers": ["MasterController","ArchitectureReviewBoard"]` are policy declarations; the H4 gate output only asserts `counterfactual_bypass`, `zero_hits`, `zero_unapproved_waivers` — none of which is a self-sign detection test.

**Finding B2 — MEDIUM / area: H4 policy / authorization**
- Description: `authorized_approvers` includes `"MasterController"`, which matches the impersonation regex prefix set. A real `MasterController` signer and a synthetic `MasterController-foo` signer both begin with the same prefix; the regex `^(MasterController|SPW|MainController)-.*$` blocks the *hyphenated* synthetic form, but `MasterController` alone is a permitted authorized approver **and** an impersonation-prefix root.
- Evidence: `"impersonation_patterns": ["^(MasterController|SPW|MainController)-.*$"]` and `"authorized_approvers": ["MasterController","ArchitectureReviewBoard"]`.
- Impact: any future waiver approved by a submitter literally named `MasterController` (whitespace/case/encoding variants) would pass the whitelist string comparison. The material itself acknowledges this class of weakness.

**Finding B3 — HIGH / area: H4 policy (self-declared limitation)**
- Description: The pack admits identity checks are not cryptographic. The only backstop is git commit signatures + git blame via pre-commit hooks — none of which is evidenced in this material (no hook output, no signed-commit verification artifact).
- Evidence: `"known_limitations": ["Approver identity whitelist and self-signing checks rely on string comparison backed by git commit signatures and git blame in pre-commit hooks, not cryptographic signing in JSON itself."]`.
- Because signer identity in the waiver JSON is a plain string field, **a same-repo editor can forge `approved_by` and `submitted_by` together** and only the (unshown) pre-commit hook stands between that and a green H4 run.

## (d) Silent downgrade / fake-green risk

**Finding D1 — MEDIUM / area: G.open-source-build**
- Description: The gate emits a warning-class condition (14 dead-link references) yet returns `verdict: PASS, exit_code: 0`. This is an **explicit, acknowledged downgrade** ("不阻断") — effectively a policy carve-out decided inside the gate itself rather than via a waiver ledger entry. Because the H4 waiver ledger is zero and H4 policy forbids ongoing waivers, there is no governance record for this carve-out.
- Evidence: `"...发布后成死链，不阻断"` plus `"verdict": "PASS", "exit_code": 0` on the same gate; compare H4 policy `"max_ongoing_waivers": 0` and `"policy_enforcement": "Any waiver without pre-approved authorized approver or unapproved ongoing scope fails closed (RC=1 in H4 gate)."`.
- This is the clearest fake-green risk in the pack: a known defect is silently promoted to PASS without an approved waiver tying it to a governed scope.

**Finding D2 — MEDIUM / area: G.vendored-upstream-drift**
- Description: Gate reports drift equality against an absolute local path `D:\_Progs\02Business\DeepBase`. This same path is defined as `H4.HARDCODED_ABS_PATH` (medium severity, "Absolute machine path baked into production code"). The gate's own comparison anchor uses a machine-specific path — meaning the gate can only run on the same developer machine, and its PASS is not machine-independent.
- Evidence: `"[G.vendored-upstream-drift] 上游定位: D:\\_Progs\\02Business\\DeepBase"` vs `h4_patterns` entry `"id": "H4.HARDCODED_ABS_PATH", "pattern": "D:\\\\_Progs"`.
- Note: The H4 pattern is scoped to *production code*; the gate is tooling. Still, this weakens portability and reproducibility of the PASS.

**Finding D3 — LOW / area: H3 runtime gates**
- Description: `H3.runtime-autofix` completes in 0.085s and `H3.deep-ui-test` in 0.09s, each asserting 5 and 3 counterfactuals respectively. These durations are too short for genuine UI/exercise of a C# Windows desktop binary. Either the counterfactuals are static analyses (undisclosed) or the assertions are trivial.
- Evidence: `"gate_id": "H3.deep-ui-test", "duration_seconds": 0.09` and `"gate_id": "H3.runtime-autofix", "duration_seconds": 0.085`.
- Compare `H3.gui-verify-smoke` at 12.5s (plausible for a real GUI smoke). This suggests H3.deep-ui-test / runtime-autofix may not be runtime tests in the claimed sense. Not conclusive from material alone; flagged.

**Finding D4 — LOW / area: claims_asserted vs. output excerpt**
- Description: Multiple gates reorder the `claims_asserted` list relative to the manifest-declared `claims` (e.g. `H2.unit-tests`, `H4.bypass-patterns`) and the `output_excerpt` shows generic `[CLAIM_ASSERTED] counterfactual_N` markers rather than evidence the counterfactual actually ran. This pattern permits a "claims asserted" rubber-stamp style of fake-green.
- Evidence: e.g. `"[CLAIM_ASSERTED] counterfactual_3 | [CLAIM_ASSERTED] counterfactual_4 | [CLAIM_ASSERTED] counterfactual_5 | [H3.runtime-autofix] PASS"` — the label being printed is not, by itself, proof the counterfactual fired.

**Finding D5 — INFO / area: subject/run pinning**
- Description: `subject_sha256` and `head_commit` (`7cebca6`) are consistent across all 12 gate records, and `gate_run_sha256` is pinned. No hash mismatch detected. The pinning claim in `h4_policy.anti_self_approval_rules` ("any ledger modification invalidates pinned digest") is consistent with observed values.
- Evidence: all `"subject_sha256": "ce2ef0e714f6cfd1edeb3cffc6a2146832275c16c7c2bbd051694c72be5d7177"` and top-level `"gate_run_sha256": "66c95f85ac561da407b540629b61f40b23aa69944743f80f7189892cb3469ba1"`.
- Positive observation, no issue found.
