### 错到什么程度

`ev-flash-input-wechatbridge-reading-full-co` 这一个编号下有 **91 条**条目，
每条都是同一文件 `.flash-input/wechatbridge-reading/full-corpus.txt` 的**不同区段**：

| 条目 | lines | excerpt 首行 |
|---|---|---|
| 1 | 4-161 | `# The Swift toolchain comes from Xcode, which mise does not manage.` |
| 2 | 162-167 | `# 微信流（WeChatBridge）产品能力文档` |
| 3 | 168-187 | `## 1. 产品定义` |
| … | … | … |
| 91（最后一条） | 1204-1218 | `#     sheet on attachments WeChatBridge did not produce, and they never call pluginkit.` |

而 `trees/function-tree.yaml` 里有 **91 个节点**引用这一个编号。
按 `EvidenceCollector.pas:196` 的 `AddOrSetValue`（last-wins），
这 91 个节点的"来自哪几行"全部解析成最后一条。

节点 `func-the-swift-toolchain-comes-from-xcode-whi`（修复前 `trees/function-tree.yaml:3196`）
标题是 "The Swift toolchain comes from Xcode..."，对应的却是第 1 条（4-161 行），
但解析落到第 91 条（1204-1218 行）——**节点说一件事，证据指向另一件事。**

### 根因（代码定位，已在源码中确认）

`src/services/AsWish.Services.TreeBuilder.pas` 原第 164 行：

```pascal
Result.Id := 'ev-' + MakeSlug(ARelPath);   // 一个文件一个 id
```

而调用方随后把 `Lines`/`Excerpt` 改成**章节级**（见原第 553-558 行）：

```pascal
var LEv := MakeEvidenceForFile(LFile);
LEv.Lines := Format('%d-%d', [LStartLine, LEndLine]);  // 章节级行区
LEv.Excerpt := LTrimmed;
```

**id 按文件算，内容按章节算**，两边粒度不一致 → 撞号。

### 修法（已落地）

1. `MakeEvidenceForFile` 增加带行区的重载；id 改为在 `Lines` 定稿**之后**推导，
   并把行区编进 id（`ev-<slug>-<起>_<止>`），使"同文件不同章节"按构造即可区分。
2. 所有"先建证据再改行区"的调用点改为**建证时传行区**（共 2 处：文档标题、Delphi 类）。
3. 新增 `FUsedEvidenceIds` 唯一性登记；仍撞号时加数字后缀并计入
   `EvidenceIdCollisions`（不静默吸收）。
4. 消费侧 `EvidenceCollector.pas` 的 `AddOrSetValue` 改为**发现重复 id 直接报错**
   （附前 5 个肇事 id），不再按列表顺序悄悄挑一个。

### 回归测试（已落地，且已验证能抓住原缺陷）

`tests/Test.AsWish.TreeBuilder.pas` 新增 2 个用例，并修订 1 个既有断言：

- `MakeEvidenceForFile_SectionRanges_ProduceDistinctIds`
- `BuildFromScan_EvidenceIds_AreUniqueAcrossWholeList`（全表 id 唯一性不变量）
- `MakeEvidenceForFile_CalculatesHash_Lines_And_Excerpt`（id 格式断言随之更新）

**红→绿验证（不是只跑绿）**：把 id 推导临时退回"不带行区"→ 2 个新用例转红；
再把唯一性登记整个删掉 → 3 红 1 error，报出
`Duplicate evidence id "ev-docs-corpus-md"`，与线上缺陷同形。
全部还原后 259/259 通过。

## GAP-02 · 工具自己生成的节点 id，过不了自己的校验（已复现，未修）

**严重度：P1**

`AsWish.Validation.pas:163` 的节点 id 正则：

```
^(func|mod|view|data)-[a-z0-9][a-z0-9\-]{0,49}$      // 总长上限 51 字符
```

而 `TreeBuilder.pas` 生成 data 字段节点时用
`UniqueId('data-field-' + MakeSlug(字段名))`，`MakeSlug` 只把 slug 截到 40 字符，
加上 `data-field-` 前缀后最长可到 51+，实测 data 树里最长节点 id **85 字符**。

复现：

```bash
cli/bin/AsWish.CLI.exe validate D:/_Progs/02Business/DeepAxis
# → [invalid_id_format] 206 error(s)
grep -a '^  - id: ' .AsWish/trees/data-tree.yaml | awk -F'"' '{print length($2)}' | sort -rn | head -1
# → 85
```

**这是"工具说的话 vs 工具做的事"对不上的典型**：validator 规定 id 最长 51，
生成侧却能产出 85。`validate` 因此永远 FAILED（共 407 error）。

## GAP-04 · HTML 里的证据编号是死代码，无处可查（2026-09-25 修正前提 · 已修复）

**严重度：P2（但它是 GAP-01 能潜伏这么久的直接原因）**

### 先纠正：最初的测量本身是错的

最初记的是"8 个 HTML 里 `ref_id` 命中 0 次"。这个测法量的是 **YAML 键名**
`ref_id` 字面量，不是它的值——展示层本来就输出值不输出键名，所以必然 0 次。
据此得出的"展示层根本没透出证据编号"结论**不成立**，写在这里避免下一个人
按错的前提继续查。

### 真实缺陷（重新实测，口径为"证据编号的值在 HTML 里出现几次 / 能不能点开"）

实测方式：扫一个小项目后逐文件统计 distinct 证据编号，并抓渲染原文。

| 文件 | distinct 证据编号 | 可点击 |
|---|---|---|
| `module-tree.html` | 30 | 否，纯 `<span>` |
| `data-tree.html` | 31 | 否，纯 `<span>` |
| `function-tree.html` | 0 | — |
| `view-tree.html` | 0 | — |
| `index.html` / `problems.html` / `scan-report.html` | 0 | — |

渲染出来长这样：

```html

```

是**不可点的裸编号**。整个 `.AsWish/html/` 目录下没有任何 evidence 页面
（`ls | grep -i evid` 为空），`source-evidence.yaml` 从头到尾没有对应的
HTML 渲染。`node-detail.html` 同样是 `<code>编号</code>` 不可点，
而且它只在 GUI 里按需生成，无头扫描根本不产出。

所以准确表述是：**编号透出了，但查不了**。人看到 `ev-src-...` 想知道它指向

（2878 条证据只有 649 个可达 id）能潜伏这么久的直接原因：编号既然查不了，
"编号是不是对得上"就没人能发现。

### 修复（已交付）

1. `TAsWishRenderService.RenderEvidencePage` 新增，把证据台账渲染成
   `evidence.html`：每条一行，带 `id="<证据编号>"` 锚点，列出

   否则指向一个不存在的页面。
3. `index.html` 的页面列表加 Evidence 入口（同样按文件存在判断）。
4. `cli/AsWish.CLI.dpr` 的 scan 渲染顺序：先渲染 `evidence.html`，
   再渲染树页面——顺序反了树页面就拿不到锚点目标。

## 新增复现缺陷：非 UTF-8 文档直接炸掉整次扫描（P0，已修复）

扫描 DeepCompare 的 4824 文件时，进程在 `System.SysUtils` 抛出
`EEncodingError: No mapping for the Unicode character exists in the target
multi-byte code page` 后中止，`trees/*.yaml` 只剩空壳。

隔离复现：造一个只含 2 个文件的 fixture（`docs/gbk.md` GBK 编码、
`docs/utf16.txt` 无 BOM UTF-16），崩溃地址 `0x4A822` 与线上完全一致；
换回合法 UTF-8 则正常。根因：`TFile.ReadAllLines(path, TEncoding.UTF8)`
对第一个非法字节序列直接抛异常，没有一个 try 兜住。

**修法**：新增 `src/core/AsWish.TextIO.pas`，按 BOM + 无 BOM UTF-16 的
NUL 高位字节启发式判编码，再按 UTF-8 → 系统代码页 → Latin-1 逐级降级，
并回报真正解成功的编码；TreeBuilder 的 8 处读文件全部改走它。

**降级必须可见，不能静默**：`TreeBuilder.NonUtf8Files` 列出所有走了
代码页回退的文件，CLI 打印告警，受影响证据条目带
`note: decoded as ansi, not utf8; excerpt may be lossy`。
真正是 UTF-16 的文件**不**算降级（实测 DeepCompare 只报 1 个 GBK 文件，
那个无 BOM UTF-16 的 `.js` 不在告警列表里）。


## GAP-05 evolve 丢失父 baseline 的 tree_type（2026-09-24 追加 · 已修复）

**缺陷**：`EvolveBaseline` 把变化集的 `IntentTree` 硬编码为 `ttView`
（`src/services/AsWish.Services.VisualWorkflow.pas:273` 原值），而
`CreateBaseline` 按 `AChangeSet.IntentTree` 推导 `tree_type`。结果是
**无论父 baseline 是哪棵树，演进出的 baseline 永远是 `view`**。

**为什么不是样式问题**：`difference` 与 `evolve` 都按 `tree_type` 选要读
的树。演进出的 baseline 一旦被标成 `view`，它就只跟 view 树比。一个功能树
变了的项目，对演进后的 baseline 做 difference 会**看不出来**——这不是
"报告不准"，是"完全不报告"。

### 隔离复现（HEAD 对照 vs 修复后，同一 DeepAxis 文件集）

| | 父 baseline | 演进出的 baseline | tree_type |

## GAP-06 · scan 会把生成物撒进目标项目的 git 仓库（2026-09-25 · 已修一半）

**严重度：P2（但它是"工具宣称不侵入目标项目"这句话的直接反例）**

### 隔离复现（全新 git 仓库，不依赖任何既有项目）

```bash
mkdir -p /tmp/gg/src && cd /tmp/gg && git init .
printf 'unit a;\n\ninterface\n\nimplementation\n\nend.\n' > src/a.pas
git add -A && git commit -m init
git status --short                                   # 空，干净
cli/bin/AsWish.CLI.exe scan /tmp/gg
git status --short --untracked-files=all .AsWish/    # 14 个未跟踪文件
git add -A --dry-run                                 # 14 个全部会被暂存
```

一次扫描后，`git add -A` 会把这 14 个文件全部提交进用户的仓库：

```
.AsWish/.gitignore
.AsWish/decisions/requirement-decisions.yaml
.AsWish/evidence/source-evidence.yaml
.AsWish/issues/doc-issues.yaml
.AsWish/project-spec.yaml
.AsWish/relations/requirement-relations.yaml
.AsWish/scan-report.yaml
.AsWish/snapshots/{function,module,view}.bak.yaml     ← 滚动备份，每次扫描被覆盖
.AsWish/trees/{function,module,view,data}-tree.yaml
```

**为什么是缺陷**：工具自己的 `.AsWish/.gitignore` 写着
"AsWish generated artifacts (regenerable)"，但只 ignore 了 `html/`、`llm/`、
`logs/`、`prompts/`——全是展示层。真正由扫描重建出来的规格状态一个都没管。
WO-0047 当初的处置是"列入两项目的 .gitignore（单独 commit）"，
即**每个目标项目都要人工补一行**，工具本身不做。

### 顺带查出的两处既有遗漏

1. `snapshots/*.bak.yaml` 是单文件滚动备份，每次扫描被覆盖——纯派生，必该 ignore。
2. `prompts/` 的 per-file 白名单漏了 `prompts/optimization-prompt.md`，
   而它正是"导出优化 Prompt"按钮的产物（`AsWish.Controller.pas:463`）。
   说明按文件列白名单这条路本身就会漏，改为整目录 ignore。

### 已修（客观部分）

- `.AsWish/.gitignore` 补齐全部派生产物：`snapshots/`、`scan-report.yaml`、
  `project-spec.yaml`，`prompts/` 由逐文件改为整目录。
- `llm/` **保持逐文件**：`llm/candidate-intent.yaml` 是人录进去的意图，
  不是产物，不能连带 ignore（这一点特意没有"顺手统一"）。
- 改为**每次扫描都重写**该文件，不再"仅当不存在才写"。
  原写法导致老项目永远拿着过期白名单，且没有任何信号提示它过期了——
  本次修复对已扫过的项目（DeepAxis/DeepCompare）根本到不了。

修后同一个隔离复现：`git add -A --dry-run` 从 14 项降到 **8 项**，
剩下的全部是规格状态，且 `.gitignore` 里有注释说明取舍、CLI 末尾
打印一行提示告诉用户"哪些没被 ignore、要不要自己加"。

### 处置说明（WO-0057 1.4.2）

规格状态（`trees/` `evidence/` `issues/` `decisions/` `relations/`）默认未被忽略，已在 `.AsWish/.gitignore` 头部注释、CLI scan 末尾提示文案与 `docs/05.协议-AsWish协议基线.md` §2.1 中明确交代当前取舍（跟踪规格资产 vs 减少 diff 噪音），告知用户如需完全忽略可于项目根 `.gitignore` 加入 `.AsWish/`。若产品后续需改口径，另行开单。

**回归测试**：`Test_WriteGitIgnore_CoversRegenerableArtifacts`、
`Test_WriteGitIgnore_RefreshesStaleContent`。两条都亲眼看过转红
（`rolling .bak.yaml backups are regenerated on every scan` /
`an existing .gitignore must be refreshed, not left stale`），修后 282/282。
