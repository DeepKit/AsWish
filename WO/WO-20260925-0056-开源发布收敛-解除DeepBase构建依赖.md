## 1. 由来

老板问"AsWish 可以开源发布了吗"。实测结论：**不能**。两个硬卡点：

1. **干净克隆编译不出来**。把 HEAD 的 593 个文件原样导出到空目录编译：
   - 命令行版 exit 0 ✓
   - 界面版 **失败**：`src\app\AsWish.MainForm.pas(42) Fatal: F2613 Unit 'DeepBase.EHAI.Types' not found.`
   - 测试版 **失败**：`Test.AsWish.EHAI.Binding.pas(28) Fatal: F2613 Unit 'DeepBase.EHAI.Types' not found.`
2. **225 个内部文件会被一起公开**（工单/审核请求/测试日志 + 5 份工作日志），
   内容涉及其他私有项目（DeepSpec）、内部分工、待老板拍板的决策清单。

本单解决这两条。

---

## 2. 依赖实况（已核实，非推测）

AsWish 对 DeepBase 的引用**只有两个类型单元**，全仓定位结果：

| 引用方 | 位置 |
|---|---|
| `src/app/AsWish.MainForm.pas` | `:42` `DeepBase.EHAI.Types`、`:43` `DeepBase.HB.Choice.Types` |
| `tests/Test.AsWish.EHAI.Binding.pas` | `:28` `:29` 同上 |
| `src/services/AsWish.Binding.HB.pas` | 接口中直接使用两单元的类型（`THbChoiceAction` / `TEhaiTraceRecord` 等） |
| `cli/` | **零引用** |

依赖链（实测）：

```text
DeepBase.EHAI.Types        → 只用 RTL
DeepBase.HB.Choice.Types   → 只用 RTL + DeepBase.EHAI.Types
                             +【死引用】DeepBase.HB.Core ← 一个符号都没用到
```

**关键实测**：把 `DeepBase.HB.Choice.Types` 的 `uses` 里那行 `DeepBase.HB.Core` 删掉，
单独编译 → exit 0，979 行，无任何缺符号报错。**HB.Core 是死引用**，
原本白拖一个 1335 行的主题/令牌引擎进编译。

许可证实况：DeepBase 根目录双许可证——`LICENSE`（Apache 2.0）与 `LICENSE-BSL`
（Business Source License 1.1）。BSL 的参数段只覆盖
`Core/DeepBase.AutoFix*`、`FMX/DeepBase.AutoFix*`、`Features/DeepBase.Browser*`、
`Governance/DeepBase.Governance*`。
**AsWish 用到的两个类型单元不在 BSL 清单内，归 Apache 2.0**，可再分发。

## 3. 方案与取舍

**选定：vendored 类型层（两文件）+ 上游漂移门禁。**

把两个类型单元原样收进 `vendor/deepbase-ehai/`，构建脚本改指本地路径，
另加一道确定性门禁盯住上游漂移。

理由：

- 这两个单元是**被正式契约冻结**的：`AsWish.Binding.HB.pas` 头部登记了
  SSOT 基线（`EHAI-DELPHI-SYMBOL-BASELINE-v1.0`）与两个文件的 SHA256。
  契约的用意就是"跨产品复用同一份语义"，vendored + 指纹门禁保住了这个用意
  （上游改了会响），而纯拷贝不管则会让契约退化成装饰。
- 两个单元本身已是 Apache 2.0，再分发合法。
- 与此相对的两个方案明确不选：
  - *把 DeepBase 整体开源后 AsWish 依赖它*：DeepBase 的护城河部件是 BSL，
    开源整仓不是本单能定的；
  - *砍掉 HB 选择甲板功能*：那是真功能（MainForm 里 0-9 键盘交互 + 789 行测试），
    砍它等于功能回退，不能当作"修构建"的副作用。

**已核实的既有事实**（避免误报）：`AsWish.Binding.HB.pas` 头部登记的指纹
`de9a3208…` / `963fedd0…` 与上游当前文件**原样比对不匹配**，
但与"去 BOM 后内容"的 SHA256 **完全匹配**——即指纹约定本就是按去 BOM 内容算的，
契约未漂移。漂移门禁按同一约定实现。

## 4. 改动清单

### A. vendored 类型层（新增）

- `vendor/deepbase-ehai/DeepBase.EHAI.Types.pas` —— 与上游**逐字节一致**（LF、无 BOM）
- `vendor/deepbase-ehai/DeepBase.HB.Choice.Types.pas` —— 同上游，**唯一偏差**：
  删掉死引用 `DeepBase.HB.Core` 那行（否则本地编译会因找不到该单元而失败）
- `vendor/deepbase-ehai/upstream.json` —— 逐文件记录：上游路径、上游 SHA256（去 BOM）、
  本仓 SHA256、偏差说明
- `vendor/deepbase-ehai/README.md` + `LICENSE` —— 来源、基线引用、Apache 2.0 归属

### B. 构建路径解耦

| 文件 | 改法 |
|---|---|
| `_build.bat` | `..\DeepBase\Core;..\DeepBase\VCL` → `vendor\deepbase-ehai`；同时删掉那句"zero external framework dependencies"的假注释（改动前它同文件第15行正引用外部路径） |
| `cli/_build_cli.bat` | `..\..\DeepBase\Core;..\..\DeepBase\VCL` → `..\vendor\deepbase-ehai` |
| `tests/_build_tests.bat` | 同上 |

CI 侧：`.github/workflows/build.yml` 删掉 `DEEPBASE_HOME` 死环境变量
（三个构建脚本从未读过它），并订正"BDS / DEEPBASE_HOME env-overridable"的失实注释。

### C. 内部文件剔出发布范围

用 `.gitattributes` 的 `export-ignore` 实现——`git archive`（即打发布包的标准路径）
会跳过它们，而**仓库里照旧保留**（工单和日志是内部资产，不是要删的东西）：

- `WO/ export-ignore`
- `.workbuddy/ export-ignore`
- `.AsWish/ export-ignore`、`.ai-workbench/ export-ignore`

**实际盘点发现的第二批漏网**（原定只排 `WO/` 与 `.workbuddy/`，核对导出清单时发现）：
内部材料不止这两个目录——仓库根目录躺着一份 `AUDIT-REQUEST-…md`，
`docs/归档/` 有 146 份历史包、若干交接与新人上手文档。
所以规则改按**内容特征**配，不靠一份已知前缀清单：

- `docs/归档/`、`docs/*交接*`、`docs/*交接包*`、`AUDIT-REQUEST-*`

顺带按 WO-0055 E1 补 `*.pas text eol=lf` / `*.dpr text eol=lf`（本仓此前无 .gitattributes）。

### C-2. 首批三处连带修复（干净克隆首次全绿时暴露）

1. **`AsWish.res` 曾被 `*.res` 忽略**（提交 `4aba922`）。`AsWish.dpr` 有
   `{$R *.res}`，干净克隆会 `E1026 File not found: 'AsWish.res'`。本地与 CI 都看不见——
   自建 runner 复用工作区，文件一直在。它是 tracked `AsWish.ico` 编出来的版本/图标资源，
   不是构建副产品，故 `.gitignore` 里加 `!AsWish.res` 例外并入册。
2. **六份机锚夹具原本住在 `WO/evidence/commons-anchors/`**（提交 `5fd5115`）。
   `WO/` 被剔出发布范围后，干净克隆构建全过但**测试挂 6 个**：种子课程和测试
   指向的目录在发布包里不存在。已 `git mv` 到 `tests/fixtures/commons-anchors/`
   （内容是干净测试数据，无内部材料），并订正**种子表**
   `src/services/AsWish.Services.Commons.pas`——最初只扫了 `tests/`，
   漏了源码里的 6 处硬编码路径。
3. **GUI 实测例程把证据写进 `WO\evidence`**（提交 `d41fe05`）。
   该目录是内部材料、发布包里没有，等于发布的源码会在用户克隆里重建内部目录。
   改写 `dogfood_gui/`（已被 `.gitignore` 的 `dogfood_*/` 覆盖，跑实测不脏工作树）。

### D. 新增两道确定性门禁（R0）

- `tools/spw-gates/gate_ehai_vendor_drift.py`
  - 上游可达（`DEEPBASE_HOME` 或默认 `../DeepBase` 存在）→ 重算上游去 BOM SHA256，
    与 `upstream.json` 登记值比对，不一致即 **FAIL**（上游改了，须人工复核后重新 vendored）
  - 上游不可达（公开克隆场景）→ **SKIP** 并说明原因，不阻塞
  - 另校验 vendored 文件自身 SHA256，防本地误改
- `tools/spw-gates/gate_open_source_build.py`
  - 任何被跟踪的构建脚本里不得再出现 `..\DeepBase`
  - 三个构建脚本的搜索路径都必须含 vendored 目录
  - `.gitattributes` 必须含 `WO/` 与 `.workbuddy/` 的 export-ignore
  - `git archive HEAD` 的实际导出清单按内容特征比对，不得命中内部材料
  - 发布包必须含 `README.md` / `LICENSE` / `NOTICE`
  - 任何 `{$R …}` 引用的资源必须已入册（防 `AsWish.res` 那类只在干净克隆炸的坑）
  - **反向检查**：导出清单内的代码/配置不得引用"HEAD 里有、但被 export-ignore 剔掉"
    的路径（差集即被剔集合，命中即 FAIL）。这是第 C-2.2 条那 6 个失败暴露的缺口——
    本地能满足、发布包不能满足的引用，构建阶段一句预警都没有。
    `.md` 文档对 `docs/归档/` 与 `WO/` 的溯源引用只计数报出，不阻断（那是出处不是依赖）。

## 5. 验收

全部实测，非推断：

| # | 项 | 结果 |
|---|---|---|
| 1 | 干净导出三构建全过 | **PASS**。`git archive HEAD` → 空目录 → 界面版 / CLI / 测试版三构建全部 exit 0（修前界面版与测试版必败 F2613） |
| 2 | 全量测试 | **PASS 322/322**（干净克隆内实跑，Found 322 / Passed 322 / Failed 0） |
| 3 | 漂移门禁分支 | **PASS**（上游一致）／**FAIL**（上游漂移、本地误改）／**SKIP**（上游不可达，隔离树实测）——四个分支逐一跑过 |
| 4 | 开源门禁 | **PASS**（185 个文件导出，零内部材料命中） |
| 5 | 导出清单无 `WO/`、`.workbuddy/`、`docs/归档/`、`AUDIT-REQUEST-*` | **PASS**（均为 False） |
| 6 | SSOT 基线与上游去 BOM SHA256 | **PASS**（`de9a3208…` 与上游逐位一致，契约未破） |
| 7 | 无新增敏感信息 | **PASS**（发布包 grep 不到密钥形态；`WO/` 内亦无真实密钥） |
| 8 | CI 死配置 | **PASS**（`DEEPBASE_HOME` 改为漂移门禁上游定位变量，有真实用途） |
| 9 | 六门全绿 | **PASS**：autofix／vendor-drift／encoding／open-source-build／resource-locks／ui-bridge |
| 10 | 新反向检查会变红 | **PASS**。在父提交 `4aba922` 上跑当前门禁，报出全部 25 处真实引用（13 打点日志 + 12 夹具路径），exit 1；修后 exit 0 |

**导出规模**：593 个入册文件 → 185 个进入发布包。

**已知限制**：两道新门禁都要 git 仓（`git archive` / `git ls-tree`）。
真实克隆有 `.git`，不受影响；把发布包**解压成目录**再跑会 FAIL 并说明
"git archive HEAD 失败"。这不是发布阻断项，是运行前提。

## 6. 遗留与后续

- `DEEPBASE_HOME` 从此有真实用途：漂移门禁的上游定位变量。
- **公开文档有 33 处溯源死链**：`docs/` 下 17 份公开文档引用了 `docs/归档/`（25 处）
  与 `WO/`（8 处）的出处，发布包里这些文件不存在。这些引用是"结论凭什么可信"的
  凭据，删了反而伤文档价值，故门禁只报数不阻断。若要清理，应改写为
  "归档出处"的文字说明而非路径，须另立项（涉及 17 份文档的表述口径）。
- 后续可选（本单不做）：若哪天 DeepBase 的类型层要独立公开发布，
  应改为"双方共同依赖一个小型 Apache 2.0 类型包"，届时删掉 vendored 副本。
  该改动会影响 SSOT 归属，须单独立单。
- WO-0042（H5 独立观察不可用）仍是 `release_ready=false` 的外部卡点，
  本单不解它——本单只解"干净克隆能不能编译/能不能发源码"。

## 7. 本单暴露的流程缺口（已并入 WO-0055 优化单）

1. **本机能跑 ≠ 干净克隆能跑**。三处缺陷（DeepBase 路径、`AsWish.res`、
   测试夹具住在内部目录）全部只在干净克隆现形，本地与自建 CI 因为复用工作区
   一概看不见。**结论：任何"可发布/可分发"的宣称，验收动作必须是
   `git archive HEAD` → 空目录 → 重构建 → 重跑测试**，不能拿本机一次绿了结。
2. **剔除动作会制造新的断点**。`WO/` 一被剔出，指向它的种子路径、测试夹具、
   GUI 证据目录同时失效——而三条都不在"构建依赖"的常规视野里。
   所以剔除清单引出两道新检查：导出清单本身，和"导出清单内的东西引用被剔路径"。
3. **写门禁的人也会静默失败**。开源门禁最早自己手搓 tar 解析，把文件内容当头部
   逐 512 字节踩，凭空造出 7648 个条目然后 PASS——和 WO-0055 记录的
   "报成功但内容是空的"同一个病。改用 `zipfile` 真解析才作数。
   教训：**取证/清点类工具必须自证取到了东西**（本次靠"应命中 25 处却报 0"才对上）。
