## 1. 由来

老板问"AsWish 可以开源发布了吗"。实测结论：**不能**。两个硬卡点：

1. **干净克隆编译不出来**。把 HEAD 的 593 个文件原样导出到空目录编译：
   - 命令行版 exit 0 ✓
   - 界面版 **失败**：`src\app\AsWish.MainForm.pas(42) Fatal: F2613 Unit 'DeepBase.EHAI.Types' not found.`
   - 测试版 **失败**：`Test.AsWish.EHAI.Binding.pas(28) Fatal: F2613 Unit 'DeepBase.EHAI.Types' not found.`
2. **225 个内部文件会被一起公开**（工单/审核请求/测试日志 + 5 份工作日志），
   内容涉及其他私有项目（DeepSpec）、内部分工、待老板拍板的决策清单。

本单解决这两条。

---

## 2. 依赖实况（已核实，非推测）

AsWish 对 DeepBase 的引用**只有两个类型单元**，全仓定位结果：

| 引用方 | 位置 |
|---|---|
| `src/app/AsWish.MainForm.pas` | `:42` `DeepBase.EHAI.Types`、`:43` `DeepBase.HB.Choice.Types` |
| `tests/Test.AsWish.EHAI.Binding.pas` | `:28` `:29` 同上 |
| `src/services/AsWish.Binding.HB.pas` | 接口中直接使用两单元的类型（`THbChoiceAction` / `TEhaiTraceRecord` 等） |
| `cli/` | **零引用** |

依赖链（实测）：

```text
DeepBase.EHAI.Types        → 只用 RTL
DeepBase.HB.Choice.Types   → 只用 RTL + DeepBase.EHAI.Types
                             +【死引用】DeepBase.HB.Core ← 一个符号都没用到
```

**关键实测**：把 `DeepBase.HB.Choice.Types` 的 `uses` 里那行 `DeepBase.HB.Core` 删掉，
单独编译 → exit 0，979 行，无任何缺符号报错。**HB.Core 是死引用**，
原本白拖一个 1335 行的主题/令牌引擎进编译。

许可证实况：DeepBase 根目录双许可证——`LICENSE`（Apache 2.0）与 `LICENSE-BSL`
（Business Source License 1.1）。BSL 的参数段只覆盖
`Core/DeepBase.AutoFix*`、`FMX/DeepBase.AutoFix*`、`Features/DeepBase.Browser*`、
`Governance/DeepBase.Governance*`。
**AsWish 用到的两个类型单元不在 BSL 清单内，归 Apache 2.0**，可再分发。

---

## 3. 方案与取舍

**选定：vendored 类型层（两文件）+ 上游漂移门禁。**

把两个类型单元原样收进 `vendor/deepbase-ehai/`，构建脚本改指本地路径，
另加一道确定性门禁盯住上游漂移。

理由：

- 这两个单元是**被正式契约冻结**的：`AsWish.Binding.HB.pas` 头部登记了
  SSOT 基线（`EHAI-DELPHI-SYMBOL-BASELINE-v1.0`）与两个文件的 SHA256。
  契约的用意就是"跨产品复用同一份语义"，vendored + 指纹门禁保住了这个用意
  （上游改了会响），而纯拷贝不管则会让契约退化成装饰。
- 两个单元本身已是 Apache 2.0，再分发合法。
- 与此相对的两个方案明确不选：
  - *把 DeepBase 整体开源后 AsWish 依赖它*：DeepBase 的护城河部件是 BSL，
    开源整仓不是本单能定的；
  - *砍掉 HB 选择甲板功能*：那是真功能（MainForm 里 0-9 键盘交互 + 789 行测试），
    砍它等于功能回退，不能当作"修构建"的副作用。

**已核实的既有事实**（避免误报）：`AsWish.Binding.HB.pas` 头部登记的指纹
`de9a3208…` / `963fedd0…` 与上游当前文件**原样比对不匹配**，
但与"去 BOM 后内容"的 SHA256 **完全匹配**——即指纹约定本就是按去 BOM 内容算的，
契约未漂移。漂移门禁按同一约定实现。

## 4. 改动清单

### A. vendored 类型层（新增）

- `vendor/deepbase-ehai/DeepBase.EHAI.Types.pas` —— 与上游**逐字节一致**（LF、无 BOM）
- `vendor/deepbase-ehai/DeepBase.HB.Choice.Types.pas` —— 同上游，**唯一偏差**：
  删掉死引用 `DeepBase.HB.Core` 那行（否则本地编译会因找不到该单元而失败）
- `vendor/deepbase-ehai/upstream.json` —— 逐文件记录：上游路径、上游 SHA256（去 BOM）、
  本仓 SHA256、偏差说明
- `vendor/deepbase-ehai/README.md` + `LICENSE` —— 来源、基线引用、Apache 2.0 归属

### B. 构建路径解耦

| 文件 | 改法 |
|---|---|
| `_build.bat` | `..\DeepBase\Core;..\DeepBase\VCL` → `vendor\deepbase-ehai`；同时删掉那句"zero external framework dependencies"的假注释（改动前它同文件第15行正引用外部路径） |
| `cli/_build_cli.bat` | `..\..\DeepBase\Core;..\..\DeepBase\VCL` → `..\vendor\deepbase-ehai` |
| `tests/_build_tests.bat` | 同上 |

CI 侧：`.github/workflows/build.yml` 删掉 `DEEPBASE_HOME` 死环境变量
（三个构建脚本从未读过它），并订正"BDS / DEEPBASE_HOME env-overridable"的失实注释。

### C. 内部文件剔出发布范围

用 `.gitattributes` 的 `export-ignore` 实现——`git archive`（即打发布包的标准路径）
会跳过它们，而**仓库里照旧保留**（工单和日志是内部资产，不是要删的东西）：

- `WO/ export-ignore`
- `.workbuddy/ export-ignore`
- `.AsWish/ export-ignore`、`.ai-workbench/ export-ignore`

顺带按 WO-0055 E1 补 `*.pas text eol=lf` / `*.dpr text eol=lf`（本仓此前无 .gitattributes）。

### D. 新增两道确定性门禁（R0）

- `tools/spw-gates/gate_ehai_vendor_drift.py`
  - 上游可达（`DEEPBASE_HOME` 或默认 `../DeepBase` 存在）→ 重算上游去 BOM SHA256，
    与 `upstream.json` 登记值比对，不一致即 **FAIL**（上游改了，须人工复核后重新 vendored）
  - 上游不可达（公开克隆场景）→ **SKIP** 并说明原因，不阻塞
  - 另校验 vendored 文件自身 SHA256，防本地误改
- `tools/spw-gates/gate_open_source_build.py`
  - 任何被跟踪的构建脚本里不得再出现 `..\DeepBase`
  - 三个构建脚本的搜索路径都必须含 vendored 目录
  - `.gitattributes` 必须含 `WO/` 与 `.workbuddy/` 的 export-ignore
  - `git archive HEAD` 的实际导出清单不得含 `WO/…`、`.workbuddy/…`

## 5. 验收

1. **干净导出三构建全过**（本单的主验收）：`git archive HEAD` 导出到空目录，
   界面版 / 命令行版 / 测试版三构建全部 exit 0——这是修之前界面版与测试版
   必败（F2613）的那两条。
2. 全量测试通过（修前基线 322/322，修后不得下降）。
3. 漂移门禁三个分支都要亲自跑过：上游一致 PASS、上游不一致 FAIL、
   上游不可达 SKIP。
4. 开源门禁 PASS。
5. `git archive HEAD` 产物里 grep 不到 `WO/` 与 `.workbuddy/`。
6. SSOT 基线登记值与上游去 BOM SHA256 仍匹配（证明未破坏契约）。
7. 全仓无新增敏感信息（修前基线：无真实密钥）。
8. SPDX/CI 死配置已清。
