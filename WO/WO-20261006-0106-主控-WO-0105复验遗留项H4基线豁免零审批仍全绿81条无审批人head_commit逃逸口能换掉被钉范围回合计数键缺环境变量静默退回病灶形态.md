## 一、第 1 项：H4 baseline 豁免零审批仍全绿（P1，主项）

### 1.1 事实（主控亲手查实，非 observer 转述）

- `tools/spw-gates/h4_waivers.json`：`waivers` 数组 **81 条**，
  `approved_by` 为空的 **81/81**（脚本逐条统计，非抽样）。
- `spw-manifest.json` → `h4_policy.max_ongoing_waivers = 0`。
- `tools/spw-gates/gate_bypass_patterns.py:141-162`：审批检查被
  `if app_str:` 包住——`approved_by` **非空**才查白名单/冒充/自签；
  `approved_by` 为空时，只有 `scope == "ongoing"` 才出
  `[HIGH] unapproved ongoing waiver`，**`scope=baseline` 空审批零 finding**。
- `:223` 的 `len(ongoing_waivers) > max_ongoing` 只数 `scope=ongoing`，
  baseline 一条都不进分母。

命令（主控实跑留证）：

```
python -X utf8 -c "
import json
w=json.load(open('tools/spw-gates/h4_waivers.json',encoding='utf-8'))['waivers']
print(len(w), sum(1 for x in w if not (x.get('approved_by') or '').strip()))
"          # -> 81 81
grep -n "max_ongoing\|approved_by" tools/spw-gates/gate_bypass_patterns.py
```

### 1.2 为什么这是 P1 而不是 P3

两名异构 observer 在最新证据包里**独立**给出同一结论
（`_repro/spw-evidence-d436912.json` → `observer_seat_outcomes`）：

- deepseek `[BLOCKER] evidence_integrity`：H4 policy 声明 0，
  ledger 81 条无审批 → **要么 H4 的 PASS 是假的，要么台账根本没在执行**；
- gemini `[BLOCKER] self_approval`：开发者可自行往 `tools/spw-gates/h4_waivers.json`
  追加空审批条目，无需第三方复核。

这句话按在当前 H4 上**部分成立**：PASS 不是伪造的（门禁确实按自己的规则跑通了），
但**规则本身留着"零审批也算合规"的口子**。这与 RZB-009 是同族病——
绿灯照着未治理状态。

### 1.3 默认路线（不许反问，按这个做）

**(a) baseline 也必须带合法审批**：把 `gate_bypass_patterns.py:141` 的
`if app_str:` 改成 fail-closed——`approved_by` 为空**直接出 `[HIGH]`**，
不再分 scope 放行。`h4_approvers.json` 白名单与反冒充机制已就位，复用即可。

**(b) 81 条存量必须处置，不许留着过年**：
- 逐条核对，真被审批过的补 `approved_by` + `approved_at`（必须在
  `h4_approvers.json` 白名单内）；
- 补不上的**删豁免、改代码本身**（把绕过模式从源码里去掉）；
- 处置完 `h4_waivers.json` 的条数与 `max_ongoing_waivers` 必须自洽，
  自洽关系写进 README 或注释，说明这个 0 是什么口径。

**反证（必须亲眼见红）**：
- 往 `h4_waivers.json` 追加 1 条 `scope=baseline`、`approved_by` 为 "" 的豁免
  → 跑 `gate_bypass_patterns.py` 必须 RC=1 且 finding 指到那条；
- 追加 1 条 `approved_by` 不在白名单的 → 仍必须 RC=1（不许回归）；
- 追加 1 条 `approved_by` == `submitted_by` 的 → 仍必须 RC=1（自签不许回归）。

### 1.4 禁条

- 不许用"把 81 条一次性盖章成某人审批"来消 finding。审批是历史事实，
  没有就是没有；宁可删豁免改代码。
- 不许把 `max_ongoing_waivers` 从 0 改成 81 来让门禁闭嘴。
- 不许只改 manifest 不改门禁脚本（或反之）——两边必须同向，且都要有反证。

## 二、第 2 项：`head_commit` 逃逸口能换掉被哈希钉住的范围（P2）

### 2.1 事实

`tools/spw-evidence/generate_evidence.py` 阶段 2b：

```
parent_head = git rev-parse HEAD~1
if ledger_head == parent_head:
    diff_files = git -c core.quotepath=false diff --name-only HEAD~1 HEAD
    allowed_prefixes = ("tools/spw-gates/gate-run/", "spw-manifest.json", "WO/")
    if diff_files and all(f.startswith(p) for p in allowed_prefixes ...):
        is_valid_head = True
```

这条逃逸口的本意是放行"台账 pin 提交自己"（`d436912` 只改了 gate-run/ +
spw-manifest.json + WO/，必须放行，否则无限回归）。但它带来两个门：

- **门一**：`spw-manifest.json` 在放行名单里。manifest 的 `subject_files`
  决定 `subject_sha256` 到底覆盖哪些文件。改 manifest 就能在"文档型提交"里
  把受保护范围换掉，而台账不用重跑。
- **门二**：`check_tree_dirty()` 用 `:(exclude)tools/spw-gates/gate-run/`
  **整目录**排除。而 `gate-run/internal_markers.json`——**标记词探测器自己的
  配置**——正住在这个被排除的目录里。改它不触发 `tree_dirty_at_run`，
  又能被逃逸口放行 → 探测器配置可在"不留脏"的情况下被换掉。

### 2.2 默认路线

1. **逃逸口名单去掉 `spw-manifest.json`**：manifest 变更一律要求重跑门禁。
   放行名单收缩为 `tools/spw-gates/gate-run/` 与 `WO/`。
2. **脏检查从"整目录排除"改成"排除三个具体文件"**：
   `gate_run_results.json`、`gate_*.log`（台账自己与门禁日志会因跑门禁而变），
   其余 `gate-run/` 下的文件（尤其 `internal_markers.json`）一改就记脏。

**反证（必须亲眼见红）**：
- 构造一个只改 `spw-manifest.json` + `gate-run/gate_run_results.json` 的提交
  （可在临时工作树上做，或用手改台账复现），跑生成器必须 RC=1
  且回显 `head_commit mismatch`；
- 只改 `gate-run/internal_markers.json` 后跑 `run_all_gates.py`，
  台账的 `tree_dirty_at_run` 必须为 `true`（门禁本身可照样过，但台账必须记脏）。

### 2.3 禁条

- 不许把 `internal_markers.json` 搬去不受 export-ignore 保护的位置（那是 RZB-011 的回头路）。
- 不许为了让反证通过而把 `WO/` 也移出放行名单后又加回来——`WO/` 与 `gate-run/`
  是 pin 提交的正当依赖，保持即可。

## 三、第 3 项：回合计数键缺环境变量时静默退回病灶形态（P2）

### 3.1 事实

`tools/shims/safe-delete-bulk-guard.cjs:70-81`：

```
requestId: conversationRequestId || input.toolCallId,
```

`CODEEBUDDY_CONVERSATION_REQUEST_ID` 一旦没注入，`requestId` 就**静默等于
`toolCallId`**，于是 `state.requests` 的键重新退回 RZB-010 的病灶形态：
同回合跨调用不再累计，阈值永不触发。已经查实 harness 侧确实会注入该变量
（`cli/dist/codebuddy-headless.js` 含 `CODEBUDDY_CONVERSATION_REQUEST_ID=` 赋值），
但**钩子自己没有任何校验**——注入方式一变就是无声失效，不报错、不留痕。

### 3.2 默认路线

`getContext()` 里对 `CODEBUDDY_CONVERSATION_REQUEST_ID` 做 fail-closed：
缺失即 `fail()`，走 `SAFE_DELETE_BULK_GUARD_ERROR` + rc=1。
宁可这次删不干净，也不许静默失效。

**反证（必须亲眼见红）**：
- 清掉 `CODEBUDDY_CONVERSATION_REQUEST_ID` 跑 `check` → 必须 rc=1，
  stderr 含 `SAFE_DELETE_BULK_GUARD_ERROR`；
- 正常注入该变量跑 J/K 场景 → 仍必须 rc=2 / rc=0（不许回归，见 WO-0105 §八）。

### 3.3 禁条

- 不许用"默认给个假 requestId"糊过去；不许把 fail-closed 改成打一行 warning 后继续。

## 四、第 4 项：完工报告的披露口径（P3）

WO-0105 完工报告验收第 10 项写"`spw.py verify` 返回 `ok: true, errors: []`，
台账裁决真实 → PASS"。这句话本身**不假**（主控已实跑确认），但**不完整**：
同一份结果里还有 `acceptable_for_release: false`、
`certification.status = 'withheld'`、`pending_count = 13`、
`release_ready = False`。只写前半句会让读的人以为已经可以发版。

**要求**：今后所有完工报告的验收表里，凡是引 `spw.py verify` 结果，
必须同句写全 `ok` / `errors` / `release_blockers` / `acceptable_for_release` /
`certification.status` 五个字段，缺一不可。本项不需要改代码，是纪律要求，
在下一次完工报告里生效。
