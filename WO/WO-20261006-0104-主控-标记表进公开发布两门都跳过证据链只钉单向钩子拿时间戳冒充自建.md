## 一、缺陷本体（均为实测，非推测）

### 1.1 标记表进入公开发布，两道边界门同时跳过它

```
git archive --format=zip HEAD
  → tools/spw-gates/README.md 在发布包内
  → 该文件含 6 个治理标记词共 7 处
```

排除链路（两处叠加）：

```
tools/spw-gates/gate_external_boundary.py:78
    r"(^|/)(gate_(external_boundary|open_source_build)\.py|tools/spw-gates/README\.md)$"
tools/spw-gates/gate_open_source_build.py:359
    if name.startswith("tools/spw-gates/"): continue
.gitattributes
    tools/spw-gates/gate-run/ export-ignore   ← README 不在其内
```

WO-0101 的病灶原话是"门禁在守公开面不能出现什么，但守规矩的人查不到规矩"。
修完之后：规矩写进了公开发布的 README，而判官恰好被配置成不看这一页。
**病从作者侧搬到了执行侧，且从"踩雷才 FAIL"变成"永远不会 FAIL"。**

### 1.2 证据链只钉单向：台账记的 manifest 哈希从不被校验

```
tools/spw-gates/gate-run/gate_run_results.json  "manifest_sha256": "1b22628a…"
spw-manifest.json 实际 sha256                                        "d3a8f75c…"
spw.py verify → ok=true / errors=[]
```

`generate_evidence.py` 只在 :346 / :428 / :445 **写** `manifest_sha256`
并打进证据包（:680），从不**读**台账里那个值与实际 manifest 比对。

同族缺口：`ledger.gates[].subject_sha256` 被原样抄进证据包（:615），
却从不与本次新鲜冻结的 `subject_sha`（:460）比对。
作为对照，H5 观察者席位**是比对**的（:93 / :135 / :394）——
所以这不是"设计上不比对"，是**确定性门禁这一侧漏了**。

后果：门禁跑完后改 manifest，只要不动任何 gate 的 `command` 数组
（`required` / `claims` / `subject_files` / `min_observer_families` 全在此列），
钉死值不变、12 份日志不变、证据包照样 `ok=true`。

### 1.3 钩子拿时间戳冒充"自建"

```js
const fileTime = Math.max(stat.birthtimeMs || 0, stat.ctimeMs || 0, stat.mtimeMs || 0);
if (fileTime >= sessionStartTime - 30000) return true;
```

Windows 上 `ctimeMs` 是 MFT 记录变更时间（复制、改名落位、改属性都会刷新），
`mtimeMs` 任何内容写都会刷新。三者取 max = "任一时间戳新过就算自建"。

主控亲手复跑结果（WO-0103 四条反证全过，三条加压全不过）：

| 用例 | 目标 | 预期 | 实测 |
|---|---|---|---|
| 反证 A | 本回合自建 49B 探针 | 放行 | 放行 ✓ |
| 反证 B | 非自建目录 | 拦截 | 拦截 ✓ |
| 反证 C | 20 个自建文件 | 拦截 | 拦截 ✓ |
| 反证 D | `--dry-run` | 预览且不改状态 | ✓ |
| 加压 E | 既有未跟踪文件，本回合仅被写过一次 | 拦截 | **放行** ✗ |
| 加压 F | 三个时间戳均为 3 小时前的既有文件 | 拦截 | **放行** ✗ |
| 加压 G | 5 小时前创建、本回合被写过的既有文件 | 拦截 | **放行** ✗ |

### 阶段 2：证据链补双向钉死（必做）

`generate_evidence.py` 启动校验增加两条硬断言，不一致即 `RuntimeError` → RC=1：

1. `ledger["manifest_sha256"] != sha256(manifest bytes)` → 报错，

**不得**用"以写入方为准"或"跳过该 gate"之类降级继续跑——本单要消灭的正是静默分裂。

### 阶段 3：钩子"自建"判据改用真实创建记录（必做）

`isSelfCreatedTarget()` 改造，二选一并说明取舍：

- **A（推荐）**：写文件时登记创建台账（path + session + 时间），判定查台账；
- **B（最小改动）**：只用 `birthtimeMs` 单项与 session 目录创建时间比较，
  **去掉 `max(...)` 里的 `ctimeMs`/`mtimeMs`**。⚠️ **只改 `max()` 不够**，
  `sessionStartTime` 那侧同样坏，必须一起改（实测见 §五 第 6 条）：
  - `sessionStartTime = Math.min(bStat.birthtimeMs || bStat.ctimeMs, bStat.ctimeMs || bStat.birthtimeMs)`
    ——`birthtimeMs` 取不到（个别卷/挂载点为 0）时 `min(0, ctime)` 退化成 **0**，
    于是 `fileTime >= 0 - 30000` 恒真，**全部目标都算自建**；
  - `stat` 失败时的兜底是 `now - 3600 * 1000`，即**窗口地板 1 小时**，
    不是"本会话创建"。
- 无论 A/B，都要有 fail-closed 分支：取不到创建时间就判非自建，不许放行。

无论选哪条，必须新增反证并亲手跑：

- **反证 H**：既有未跟踪文件，本回合仅被写过一次 → **仍判非自建、维持拦截**。
- **反证 I**：既有文件只被改元数据（如 PowerShell 设 `CreationTime`，或改名/复制落位）
  → **仍判非自建、维持拦截**（专打 `ctimeMs` 被"改属性"刷新这一条）。

### 阶段 4：把修复纳入版本控制（必做）
