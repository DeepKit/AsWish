## 背景：为什么这张票值得单开

WO-0047 收尾时连修了两条 gap（GAP-04 证据编号可解析、GAP-06 生成物不污染
目标仓库），两条都必须**在 CLI 里再改一遍才生效**。根因是同一件事：

**scan 的编排有两份，而"渲染"这一段的编排有五份。**

```
GUI 编排   → src/controllers/AsWish.Controller.pas  RunScan（走 TAsWishController）
CLI 编排   → cli/AsWish.CLI.dpr                     RunScan（直接用各 Service，不用 Controller）
```

Controller 内部还有三个各自独立的渲染序列：

| 位置 | 方法 | 何时走到 |
|---|---|---|
| `AsWish.Controller.pas:476` | `RenderAll` | 常规全量渲染 |
| `AsWish.Controller.pas:560` | `RefreshFromYaml` | 从 YAML 重载后刷新 |
| `AsWish.Controller.pas:1084` | `RunScan` 内联 | 扫描时 |

外加 CLI 自己那一份（`AsWish.CLI.dpr:1014` 起）。**五处各自列
`RenderScanReport` / `RenderIndex` / `RenderTree` ×4 / `RenderProblemsPage`。**

这不是假设风险，是已经发生的事实：本次 GAP-04 新增的
`RenderEvidencePage`，五处序列里**只有 CLI 那一处调用了**。
也就是说 GUI 用户到现在仍然看到不可解析的裸证据编号，
而命令行用户看到的是修好的——同一个仓库，两种行为。

## 轨道 A · 把渲染序列收敛成一份（P1，正解）

### A-1 五处渲染序列合一
- **现状**：`RenderAll` / `RefreshFromYaml` / `RunScan`（Controller 三处）
  + CLI 一处，各自手写同一串调用。加一个页面要改五遍，漏一处就是
  "GUI 和命令行行为不一致"，而没有任何测试能发现。
- **方案**：抽出一个 `RenderStandardPages`（命名自定），把
  "scan-report → index → evidence → 四棵树 → problems → bundles"
  的固定序列写成一处。三处 Controller 场景与 CLI 都调它；
  真正有差异的部分（如 `RunScan` 里多一个 decisions 页面）以参数或
  前置/后置钩子表达，不复制整段序列。
- **验收**：Controller 与 CLI 里"逐个 RenderXxx 调用"的序列各只剩一处；
  grep `RenderTree(` 在 `src/` 与 `cli/` 的命中数等于"定义 1 处 + 递归自调用"。

### A-2 渲染顺序成为可测约束，而不是注释
- **现状**：`evidence.html` 必须先于树页面渲染，这个约束现在只以一行
  注释的形式存在于 CLI（`AsWish.CLI.dpr` 渲染序列上方）。注释不执行。
- **方案**：把"先证据台账、后树页面"的顺序约束写进 A-1 抽出的那个方法体内，
  并加一条测试直接对它断言，不经过任何入口。
- **验收**：新增测试直接调用收敛后的渲染入口，验证
  `evidence.html` 存在时树页面输出的是链接而非裸编号。

### A-3 CLI 不再自建 scan 流程
- **现状**：`cli/AsWish.CLI.dpr` 的 `RunScan` 约 100 行，直接持有一组 Service，
  自己编排顺序。CLI 的 uses 里逐个列了 15 个 src 单元——它实际上是
  Controller 的一个平行副本。
- **方案**：CLI 只保留参数解析与输出；scan 编排统一走
  `TAsWishController`。CLI 需要的行为（静默 / 进度行 / 退出码）
  通过 Controller 已有的状态/回调通道拿到，不让 CLI 回去摸 Service。
- **验收**：`cli/AsWish.CLI.dpr` 的 uses 中不再出现
  `AsWish.Services.SpecStore` / `AsWish.Services.TreeBuilder` /
  `AsWish.Services.Render` 等被 Controller 包住的单元。

### A-3 保留差异的入口行为显式化
- **现状**：CLI 与 GUI 的合理差异（CLI 无 WebView 桥、GUI 有）现在是隐式的，
  因为两套流程本来就不一样。
- **方案**：统一后，把入口差异收敛成 Controller 的少数几个开关/事件，
  在接口处命名写清楚，不散落在两个入口里。
- **验收**：差异点能在 Controller 接口上一眼数完。

## 轨道 B · 防再分叉（P2，成本低收益高）

### B-1 一条"入口等价"测试
- **现状**：没有任何测试能发现"CLI 改了 GUI 没改"。
- **方案**：对一个固定 fixture 项目，分别跑 Controller 扫描与 CLI 扫描，
  断言两者产出的 `.AsWish/html/` 文件集合一致（不要求逐字节相同，
  时间戳/footer 会漂）。
- **验收**：人为只在 CLI 加一个渲染调用，该测试必须转红。
  **这条测试必须亲眼看过转红才算数**（规矩：见 `AGENTS.md` 与反馈记忆）。

### B-2 架构红线写进文档

- 指向 `AsWish.Controller.pas` 作为唯一编排点，不复述其内容。

## 执行中追加发现与修复（2026-09-25）

在给 A-2 补回归测试时，测试第一遍就没绿——暴露出两个先于本单存在、
且直接击穿 A-2 验收前提的缺陷。均已隔离复现、修复、并各自看过转红：

### 追加缺陷 1 · 文档派生的功能节点根本不出现在页面上
- `BuildDocsFunctions` 把子节点 id 收进 `LFuncChildren` 后**没有赋回根节点**就
  释放了。`RenderTree` 只认 `Children` 不认 `ParentId`，于是这些节点写进了
  `function-tree.yaml`，却永远不出现在 `function-tree.html`。
- 同一文件里 `BuildViewsFunctions`（:591）和数据树（:1848）都做了赋值，
  只有这条路径漏了。
- **实测**（AsWish 仓库自身，820 文件）：修前 `function-tree.html` 渲染 1 个
  节点，YAML 里 201 个。

### 追加缺陷 2 · 根节点 id 绕过 UniqueId，与文档标题撞号
- 四棵树的根 id 是手拼的（`'func-' + LRootSlug` 等），没走 `UniqueId` 注册。
  本仓库 README 的 `# AsWish` 标题与项目名同 slug，派生节点直接拿走了根节点的
  id。`RenderTree` 用 `AddOrSetValue` 建映射，同 id 的后来者覆盖根节点，
  整棵树的兄弟节点全部孤儿。
- 修前 `function-tree.yaml` 里有 **两个** `func-aswish`，201 个节点渲染出 1 个。
- 数据树的根本来就走 `UniqueId`（:1831），功能/模块/界面三棵没走。

### 修复方式
不逐点打补丁，收敛成**一处**根因修复——`BuildFromScan` 末尾统一跑
`LinkChildren()`，由 `ParentId` 反推 `Children`（含自环保护，防 `RenderNode`
无限递归）；同时三棵树的根 id 改走 `UniqueId`。
这正好是 A-1 主张的方向：同一条约束只写一遍。

### 修复后实测（同一仓库，同一命令）
| 树 | YAML 节点 | 渲染节点 | 证据链接 |
|---|---|---|---|
| function | 201 | 201 | 200 |
| module | 137 | 137 | 136 |
| view | 31 | 31 | 30 |
| data | 451 | 451 | 450 |
| **合计** | | | **816** |

四棵树重复 id 均为 0。**修前全站只有 64 个节点能被看见。**

## 需要老板裁定的未决项（不阻断本单，但影响产品方向）

来自 GAP-06：**规格状态（`trees/` `evidence/` `issues/` `decisions/`
`relations/`）到底该不该进用户的版本控制？**

- 跟踪它们：这是本工具的核心资产，变更历史可能正是用户要的。
- 不跟踪：每次扫描都大幅翻动，提交进去就是持续的 diff 噪音与合并冲突。

当前实现取的是"不擅自决定"：派生的全 ignore，规格状态的留下、在生成的
`.gitignore` 里写清取舍、CLI 末尾打印一行告知。本单按此现状推进，
裁定下来后如需调整，只需改 `WriteGitIgnore` 一处。
