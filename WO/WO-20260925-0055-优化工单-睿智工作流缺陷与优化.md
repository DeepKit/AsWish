## 3. 逐项：现象 · 复现 · 根因 · 优化方案

### 3.1 M1 · 会议系统的共识/分歧产物恒为空（P0）

**现象**
`run_meeting` 返回的 advice pack 里，五个承载实质内容的字段永远是空数组：

```
ok            = True
status        = completed
families      = ['f1', 'f2']
participants  = ['m.a', 'm.b']
consensus     = []
disagreements = []
risks         = []
evidence      = []
detect_consensus = []          # diverge_merge 对该 pack 的共识检测
validate_ok   = True           # validate_advice_pack 判定为合法
```

而同一时刻，backend 明明返回了带 CONSENSUS / DISAGREEMENT / RISKS 的实质内容，
只存在于 `backend-output.txt`，**没有任何东西解析它**。

**复现（已跑）**
用 `CommandResult` 伪 runner 注入固定 stdout，两个 family、两个 role，
`run_meeting(..., runner=FakeRunner)`，不调用真模型。完整脚本见 §4。

**根因**
`bcw_work_system/meeting.py` 第 511–515 行，构造 pack 时把这五个字段**硬编码为
`[]`**，此后全文件再无写入点（grep 确认：`consensus` 在 meeting.py 只出现在第
511 行）。下游 `diverge_merge.py:120` 的 `detect_consensus` 读
`pack.get("consensus", [])`，`detect_disagreements` 读 `pack.get("disagreements", [])`
——**上游恒空，下游永远算出空**。整条共识/分歧管线是空转的，但 `status` 报
`completed`、`validate_advice_pack` 判合法，**没有任何信号提示它是空的**。

**优化方案**
按依赖顺序三条，前两条不破 schema：

1. **先加可见性（最小改动，立刻止血）**：`validate_advice_pack` 增补一条软校验
   ——当 `status == "completed"` 且 `backend.returncode == 0` 但五个语义字段全空时，
   给出 `ADVICE_SEMANTIC_EMPTY` 告警码。**不 invalidate**（advice pack 仍合法，
   不破坏既有消费方），但让"完成但无内容"变成机器可判定的状态，而不是静默。
2. **再补结构化产物**：`advice-pack/v2` 增加 `backend_parse` 节，记录"本次是否
   尝试过从 backend stdout 抽取语义字段、抽到几条、失败原因"。
3. **最后补真正的抽取**：为 `decide` / `fastmeet` / `diverge` 定义一份
   `advice/findings/v1` 结构化输出约定（每个模型输出 JSON findings），
   `run_meeting` 按该约定抽取并填五个字段；抽取失败即落入第 1 条的
   `ADVICE_SEMANTIC_EMPTY`，fail-closed 而不是静默填 `[]`。

**为什么不让主模型手动压缩**：Amy 技能规范要求"第三方返回先存运行报告，
再压缩为共识/分歧/证据回到主会话"——压缩这一步当前完全靠人肉，因此实际上从未
发生在 pack 里。这是流程要求落在了一个不会自动执行它的地方。

### 3.2 M2 · `meeting_id` 复用抛裸 `FileExistsError`（P1）

**现象**
同一个 `meeting_id` 第二次调用 `run_meeting`：

```
run 1: True
run 2 (same meeting_id):
  UNHANDLED FileExistsError [WinError 183] 当文件已存在时，无法创建该目录。
```

**根因**
`meeting.py:486` `run_dir.mkdir(parents=True, exist_ok=False)`。本模块其余所有
失败路径都是带稳定 code 的 `MeetingError`，只有这一条是裸 OS 异常。

两层后果：

1. **进程内调用方漏接**：`pipeline` 编排层若写 `except MeetingError`，
   这条会穿透。CLI 的 `main()` 第 613 行把 `OSError` 一并接住了，进程不崩，
   但降级成 `{"code": "FileExistsError"}`——不是一个注册过的语义码，
   无法进 `exit_codes.py` 的语义化分支，也无法判重试。
2. **会议是单次资源**：id 一次一用，重跑/续跑必须先手工删目录。

**优化方案**
`mkdir` 前显式判定并抛 `MeetingError`：

```python
if run_dir.exists():
    raise MeetingError(
        "MEETING_RUN_DIR_EXISTS",
        "meeting_id 已运行过，重跑请换 id 或先清理 run 目录",
        {"run_dir": str(run_dir)},
    )
run_dir.mkdir(parents=True, exist_ok=False)
```

要不要支持"同 id 覆盖重跑"是策略问题，但**必须是编码后的策略问题**，
不是裸 `FileExistsError`。

### 3.3 V1 · 空转测试反复出现（P0，本工作单链内 ≥3 例）

**现象**
新增的回归测试跑绿，但对它要防的缺陷**不敏感**——把被测实现改坏，测试依然绿。

本工单链内至少 3 例：

| 例 | 位置 | 空在哪 |
|---|---|---|
| a | WO-0052 BUG-B | 回归测试 + 一处冗余 `LoadPersistedTrees` |
| b | 本轮 builder-loop 测试 | 断言了一个恒真条件 |
| c | 本轮 empty-dir-detect 测试 | fixture 构造使分支不可能被走到 |

另有 1 例（`func-partial-batch`）**差点**成为第 4 例——见 3.4。

**根因**
测试写完后只跑了"绿"，没有"改坏实现看它变红"。绿只证明没编译错、没抛异常，
**不证明它在守东西**。这是本次工单链内**重复次数最多的单一缺陷类型**，
且每次都靠我在收尾时手工变异才发现。

**优化方案**
把"看过它变红"变成不可跳过的一步，而不是靠自觉：

1. 新增/修改测试时，**同一回合内**必须附带一条变异记录：改坏哪个条件、
   亲眼看到哪条断言转红、再改回。没有这条记录的测试不算完成。
2. 对 `Test_*` 补一条元数据约定：测试注释里写 `# 变红条件: ...`，
    reviewer 能直接看出它守的是什么。
3. 对已有 322 条测试做一次**存量变异抽查**（随机抽样 N 条，逐条改坏断言目标），
   把空转测试找出来。这是本工单的验收项之一，不要再留给下一次开发时偶遇。

**当前已修的样例**（证据在 `tests/Test.AsWish.Controller.pas`）：
`Test_IngestCandidateNodes_RejectedCandidateWritesNothing`
（第 1674 / 1715 行，fixture 字面量 `func-partial-batch`）就是为此加强后的形态——
它断言的是**部分合法批次必须整批拒绝**，而原始的"全坏批次"版本测不出这个，
因为全坏批次本来就没东西可写。

### 3.4 V2 · 变异存活：分不清是"测试没覆盖"还是"变异本身是 no-op"（P0）

**现象**
一次变异测试中，我把拒绝分支的写回条件改成恒真，**测试依然全绿**。
第一反应是"测试空转"，但改完 fixture 后同一条变异立刻转红。

**根因（关键）**
那次变异是 **no-op，不是测试空转**。`ValidateNode` 在拒绝时会把 id 清零，
被拒节点根本进不了 `LIngested.Accepted`，于是 `MergeInto` 收到空列表、
永远不写盘——**那个变异在语义上不可能改变任何行为**。我拿去改测试是白费，
而且会为它编一个漏洞百出的加强理由。

**优化方案**
变异测试必须区分两种存活，因为处置方式完全不同：

- `UNDETECTED`：变异改变了行为但测试没抓到 → 该加强的是**测试**。
- `INERT`：变异在语义上不可能改变行为 → 该改的是**变异本身**，
  加强测试是浪费，且会误导后来人以为那里有守卫。

实施：变异 harness 对每个变异先跑一次"变异前后行为等价性检查"
（在原 fixture 上比对可观测输出），判定 `INERT` 的变异直接标记不计数，
并提示"请换一个有语义的变异"。这条不实现，变异测试的次数就会掺水，
而掺进去的恰恰是**看起来最像在验证** 的那一批。

### 3.5 E1 · 无 `.gitattributes`，Python 文本模式整文件 LF→CRLF（P1）

**现象**
一次用 Python 改 `.pas`，commit 从预期的约 20 行变成 **2373 行**——
整个文件被判为变更。

commit `c8e6085` 的 message 记录了根因：Windows 文本模式下
`io.open(p, 'w', encoding='utf-8')` 会把所有 LF 转成 CRLF。
仓库 `core.autocrlf=false` 且**没有 `.gitattributes`**，LF 约定只存在于人脑里，
工具不会替你守。

**复现（已跑）**字节级复核三个源文件，当前状态是干净的：

```
src/controllers/AsWish.Controller.pas  LF=2579  CRLF=0
cli/AsWish.CLI.dpr                     LF=1482  CRLF=0
tests/Test.AsWish.Controller.pas       LF=1965  CRLF=0
```

注意：`grep -c $'\r'` 在 msys 下会给出全文件命中的**假阳性**，
我本次差点据它写错结论——行 endings 只能字节级判定。

**优化方案**
1. 加 `.gitattributes`：`*.pas text eol=lf` / `*.dpr text eol=lf`。
   这是结构性修复，从此任何工具都不可能再把 LF 写坏。
2. 所有改写 `.pas` 的 Python 一律 `newline=''`，并在提交前跑一次字节级
   CRLF 计数（不接受 grep）。
3. 把"整文件 diff 行数 ≫ 预期"列为 commit 前自检项——本次两个 case
   （CRLF、BOM）都表现为此。

### 3.6 E2 · BOM 不一致，放大"整文件看起来变了"（P2）

**现象**76 个 `.pas` / `.dpr` 里，48 个带 UTF-8 BOM、28 个不带。
没有规则，全看当初是谁写的。

**根因**同 E1：约定不在机制里。BOM 差异让 diff 工具更容易把整文件判为变更，
是 E1 的配套放大器。

**优化方案**随 `.gitattributes` 一并定：明确 BOM 政策（建议统一去 BOM，
Delphi 对无 BOM UTF-8 读取正常，且已在 28 个文件上验证过可用），
存量一次性归一。

### 3.7 E3 · `OpenProject` 两个实现语义不同，未实测就写注释（P1）

**现象**
我为删掉一处 `OpenProject` 调用写了注释："省掉的是三个目录的创建"。
事后读 `TAsWishProjectService.OpenProject` 才发现它**完全无副作用**，
只记路径——三个目录是 **Controller 的** `OpenProject` 建的。
注释是错的，而且错得很自信。

**根因**
两个同名方法语义不同，我在未实测的情况下把其中一个的性质断言到另一个上。
这与 3.3 是同一个病：**没测就下结论**。

**优化方案**
1. 注释只写**已测量**的事实；未测量的理由写成"待验"，不写成结论。
2. 同名不同义的方法，改名以示区分（`OpenProjectSilent` / `OpenProjectWithDirs`），
   让误用不可能发生。
3. 与 V1 共用一条元规则：**任何"这样改更安全/更轻"的断言，都要有一次实测背书。**

### 3.8 E4 · `git checkout <path>` 销毁未提交工作，无护栏（P1）

**现象**一次 `git checkout src/controllers/AsWish.Controller.pas`
把尚未提交的 `IngestCandidateNodes` 能力和 `TIngestResult` 直接抹掉，
只能靠 `git log` 确认未提交范围后从笔记原文重写。

**根因**`git checkout <path>` 在 Git 语义里就是丢弃工作区改动，
但我是在"想回退某个改动"的心智模型下用的——**心智模型与命令语义不符，
且没有任何东西提前告诉我这一点**。

**优化方案**
1. 本机 git 配置 `alias.st = status` 之外，把 `checkout -- <path>` 列入
   **每次使用前必须 `git stash list` + `git diff --stat`** 的清单。
2. 更有效的结构性改法：**先 commit 再 checkout**，或用 `git switch --detach`
   到临时位置取旧二进制。本次取"修改前版本"比较的正当做法是
   worktree（`07b9312` 那次就是这么做的，安全），不是 checkout。
3. 开发中每个能力做到"能编译 + 测试过"就立刻 commit，
   不在工作区攒未提交的大块改动。
