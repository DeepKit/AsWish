## 根因（已埋点证实，埋点已全部撤除，HEAD 干净）

`src/app/AsWish.MainForm.pas:1980`：

```pascal
LHasConsole := AttachConsole(ATTACH_PARENT_PROCESS);
if not LHasConsole then
  LHasConsole := AllocConsole;
```

主控埋点实测（`cmd /c ... 2> file` 下）：

```
before:   GetFileType(GetStdHandle(STD_ERROR_HANDLE)) = 1   (FILE_TYPE_DISK，重定向的文件)
AttachConsole(ATTACH_PARENT_PROCESS) = 1                    (成功，GetLastError=0)
after:    GetFileType(GetStdHandle(STD_ERROR_HANDLE)) = 2   (FILE_TYPE_CHAR，控制台)
```

**`AttachConsole` 会换掉进程的 std 句柄**：从"重定向到的文件"变成"控制台"。
于是：

1. `ConsoleError` → `OutputConsoleError` 拿到的是**控制台句柄**，写进去的内容
   进的是控制台屏幕缓冲，**不是那份被重定向的 stderr 文件**；
2. 异常处理末尾 `if LHasConsole then FreeConsole;` 把控制台摘掉，输出彻底消失；
3. 所以操作工/CI 拿到 exit 1 + 零诊断，与修复前一模一样。

对照组证明这不是平台限制：同一进程里 WebView2 的 Chromium 日志能到 stderr
（它自己有挂控制台的路）；`AsWish.dpr` 入口那条 `AsWish.exe foo bar` 路径
**从不调用 `AttachConsole`**，所以 `OutputConsoleError` 同一份代码在同样条件下
能把 257 字节用法块正确写进 stderr 文件。

**同一根因还打中成功路径**（机制已在同一进程同一位置实测，端到端未验，见下）：
`ConsolePrint`（`[GUI-VERIFY] Step 1..10` 那些进度行）走
`GetStdHandle(STD_OUTPUT_HANDLE)`，attach 之后同样是 FILE_TYPE_CHAR。
也就是说 `bin\AsWish.exe --gui-verify <dir> > log 2>&1` **成功时也会拿到一份
空 log**——取证工具把证据弄丢，属于最严重的那类静默失败。本机没有 Evergreen
WebView2 Runtime，成功路径我跑不到，所以这条标 `mechanism_proven_end_to_end_unverified`，
不许当已验证事实引用，但修的时候必须一并处理。

## 修法（主控定默认路线，允许提更优解但需附实测对照）

**核心原则：attach 之前把原始 std 句柄存下来；写的时候优先用存下来的句柄。**

- 在 `RunGuiVerification` 调用 `AttachConsole`/`AllocConsole` **之前**，
  捕获 `LStdErrOrig := GetStdHandle(STD_ERROR_HANDLE)` 与
  `LStdOutOrig := GetStdHandle(STD_OUTPUT_HANDLE)`（模块级或显式传入，别用隐式全局）。
- `ConsolePrint` / `ConsoleError` 的写入目标按这个优先级：
  1. 原始句柄有效且 `GetFileType` 为 `FILE_TYPE_DISK(1)` 或 `FILE_TYPE_PIPE(3)`
     → 写原始句柄（这是"被重定向/被捕获"的场景，就是本次要救的）；
  2. 否则写当前句柄（交互终端的场景，保持现状不回归）。
- `OutputConsoleErrorEx` 保持可注入（现有 `AGetStdHandle`/`AAttachConsole`/`AWriteFile`
  三个形参的形态是对的），把"句柄选择"做成可测的纯逻辑，别把 `GetFileType`
  硬编码在写路径里测不到。
- 不要为了让 stdout 有输出而在成功路径加噪音；不要复制第二份控制台写出实现
  （`ConsoleError` 已复用 `OutputConsoleError`，这个方向对，保持）。

## 顺带记录的睿智工作流缺陷（主控本轮亲测，供优化工单取用）

1. **验收 harness 选错场景 = 假绿灯**（本轮 F-3 的教训）：管道场景下
   `GetStdHandle` 恒有效，`AttachConsole` 兜底分支永远不会执行，于是"修没修好"
   在harness里根本不可观测。根因是**下发的验收条件没指定复现场景**——这是主控
   的漏项，但规则层面应升级为：**凡引用"静默失败/控制台/std 句柄"类缺陷的验收，
   必须写明运行场景（重定向 vs 管道 vs 交互）**，否则下游会用最方便的场景验证。
2. **门禁仍只覆盖源码不覆盖取证路径**：`--gui-verify` 是"必须把证据落盘/落控制台"
   的取证工具，而它自己就是个静默失败点，没有任何门禁能发现。
   建议：把 `--gui-verify` 在无 WebView2 宿主上的 fail-closed 播报
   （exit 1 + stderr 含 `GUI-VERIFY-NO-WEBVIEW`）做成一条可无人值守的门禁，
   每次构建顺手证明取证路径没哑。
