## 任务（单事项）

**已核实的代码事实**：`src/app/AsWish.MainForm.pas:2100-2105`，

```pascal
FProgressFailCount := 0;
try
  with TFileStream.Create(FProgressFile, fmCreate) do
    Free;
except
end;    // ← 截断失败无任何专属信号
```

**主控实测证据（哨兵实验）**：先往 `gui-verify-progress.txt` 写一行哨兵
`SENTINEL-FROM-PRIOR-RUN | must be truncated on a healthy start`，
再用 Win32 `CreateFileW(dwShareMode=0)` 全程独占该文件后跑 gui-verify：

```text
exit code = 0   elapsed = 12.1s
PROGRESS-WARN in stderr       : True  | count = 1
sentinel survived             : True      ← 上一轮的内容原样留在文件里
```

也就是说：**截断失败时，文件里上一轮的内容原封不动**。
0080 的那一条告警（`Cannot create file ...`）是后面第一次 append 失败时
报出来的，恰好也覆盖这个场景，所以整轮跑下来读者还是能看出"出过事"；
但只要阻塞在启动后的**毫秒级窗口**内解除（杀软扫描、备份、索引器
短占用完全做得到），后续 append 会**成功**并在陈旧内容之后追加，
产出一份**看起来连续、实则横跨两轮**的"混合证据"：

- 首行是**上一轮**的时间戳，本轮行数紧接其后 → 任何"首行必须是本轮时间戳"
  或"跨轮次字节比对"的断言**静默失效**（WO-0079 B 项刚堵上的那类污染）；
- 人读证据时无法从文件本身判断它是不是单轮产物。

**默认路线（按此实现，须说明理由）**：

1. **截断失败必须 fail-closed**：一旦 `TFileStream.Create(..., fmCreate)` 抛异常，
   立刻（a）输出一条**专属**告警
   `[PROGRESS-WARN] progress log truncate failed: <异常消息>`
   （走既有 `ConsoleError` + `AddCaptureWarning`，与 0080 的告警同族不同义，
   不许复用同一条文案否则读者分不清是截断还是追加失败）；
   （b）**把 `FProgressFile` 置空**，本运行后续不再写入该文件。
   理由：这份文件已经不可信时，唯一安全的选择是**弃用并声明**，
   而不是留着让本轮日志追加到陈旧内容后面。弃用后
   `LogProgress`/`AddCaptureWarning` 的 `FProgressFile = ''` 短路天然生效，
   且 `gui-dual-surface.txt`（`LLog.SaveToFile` 在跑完后一次性落盘）
   仍然是本轮完整证据，不会造成证据全丢。
2. **不许**把截断改成"每次写前都先截断"——那会破坏逐次 append 的
   WO-0075 语义（硬杀也能保住已写入的行）。
3. **不许**为了这个把 `FProgressFailCount` 清零动作挪位或改动 0080 已确认的
   计数/告警逻辑；两者要能同时成立（截断失败时计数应保持 0，
   因为置空文件后根本不会再走到写路径）。
4. **不许**改 `LogProgress` 行格式、`LogStepProgress` 结构、
   以及 `state=done rc=0` / `state=error ...` 两条终点行。
