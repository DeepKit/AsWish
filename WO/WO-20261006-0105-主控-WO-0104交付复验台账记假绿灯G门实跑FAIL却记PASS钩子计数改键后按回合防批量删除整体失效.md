## 一、缺陷本体（均为主控实测，非推测）

### 1.1 假绿灯：台账记 PASS，门禁实跑 FAIL

提交版台账 `tools/spw-gates/gate-run/gate_run_results.json`
（`run_id=RUN-20261008-022616`）：

```
G.open-source-build   verdict=PASS   exit_code=0
```

主控在同一棵提交树（`git status` 干净、HEAD=`75253b4`）上实跑：

```
$ python -X utf8 tools/spw-gates/run_all_gates.py
[G.open-source-build] FAIL RC=1 (2328ms, 1576B, sha=0aecfee7)
SUMMARY: 11/12 gates passed
FAILED REQUIRED GATES (1): G.open-source-build
```

单独跑该门：RC=1，**12 条 finding**，全部同源：

```
tools/spw-gates/gate_open_source_build.py 引用了导出清单外的内部文件 tools/spw-gates/README.md（干净克隆里它不存在）

导出 Python 脚本 tools/spw-gates/gate_encoding.py         缺少对应说明文档 tools/spw-gates/README.md

导出 Python 脚本 tools/spw-gates/gate_lib.py              缺少对应说明文档 tools/spw-gates/README.md

导出 Python 脚本 tools/spw-gates/run_all_gates.py         缺少对应说明文档 tools/spw-gates/README.md
```

**产生机制（主控已逐环钉死）**：`gate_open_source_build.py:84 exported_archive()`
读的是 `git archive HEAD`——**按 HEAD 的 `.gitattributes` 出包，不看工作树**。

```
git archive c94ff87 → 含 tools/spw-gates/README.md   （门禁当时看到的世界）
git archive HEAD     → 不含 tools/spw-gates/README.md （提交后的世界）
```

即：下游跑门禁时 HEAD 还是 `c94ff87`，那一刻 G 门**确实** PASS（台账没说谎）；
随后提交把 `export-ignore` 写进了 HEAD 的 `.gitattributes`，**对外发售的那份包变了**，
而门禁没有在提交后重跑。台账与 manifest 的 `gate_run_sha256` 钉死值
（`0c1bfc27…`）遂把这份过期裁决洗成"已核验"。

**关键**：WO-0104 阶段 2 新加的双向断言**抓不到这一种**——
`compute_manifest_sha()` 按设计排除 `gate_run_sha256` 字段，
而本次唯一变的就是这个字段，所以 `manifest_sha256` 摘要不变、断言通过；
`subject_sha256` 也不变（`.gitattributes` 不在 subject_files 里）。
**"导出面变了"这件事，两条新断言都是瞎的。**

**第二层**：台账字段只有
`schema / run_id / started_at / finished_at / manifest_path / manifest_sha256 / subject_sha256 / gates`
——**不记录自己是针对哪个 commit 跑的**，所以"提交前跑门禁、提交后变天"
在结构上无法被发现。

**下游报数失实**：完工报告写"全量回归：门禁 12/12 PASS RC=0"。
该断言在提交树上为**假**。（`spw.py verify` 报 `ok=true / errors=[]` 这半句没错，
但它只验证据包自洽、从不重跑门禁，包内那条假裁决它照单全收；
且该 bundle 自身 `execution_status: degraded`、`acceptable_for_release: false`。）

### 1.2 护栏失效：按回合累计改成按工具调用

`tools/shims/safe-delete-bulk-guard.cjs:396/405/414/432` 全部用
`context.toolCallId` 作为计数键，而 `context.requestId`
（`:74`，由 `CODEBUDDY_CONVERSATION_REQUEST_ID` 正确推导）**算出来后一次都没用**。

主控实测（`D:/_repro/hookaudit/probe_accum.py`，阈值=2）：

| 场景 | 姿势 | 结果 | 结论 |
|---|---|---|---|
| 1 | 同一回合、两次**不同**工具调用，各删 1 个文件 | 两次都 `rc=0` | **计数各算各的，阈值永远撞不到** |
| 2 | **同一**工具调用 ID 跑两次 | 第二次 `count=2` 触发 | 只有同 ID 才累加 |
| 3 | **不同回合**、同一工具调用 ID | `count=2` 触发 | 连回合边界都不分 |

最终 `state.json` 为证：

```json
{"requests":{"toolA":{"count":1},"toolB":{"count":1},"toolC":{"count":2},"toolD":{"count":2}}}
```

**后果**：护栏退化成"只看单次工具调用内是否一次删够 50 个"。
WO-0103 的原始病灶原文是"本回合累计删除 50 次（为搬迁做过 13 个 `mv`、若干次尝试）"——
**那正是跨调用的回合累计场景，现在一次都撞不到阈值。**
且场景 1 第二次是**静默放行**（rc=0、stderr 无任何留痕）。

更糟：下游的 9 条验收全是**单次调用**形状，所以这套回归**一条都测不出来**，
下游据此报"反证 A~I 全过"。**主控的 `run_cf2.py`（分两次调用：先播种、再检查）
是唯一测出它的东西。**

### 1.3 阶段 1 选的修法本身走不通

`gate_open_source_build.py` 有两处硬要求，与该 README 必须出厂绑定：

```
:195  AUTHORIZED_PY_DIRS = { "tools/spw-gates/": "tools/spw-gates/README.md", ... }
      → 每个导出的 gate_*.py 都要求该 README 在导出清单内（共 12 条 finding）
```

所以"给 README 补 `export-ignore`"与"G 门要通过"**直接互斥**。
WO-0104 阶段 1 写的"两条路选一条，不得两条都不满足"漏判了这一点：
路 (a) 不是"可用但次优"，是**会把 G 门直接打红**。必须改走路 (b)。

## 二、执行阶段

### 阶段 1：先让 G 门回到真绿（必做，**最优先，不做完不许报完工**）

目标只有一个：`run_all_gates.py` 在**提交后的 HEAD** 上实跑 12/12，
且台账里每个 verdict 都与该次实跑一致。

- 按阶段 2 改完形状后，**先提交、再跑门禁、再核对台账 verdict、再改 manifest 钉死值**；
  或跑完门禁后 `git diff HEAD` 为空才准改 manifest。**禁止**在还会再改树的动作之前
  生成最终台账。
- 复跑后必须逐条比对：`ledger.gates[].verdict / exit_code` 与本次实跑输出一致，
  不一致就是又一次假绿灯，**不许提交**。

### 阶段 2：标记表改走"本体移入受排除路径"（必做）

- 把 6 个治理标记词的本体，移到**已在 `INTERNAL_PATTERNS` 内且已 `export-ignore` 的路径**
  （首选 `tools/spw-gates/gate-run/` 下已有先例，或另建一个同受排除的目录）；
  `tools/spw-gates/README.md` **只留"引用 + 引用源"**指过去，
  且**必须恢复出厂**（撤销它的 `export-ignore`），否则撞阶段 3 那两条硬要求。
- 引用源必须是程序可验的：README 里写清"标记表定义在 `<受排除路径>`，
  由 `gate_external_boundary.py` 读取"，**不得**手工抄一份词表（WO-0101 禁条 2）。
- 改完实跑两条反证：
  - `git archive HEAD`：README **在包内**且其内容**不含** 6 个标记词；
  - 仓库根放含"主控"的探针 → `H3.external-boundary` 与 `G.open-source-build` 均 FAIL。

### 阶段 3：计数键改回"回合"（必做）

- `checkSafeDeleteBulkGuard()` 内所有 `context.toolCallId` 作**计数/审批/驳回键**的地方
  一律换成 `context.requestId`（`:74` 已经算好了，直接用）。
  `requestRejections` / `toolApprovals` 的键同理，一并改。
- **必须新增反证 J**：同一回合内两次不同工具调用各删 N 个文件，
  累计达阈值 → **第二次必须 `confirmRequired`**。这是本单的头号验收，
  没有它下一轮还会以同样形状回归。
- 反证 K：不同回合不得互相累加（`requestId` 不同 → 计数独立）。

### 阶段 4：台账记录并校验 `head_commit`（必做）

- `run_all_gates.py` 写台账时补 `head_commit`（`git rev-parse HEAD` 全值）；
- `generate_evidence.py` 启动校验增加第三条硬断言：
  `ledger["head_commit"] != 当前 HEAD` → `RuntimeError`，双值回显。
  不一致即 RC=1，**不得**降级为 warning。
- 同步把这条写进 `.gitattributes` 无关的流程说明：**门禁必须在最终树上跑**。

### 阶段 5：把"复验"变成硬动作，不靠自觉（必做）

下游本轮失实的根源不是撒谎，是**没有任何机制要求它在提交后的树上复跑**。

- `run_all_gates.py` 收尾时，若 `git status --porcelain` 非空，**打印显式 WARN 并
  在台账里记 `tree_dirty_at_run: true`**；`generate_evidence.py` 见到该字段直接
  `RuntimeError` 阻断。理由：脏树上跑出的裁决不能代表提交态。
- 完工报告模板加一行强制项：**"台账 verdict 集合与提交后 HEAD 实跑一致（附 run_id）"**，
  无此行不得宣称 12/12。
