### 缺陷 5 · gui-verify-smoke 门禁会自己毒化自己，时绿时红

`tools/spw-gates/gate_gui_verify_smoke.py:75`

```python
ctypes.windll.kernel32.WaitForSingleObject(pi.hProcess, 30000)   # 返回值不检查
```

**30 秒硬顶，返回值不检查，超时也不 TerminateProcess。**

主控完整复跑 9 道门禁时（前一道 H2.unit-tests 跑了 61.4s，机器有负载），
该门禁实测：

```text
[H3.gui-verify-smoke] FAIL
  - non-zero exit code: 259 (stderr: )
  - stdout file size below threshold: 0 bytes < 800 bytes
```

**259 = STILL_ACTIVE**——门禁在 30 秒处读了一个还在跑的进程的退出码，
然后关掉自己的句柄走人，**把 app 留在世上**。
而 cmd.exe 的 `> smoke_out.txt` 重定向句柄还锁在那个文件上，
于是**之后每一次跑都失败**：cmd 无法截断文件 → 共享冲突 →
cmd 退 1 → 输出 0 字节 → 门禁 FAIL。

**主控已完整复现并闭环验证**：

```text
tasklist → "AsWish.exe","26100",Console          ← 孤儿进程
CreateFileW(smoke_out.txt, 独占) → err=32        ← 文件被独占
taskkill /F /PID 26100
独占打开 → FREE
重跑门禁 3/3 → [H3.gui-verify-smoke] PASS RC=0 stdout=819B [PASS]=12
复跑 9 道 → SUMMARY: 9/9 RC=0
```

**结论：下游报的 9/9 不是稳定结论，是"机器空载 + app 在 13 秒内跑完"时的偶然结果。**
一次慢跑污染之后，门禁会持续报 FAIL 直到有人手工杀进程。
作为封版门禁，这条不可接受。

（另：主控单独跑 app 实测 exit=0、14.0s、819B、[PASS]=12，**应用本身是好的**，
问题纯在门禁工程。）

### 缺陷 6 · 单元测试那条证据不可验

证据包里 `H2.unit-tests`：

```json
"stdout_bytes": 164159, "stdout_len": 12000,
"stdout_sha256": "07532672…"
```

`stdout` 字段只存了 **12000 字符**，而 `stdout_bytes` 记 **164159**、
hash 对的是**没存进包里的那 164159 字节**。任何人拿到这个证据包
**都无法验证 348/348**——哈希绑定的内容不在包里。尾部恰好露出
"Tests Passed: 348"，但那不是可验证证据，是给人看的片段。

### 缺陷 7 · 生成证据包的工具不在仓库里

全仓 grep `evidence_self_sha256` / `release_ready` / `spw_cert_` /
`h5_observation_verdict` / `observer_seat_outcomes`，
**命中的只有 `WO/` 文档和既有的 evidence JSON，没有任何 .py / .ps1 / .yml**。
`tools/` 下只有 `gui-verify-fixture/` 和 `spw-gates/`。

也就是说：那张写着 `release_ready=true`、证书号 `spw_cert_0f4bb07029dd1c3a`

开源仓库带一张不可复现的"已认证"收据，比不带更糟。

### 阶段 4 · gui-verify-smoke 门禁去掉自毒化

1. `WaitForSingleObject` 返回值必须检查：`WAIT_TIMEOUT (0x102)` 时
   `TerminateProcess` + 判 FAIL 并报"超时"，**不许读 STILL_ACTIVE**。
2. `finally` 里 `TerminateProcess` + `CloseHandle`，**保证不留孤儿**。
3. 超时上限从 30s 提到 **180s**（实测 app 健康 14s，但门禁排在其他门禁后会变慢，
   30s 顶不住有负载的机器），并把超时值写进 manifest 可配。
4. **反证**：用 Win32 `CreateFileW(dwShareMode=0)` 全程独占 `smoke_out.txt`

   "truncate/write failed" 而非"stdout 0 字节"这类误导性表述。

### 阶段 5 · 证据包可信化

1. `stdout` 字段**必须完整落盘或显式记 `truncated: true`**；
   截断时 hash 改为对**已存部分**计算，或另存全文附件并记附件 sha256。
   **禁止"bytes 记全量、hash 记全量、正文存片段"三不一致。**
2. 生成证据包的工具必须**入库**（`tools/spw-evidence/` 或类似）并在
   `spw-manifest.json` 里登记 command，否则该证据包不得作为放行凭据。
3. 证据包文件名的 commit 后缀必须与真实 HEAD 一致（当前 `5a664c9` 对得上，
   保持）。
