WO-0052 收敛了 **scan** 一条主链，并在收尾时按字面验收会炸开 blast radius，
把其余命令整体挪到了本单。**挪之前先做了一次清点，结果比预期严重：**

母单的判断是"CLI 抄了一份编排"。清点后发现 **24 条剩余命令全部都是自己构造

## 2. P0 缺陷 · GUI 与 CLI 的差异计算结果不同（已隔离复现）

### 2.1 结论

**同一个仓库、同一个 baseline，桌面端和 CLI 算出的差异报告不是一回事。**

桌面端（GUI）**从来没跑过视觉层（L2/L3）比对**，并且每次都把这件事报成降级。

### 2.2 根因

分叉点不在 CLI，在 **Controller 自己**：

- `TAsWishVisualWorkflowService.ComputeDifference` 第一行就是
  `FDifference.RegisterComparator(TAsWishVCLDifferenceComparator.Create);`
  —— 这是**全仓唯一**注册 VCL comparator 的地方（`RegisterComparator` 只有
  DifferenceService 自己、VisualWorkflow 两处引用，无第二处调用）。
  随后它去发现 `runtime-observation.json` / `visual-binding.yaml` /
  `layout-constraints.json` / `expected-styles.json`，一并传下去。
- `TAsWishController.ComputeDifference` **绕过** VisualWorkflow，直调
  `FDifference.ComputeDifference(ProjectPath, ABaselineId, nil, '', '', '', True)`
  —— resolver 传 nil，四个发现参数全传空。
- MainForm 的差异视图走 `FController.ComputeDifference`（:2074 / :2125），
  MainForm 里没有任何直接使用 VisualWorkflow 的路径。

于是 `TAsWishDifferenceService.ComputeDifference` 里
`FComparators.Count = 0`，`LHandledByPlatform` 恒为 False，撞上
`if not LHandledByPlatform and (LBaseline.TreeType = 'view') and AAllowDegraded`
这一支，`IsDegraded := True`，
`DegradedReason := 'Degraded: No platform visual comparator handled baseline; skipped L2/L3 visual comparison.'`

**一个视觉 baseline 在桌面端永远拿不到视觉比对，而 CLI 能。**
这个缺陷与 WO-0052 里"CLI 缺东西"正好互为镜像：那次是 CLI 少一段，
这次是 GUI 少整整一层。

### 2.3 复现（已跑，非纸面推断）

`tests/Test.AsWish.Difference.pas` 新增两条，同一 fixture、同一 view baseline、
两条入口路径各跑一遍：

| 测试 | 走哪条链 | 断言 | 结果 |
|---|---|---|---|
| `Test11_ControllerPath_NeverRegistersTheVCLComparator` | DifferenceService 直调（= Controller 走的） | `IsDegraded = True` 且原因含 `No platform visual comparator handled baseline` | **通过** |
| `Test12_CliPath_RegistersTheVCLComparator` | VisualWorkflow（= CLI 走的） | `IsDegraded = False` | **通过** |

两条同时通过 = 分叉被钉住。任何人想单方面"修好"任何一侧，这两条里必有一条转红。

> 写复现时第一条确实按预测红了（Test12 首轮 assertion 失败：当时 fixture 漏写
> evidence，`Test11` 首轮即通过）。修正 fixture 后两条皆绿，说明失败原因是我
> 的 fixture 而非分析—— Controller 侧恒降级的判断独立成立。

固定版本：`4649899`。全量 298/298。

### 2.4 影响面

- 桌面端用户在差异页看到的永远是"结构差异 + 一条降级说明"，视觉差异
  （布局、观察到的控件、期望样式）**一个都不会出现在 GUI 里**。
- GUI 自动化脚本（MainForm:2085）硬编码断言 `difference count verified in DOM: 21 items`
  —— 这个 21 是"没有视觉项时的结构项数"。修好本单后这个数会变，
  该断言必须同步，否则 GUI dogfood 会假绿。
- CLI 侧行为是对的（或至少是完整的）；**这一处要改的是 Controller，
  不是 CLI**。

intent"变成"生成一整个 changeset"——那不再是换壳，是改产品行为，须老板点头。

  是否该被用户纳入版本控制** → 产品方向问题，待老板裁定，不阻断本单。
- **CLI 输出国际化/编码**（控制台非 UTF-8 时中文文件名乱码）→ 独立问题，
  本单不改输出内容只改调用来源，不在此时引入编码层改动。

### #21 实施中自己造出来又抓住的回归（留档，最重要的一条）

第一版换壳直接调 `EvolveBaseline`，**没有**先读盘上树，结果 `RenderAll`
用空 builder 重渲染，把树页面**清成空白**：

- `function-tree.html`：整段节点 HTML 被换成一行
- `index.html`：覆盖率 `25.0% → 0.0%`、平均置信度 `68% → 0%`
- `problems.html`：`1 功能节点 / 3 模块节点 → 0 / 0`，问题清单整段消失

旧 CLI 渲染范围窄，这些页面它根本不碰，所以是"留旧的"；新版碰了但是用空数据
碰，等于**主动毁内容**，比不碰更坏。

**回归测试** `Test_Accept_DiskFirst_DoesNotEmptyPersistedTree`：

### 阶段三 #6 的差异与裁定

编排等价：两边都是 `PromotePending` → 四棵树逐个
`ApplyNodeStatusTransitions` + 回写，且都跳过空树（CLI 判
`Count > 0`，Controller 判 `Count = 0` 则 Continue）。

差异只在**结果没有出口**。`PromotePendingDecisions` 原本是 `procedure`，
只经 `FStatus` 播报，所以：

- CLI 必须打印 `promoted N` → 需要计数；
- CLI 必须逐树打印 `transitions applied to %s` → 需要知道改写了哪几棵树。

裁定：**Controller 为准**，把这两个数据暴露出来，而不是让 CLI 为了拿它们
再抄一遍遍历。

- `PromotePendingDecisions(out ATreesTouched: TArray<string>): Integer` 新重载；
  原 `procedure` 版收成薄包装（Delphi 允许把函数当语句调用并丢弃结果，
  `AsWish.Commands.pas:106` 那个唯一调用点零改动）。
- `ApplyAllTreeTransitions` 由 `procedure` 改为 `function ... TArray<string>`，
  返回真正回写过的树。它同时被 `ApplyBundleDecisions` 调用，那边同样零改动。

**一个顺手避开的坑**：`PromotePending` 成功后如果 `ApplyAllTreeTransitions`
抛异常，Controller 的 except 会吞掉它（GUI 要能继续）。原来的写法把
`Result := LCount` 放在最后，异常时返回 0——CLI 就会把"其实升成了 2 条"
报成 0。已把赋值提到遍历之前。

**仍未解决（记录，不冒充已修）**：吞掉的异常在 CLI 里**完全不可见**——
静默 bundle 压掉 `FStatus.LogError`，于是 promote 失败时 CLI 会打印
`promoted 0` + `done` 并 exit 0，而旧版是未处理异常 + exit 1。
一致的修法是照 `ScanFailed` 的先例加一个 `PromoteFailed` 属性，
留给后续条目，不塞进本条。

### 阶段三 #7 的差异与裁定

两边都是"找 bundle → 记一条正式决策 → accept/reject → 四棵树跑状态机
→ 渲染"，编排同源。差异七处，逐条实测：

| # | 行为点 | CLI 旧实现 | Controller | 裁定 |
|---|---|---|---|---|
| 1 | 空锚定 bundle | 照记一条 **0 节点**决策，打印 `(0 nodes, decision dec-0001)` + `done`，**exit 0** | `LogError` + 不记决策 | **Controller 为准**。0 节点决策是"看着像决策、永远无法被执行"的台账垃圾，旧版还上报成功 |
| 2 | bundle id 匹配 | `SameText`（大小写不敏感） | `LB.Id <> ABundleId` 精确 | **Controller 为准**。GUI 的 JS Bridge 传的是页面上的原值，从不需要宽容；id 是系统生成的，精确匹配也是常规做法。**损失已记录**：CLI 用户手打 `BND-ALPHA` 旧版能中、新版报 not found（exit 1）。若要宽容，改 core 里那一行为 `not SameText(LB.Id, ABundleId)` 即可，但那会动 Controller 的匹配语义，不在换壳范围内 |
| 3 | 决策文案三串 | `accept: <title>` / `CLI accept for bundle <id>` / `Applied to N nodes via CLI` | `Accept bundle: <title>` / `bundle-accept (bundle: <id>)` / `Recorded via WebView2 JS Bridge (batch review)` | **分开裁**：title 与 decision 两串本身与来源无关，取 Controller；**rationale（来源串）不能跟着赢**，见下 |
| 4 | 渲染 | 不渲染，页面停留在上次 scan 的状态 | `ApplyAllTreeTransitions` → `ReloadInMemoryTrees` → `RenderAll` | **Controller 为准**。实测：换壳后 `function-tree.html` 里 confirmed 标记 2→6、accepted 1→3，旧版把"已确认"的页面留成"未审阅" |
| 5 | 结果出口 | JSON `promoted` 硬编码 `1`；逐树行自己再遍历四棵树 | `procedure`，只走状态栏 | 加出参重载 + `TBundleApplyResult` |
| 6 | action 词表 | `accept` / `reject` | `bundle-accept` / `bundle-reject` | CLI 入口映射，不动 Controller |
| 7 | 守卫分工 | 四条各自 `Halt(1)` | 四条各自 `LogError` | 入口守卫（无 `.AsWish`、action 非法、`bundles.yaml` 缺失）留 CLI——退出码是壳的职责；后两条（bundle 找不到、空节点）由 Controller 经 `AResult.Failure` 回报短码，CLI 自己拼文案 |

**#3 为什么不能整条赢。** `rationale` 字段落的是"这条决策是谁记的"。
Controller 的默认值写死 `WebView2 JS Bridge`——GUI 调用时是真的，
CLI 调用时就是**假的**。若整条按 Controller 收敛，老板在 decisions 页会看到
一条由 `AsWish.CLI bundle apply` 产生、却声称经浏览器桥记录的正式决策。
审计台账里留假记录，比文案不统一严重得多。所以给 core 加了
`AOriginNote` 参数（默认值即 GUI 原串，GUI 调用点零改动），CLI 传
`Recorded via AsWish.CLI bundle apply`。

实测对账（旧版 exe vs 新版 exe，同一 fixture 路径 `/d/Temp/bndrun`，
`bnd-alpha` 锚定 `func-bndfix` + `mod-bndfix`）：

- **stdout 逐字节相同**：人声 happy path、`--json` happy path、reject 三条；
  退出码一致（均 0）。
- **守卫四条逐一相同**：无 `.AsWish` / action 非法 / `bundles.yaml` 缺失 /
  bundle 找不到，文案与 exit 1 全一致。
- **`decisions/requirement-decisions.yaml` 只差三个散文字段**
  （`title` / `decision` / `rationale`），
  `id`/`type`/`target_nodes`/`status`/`decided_by`/时间戳全部相同。
- **四棵树与扫描产物仅时间戳不同**（归一后 diff 为 0）。
- **HTML 有意不同**（裁定 4 的后果）：新版多生成 `bundles.html`、
  `decisions.html`、`visual-preview.html` 三个页面，且既有页面刷新为决策后
  状态。旧 CLI 的 bundle apply 根本不渲染，这三页要么缺、要么停在 scan 时。

### 阶段三 #5 `health` 的差异与裁定

**先看清一件事：`health` 与 `ExportOptimizationPrompt` 根本不是同一个操作。**
名字里都带"健康度"，容易让人以为该复用：

| 维度 | `ExportOptimizationPrompt` | `health` |
|---|---|---|
| 度量对象 | **活着的 builder**（当前会话内存） | **落盘的四棵树 + issues** |
| 产物 | 生成一个优化提示词**文件** | 只往 stdout 打印，**不写任何文件** |
| 适用面 | GUI 有会话可量 | CLI 是一次性进程，**没有 builder** |

所以裁定不是"让 `health` 改成调 `ExportOptimizationPrompt`"，而是
**给 Controller 补一个按磁盘度量的能力** `ComputeHealthMetricsFromDisk`，
把 CLI 里那段"自己读四个树 + 自己读 issues + 自己调
`TAsWishRenderService.ComputeHealthMetrics`"的编排搬走。两者并存，不互相改造。

**CLI 旧实现的差异一处（已证伪为无行为）**：旧版在每次读之前都做
`TFile.Exists` 检查，缺失就短路退出。实测**这是空动作**——
`ReadTreeFile`/`ReadIssuesFile` 对缺失文件返回的是**空列表而非 nil**，
而 `ComputeHealthMetrics` 对 nil 与空列表的处理相同。把 data-tree 和
issues 两个文件都删掉后，旧版与新版输出完全一致、exit code 同为 0。
新实现里**不再写这些检查**：读起来像谨慎，实际什么都不改变，只会让
"缺失文件"这条路径失去被测试覆盖的机会。

实测对账（旧版 exe vs 新版 exe，同一 fixture 路径）：

- **五条路径逐字节相同**：人声、`--json`、无 `.AsWish` 守卫（文案 + exit 1）、
  data-tree 与 issues 双缺失（exit 0）、做完一个决策后的更丰富状态。
- **`health` 不写盘**：跑前跑后整个 `.AsWish` 目录 `FILE SET UNCHANGED`。

新增 `Test_HealthMetricsFromDisk_MatchesLiveBuilder`，把同一份数据下的
"builder 度量"与"磁盘度量"七个字段逐一钉相等（这正是本单要关的分叉类），
并加了"夹具不能全零"与"写入的 issue 必须被数到"两个防自嗨断言。
**看过转红**：把磁盘路径的 issues 文件名改成一个不存在的文件，306→1 红
（红在 `decisionBacklog`，比我断言的 `highRiskOpen` 更靠前——说明该字段
同样从 issues 推导，覆盖比预期更宽）。恢复后 307/307，0 泄漏。

### 阶段三 #4 `render` 的差异与裁定

**先纠一个我自己的预判。** 我原以为这是"CLI 拿 4 棵树、Controller 拿 builder"
的大分叉。实测后发现**根本不是**：GUI 侧与 CLI 侧语义对应的是
`RefreshFromYaml`（"从 YAML 重画页面"），不是 `RenderAll`
（"从内存重画页面"）——而 `RefreshFromYaml` 本来就是**同一套读盘编排**。
所以真正的差异比我预估的小得多，四条，逐条实测：

| # | 行为点 | CLI 旧实现 | Controller | 裁定 |
|---|---|---|---|---|
| 1 | 仪表盘文件数 | **节点总数**（func+module+view 三棵，`1+3+0`）当 `files` 印出来 | `FScanService.TotalFiles`——但一次性 CLI 从没 scan 过，**实际是 0** | **两边都错**，补能力见下 |
| 2 | 决策页守卫 | 查 `.AsWish/decisions.yaml` | 不渲染决策页（`RefreshFromYaml` 本来就不画） | **删**，见下"死分支" |
| 3 | 输出口 | `[render] done -> <path>\html\` | 只走状态栏 | 加出参 `TRenderResult` |
| 4 | data-tree 存在性 | `TFile.Exists` 后读，否则 `nil` | 同一套 `TFile.Exists` 判断 | **等价**，无需裁定 |

**#1 是这里唯一真正的洞。** 那个数印在仪表盘上，标签写的就是
`Scan Report (N files)`。CLI 用节点总数顶替（本 fixture 实测印 `10 files`，
真实扫描到 6 个），而 Controller 那条路在无扫描进程里会印 `0`。
两者都不对。裁法：**给 Controller 补度量**——`RenderFromDisk` 在
`FScanService.TotalFiles = 0` 时先跑一次 `ScanDirectory`。理由与
`ExportPrompt` 完全相同（Controller.pas 注释已留）：扫描是内存态、确定性的，
免费；只在"这个进程还没扫过"时补，所以 GUI 每次点刷新**不会**多扫一遍。
换壳后同一 fixture 印 `6 files`，与 `scan` 自己报的数一致。

**#2 是一段死代码。** 全仓库对 `.AsWish/decisions.yaml` 的引用只有两处：
CLI 的这次读，和 `Snapshot.pas` 收的 `decisions/decisions.yaml`（另一个路径）。
**没有任何命令写过 `.AsWish/decisions.yaml`**——决策服务读写的是
`.AsWish/decisions/requirement-decisions.yaml`。也就是说 `render` 的决策页
分支**一次都没有真正执行过**。我实测验证了这一点：手工造一个
`.AsWish/decisions.yaml` 后该分支确实会渲染出 `decisions.html`（可达），
但删掉它再跑就回到"不渲染"（常态）。已删。

**页面集合实测（这部分最值得记）。** 删掉 `decisions.html` /
`visual-preview.html` / `scan-report.html` / `evidence.html` 后各跑一次
`render`：改前改后**完全一致**——`problems.html` 与
`bundles.html` 会被重画，其余四页都不碰。所以换壳没有偷改页面集合，
`decisions.html` 的"陈旧"是 GUI 刷新路径本来的行为，不是本轮引入。

**⚑ 附带发现（未修，另行开工）：`TotalFiles` 把被忽略的目录也算成一个文件。**
`TAsWishScanService.TotalFiles := FResults.Count`，而 `FResults` 里
`fcIgnored` 条目是**目录**（`.AsWish` 本身）。实测：空项目
`scan` 报 `total_files: 1`，而 `documents/code/ui/config/ai_rules` 全 0、
`ignored: 1`；本 fixture 真实 5 个源文件，`scan` 报 6。
**改前改后一致**（我用 `9fdf41a` 版 exe 复现了同样的 1），所以不是本轮引入。
它让 `render` 与 `scan` 互相自洽（都报 6），但都比真实值多 1。
修它要动 `scan` / `health` / `prompts` / 差异链的输出，超出本单范围。

实测对账（`9fdf41a` 版 exe vs 新版 exe，**同一路径**顺序跑，
项目名取自目录名所以不能分两个目录比）：

- **stdout 逐字节相同**（含 `exit=0`）——happy path、缺 data-tree+issues+view-tree、
  全树缺失、`--json`（旧版 render 本来就不认 `--json`，新版同样不认）。
- **整个 `.AsWish` 目录树逐字节相同，只差 1 处**：
  仪表盘 `(10 files)` → `(6 files)`。其余全部是生成时间戳。
- **无 `.AsWish` 守卫**：文案与 exit 1 一致。

新增 2 个测试，**都看过转红**：

1. `Test_RenderFromDisk_FileCountIsScannedNotNodeTotal`——按 CLI 的姿势

   而不是节点总数"，并用夹具自身保证两者不相等（本 fixture 3 vs 5）。

2. `Test_RefreshFromYaml_KeepsItsStatusWording`——`RefreshFromYaml` 现在

   → 红，报错文案与预测一致。

### 阶段三 #23 `visual confirm` 的差异与裁定

四个差异，其中一个是 #21 那类"一次性进程里 builder 是空的"缺陷的**同型复发**：

| # | 行为点 | CLI 旧实现 | Controller | 裁定 |
|---|---|---|---|---|
| 1 | view 节点从哪来 | `LoadPersistedTrees` 把四棵树灌进 builder 后，从 builder 取 view id | `FTreeBuilder.ViewNodes`，只认**内存里**的 builder | **CLI 对、Controller 缺能力**，补法见下 |
| 2 | 默认 rationale 文案 | `'CLI visual confirm.'` | 硬编码 `'Visual preview confirmed via UI / Decision.'` | **两者都留不得**，加 `ADefaultOriginNote` |
| 3 | 渲染范围 | 只重画 confirm 那一条链 | `ConfirmVisualBaseline` → `RenderAll`，另外多出 `decisions.html` + `visual-preview.html` | Controller 赢，**接受** |
| 4 | 输出口 | 打 `created Accepted Visual Baseline ... (decision: ...)` | 单参版只返回 baselineId，decisionId 只走状态栏 | 加出参 `TVisualConfirmResult` |

**#1 是 #21 的同一类洞。** `ConfirmVisualBaseline` 从头到尾读
`FTreeBuilder.ViewNodes`：既用它做"没有 view 节点就别确认"的前置守卫，
又用它收集受影响的 view id。一次性 CLI 进程里这个 builder 是空的，
所以旧 CLI 必须自己先 `LoadPersistedTrees`——这正是 #21 里 evolve
踩过的坑（当时 CLI 没加载，报"没有 view 节点"）。
换壳时**没有**把 `LoadPersistedTrees` 一起搬进 Controller，而是留在 CLI
调用侧，并用**反向变异**证明它不是可有可无的仪式：从新 CLI 里删掉那一行后，
在一个 `view-tree.yaml` 有 3 个真实 view 节点的夹具上跑，
命令报 `[visual confirm] error: no View Spec nodes to confirm` 且 exit 1。
所以那一行是本命令的功能组成部分，不是冗余代码——这条结论是测出来的，
不是读代码读出来的（BUG-B 的教训：看着像多余的加载，删了就红）。

**#2 是审计台账里的假记录。** 决策服务会把 rationale 原样写进
`decisions/requirement-decisions.yaml`，将来谁回看这条 JSONB 字段，
看到的是 `Visual preview confirmed via UI / Decision.`——而做这个决定的
是命令行，不是 UI。这和 #7 `bundle apply` 的 `AOriginNote` 是**同一个病**
（那次的假记录写的是 `Recorded via WebView2 JS Bridge`）。
裁法一致：不写死来源串，由调用方传。CLI 现在传
`'Recorded via AsWish.CLI visual confirm'`，GUI 单参包装仍传原来那句
（GUI 那句是真的）。实测：同一夹具，改前 rationale 是
`"CLI visual confirm."`，改后是 `"Recorded via AsWish.CLI visual confirm"`。

**#3 是"Controller 赢"的代价，这里明确记账。** 旧 CLI 只重画 confirm 那
条链涉及的两页，换壳后每次 confirm 会**多出** `html/decisions.html` 和
