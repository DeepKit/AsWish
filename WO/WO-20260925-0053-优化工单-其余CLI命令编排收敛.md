WO-0052 收敛了 **scan** 一条主链，并在收尾时按字面验收会炸开 blast radius，

## 2. P0 缺陷 · GUI 与 CLI 的差异计算结果不同（已隔离复现）

### 2.1 结论

**同一个仓库、同一个 baseline，桌面端和 CLI 算出的差异报告不是一回事。**

桌面端（GUI）**从来没跑过视觉层（L2/L3）比对**，并且每次都把这件事报成降级。

### 2.2 根因

分叉点不在 CLI，在 **Controller 自己**：

- `TAsWishVisualWorkflowService.ComputeDifference` 第一行就是
  `FDifference.RegisterComparator(TAsWishVCLDifferenceComparator.Create);`
  —— 这是**全仓唯一**注册 VCL comparator 的地方（`RegisterComparator` 只有
  DifferenceService 自己、VisualWorkflow 两处引用，无第二处调用）。
  随后它去发现 `runtime-observation.json` / `visual-binding.yaml` /
  `layout-constraints.json` / `expected-styles.json`，一并传下去。
- `TAsWishController.ComputeDifference` **绕过** VisualWorkflow，直调
  `FDifference.ComputeDifference(ProjectPath, ABaselineId, nil, '', '', '', True)`
  —— resolver 传 nil，四个发现参数全传空。
- MainForm 的差异视图走 `FController.ComputeDifference`（:2074 / :2125），
  MainForm 里没有任何直接使用 VisualWorkflow 的路径。

于是 `TAsWishDifferenceService.ComputeDifference` 里
`FComparators.Count = 0`，`LHandledByPlatform` 恒为 False，撞上
`if not LHandledByPlatform and (LBaseline.TreeType = 'view') and AAllowDegraded`
这一支，`IsDegraded := True`，
`DegradedReason := 'Degraded: No platform visual comparator handled baseline; skipped L2/L3 visual comparison.'`

**一个视觉 baseline 在桌面端永远拿不到视觉比对，而 CLI 能。**
这个缺陷与 WO-0052 里"CLI 缺东西"正好互为镜像：那次是 CLI 少一段，
这次是 GUI 少整整一层。

### 2.3 复现（已跑，非纸面推断）

`tests/Test.AsWish.Difference.pas` 新增两条，同一 fixture、同一 view baseline、
两条入口路径各跑一遍：

| 测试 | 走哪条链 | 断言 | 结果 |
|---|---|---|---|
| `Test11_ControllerPath_NeverRegistersTheVCLComparator` | DifferenceService 直调（= Controller 走的） | `IsDegraded = True` 且原因含 `No platform visual comparator handled baseline` | **通过** |
| `Test12_CliPath_RegistersTheVCLComparator` | VisualWorkflow（= CLI 走的） | `IsDegraded = False` | **通过** |

两条同时通过 = 分叉被钉住。任何人想单方面"修好"任何一侧，这两条里必有一条转红。

> 写复现时第一条确实按预测红了（Test12 首轮 assertion 失败：当时 fixture 漏写
> evidence，`Test11` 首轮即通过）。修正 fixture 后两条皆绿，说明失败原因是我
> 的 fixture 而非分析—— Controller 侧恒降级的判断独立成立。

固定版本：`4649899`。全量 298/298。

### 2.4 影响面

- 桌面端用户在差异页看到的永远是"结构差异 + 一条降级说明"，视觉差异
  （布局、观察到的控件、期望样式）**一个都不会出现在 GUI 里**。
- GUI 自动化脚本（MainForm:2085）硬编码断言 `difference count verified in DOM: 21 items`
  —— 这个 21 是"没有视觉项时的结构项数"。修好本单后这个数会变，
  该断言必须同步，否则 GUI dogfood 会假绿。
- CLI 侧行为是对的（或至少是完整的）；**这一处要改的是 Controller，
  不是 CLI**。

### 阶段一附带发现（未修，另行开工）

**GUI dogfood 的"DOM 断言"是硬编码数字。** `MainForm.pas:2085` 打印
`[DOM-ASSERT] ... verified in DOM: 21 items`，但 `21` 是**写死在日志字符串里**的，
不是从 DOM 读出来比对的。真正发生的唯一检查是 `WaitForBrowserReady('21', ...)`
——只证明 DOM 文本里**某处出现过字串 `21`**，不证明差异数是 21。

差异数一旦变化（比如将来给 dogfood 项目加了 `runtime-observation.json`，
视觉比对就会多出条目），日志仍会印 21，而 `WaitForBrowserReady` 会一直等到超时
后从文件读 HTML 兜底——**结果是变红还是变绿取决于兜底路径，不可预期**。

这不是本轮引入的，且本单修复**不改变**它：dogfood 的 `B-0001` 是
`Tree: function` 基线，项目里没有 `runtime-observation.json`，
`TAsWishVCLDifferenceComparator.CanHandle` 对 function 基线且无观察 JSON 时
返回 False，`LHandledByPlatform` 为 False，而 `TreeType <> 'view'` 又让降级分支
不触发——**改前改后项集合与降级状态完全一致**，21 仍然成立。

### 阶段二 #14/#15 的两个实测坑（留档）

1. **委托模型（K3）把 `LCS.Id` 偷换成了 `AChangeSetId`。**
   它给 CLI 的 diff 里 `WriteJsonKV('change_set_id', LCS.Id)` 变成了
   `AChangeSetId`。这不是等价改写：`LoadChangeSet` 是按**文件名别名**找到文件、
   再解析出文件里声明的 `change_set_id`，两者可以不同
   （`AChangeSetId` 为空时还会落到 `change-set.yaml`）。
   **抓它的不是审 diff 的眼睛**，是我为此专门造了一个
   `cs-alias-01` / `cs-internal-777` 的夹具：旧版 exe 与新 exe 各跑一次，
   输出必须逐字节相同。若按 K3 的版本合入，新 exe 会打印 `cs-alias-01`。
   配套回归测试 `Test_ChangeSet_DecisionResult_CarriesParsedIds`
   **已亲眼看过转红**（把 `LCS.Id` 换回 `AChangeSetId` 后报
   `Expected [cs-internal-777] but got [cs-alias]`，与预测一致），再恢复变绿。

2. **Controller 走 `FStatus` 播报，会污染 CLI 的输出流。**
   `RejectChangeSet` 成功后调 `FStatus.Info('AsWish.ChangeSet', ...)`，
   而 `TConsoleStatusManager.Info` 在非静默模式下直接 `Writeln`——
   照搬会把一行 `[AsWish.ChangeSet] Rejected ...` 插进出流，
   `--json` 模式下更是直接把 JSON 撑坏。
   `scan` 反过来**依赖**这行回声（干跑显示 `[AsWish] Opening project:`
   等 6 行状态行都在 stdout 里），所以不能全局关。
   修法：`TControllerBundle.Create(ASilentStatus: Boolean = False)`，
   只有输出格式自己的命令（reject/clarify）传 True。
   `TConsoleStatusManager.Create(True)` 只压回声、不丢 entry，已有测试钉住。

| 1 | CLI 无幂等守卫，Controller 有 `FindAcceptedByChangeSet` | **Controller 为准**——这是本单要修的 P0 分叉，不是可保留的入口层差异 |
| 2 | CLI 自己从盘上读四棵树；Controller 只作用于内存 live builder | 新增 `ALoadTreesFromDisk` **入口层参数**，不塞进编排 |
| 3 | CLI 基线无父基线血缘；Controller 取 `ListBaselines[0]` 作 parent | **Controller 为准**——丢血缘是 CLI 的缺陷 |
| 4 | CLI 不调 `RenderAll`；Controller 调 | **Controller 为准**——CLI 因此留下过期 HTML（见下） |
| 5 | CLI 跑一遍 lenient 校验然后把 report 丢掉 | **删除**——死工，不属于任何一边 |

**差异 2 为什么必须是参数而不是默认行为。** `BuildFromScan` 是从源码
重建树，不是读盘上的 YAML；`RunScan` 更会在第 5 步无条件
`WriteTreeFile` 把重建结果写回盘。所以"让 CLI 先 scan 再 accept"是错的：
扫描版树会先覆盖权威树，随后读盘读回来的是扫描版，等于静默毁掉
Canonical Spec。正确顺序只能是不扫、直接读盘——这正是参数为 False 时
GUI 路径、为 True 时 CLI 路径共用同一个 `AcceptChangeSetCore` 的原因。

**差异 4 的代价（留档，不是新缺陷的掩饰）。** CLI 现在会重渲染 HTML，
好处是被 accept 改动的树页面终于反映新状态（旧版 `function-tree.html`
里还是 accept 前的旧 summary，决策工具栏也还在）；代价是
`scan-report.html` 会被用**空的扫描状态**重渲染成 `0 文件 / unknown`，
而旧版从不碰这个文件、留下的是上一次真扫描的结果。根因是一次性 CLI
进程没有扫描态，`RenderAll` 却要拿它渲染扫描报告。
这里**没有**顺手修：修法要么给 Controller 加一个"只补扫描态不写盘"的新
方法（超出本条的边界），要么改 `RenderAll` 的职责，两者都不是换壳该干的。
记为阶段三的后续候选，不冒充本轮已解决。

**本轮委托结论。** 我按"难活给 K3"给 `t4-changeset-accept-disk-first` 下了
带两份 verbatim 代码片段的简报，同时要求"用真实行号和真实上下文行"——
K3 拒稿并逐条点名它缺哪些区域（类声明私有段、`Reject/Clarify` 邻近实现、
`.dpr` 全文、uses 子句占用）。**这是我的简报自相矛盾，不是它的错**：
片段凑不出真实行号，硬让它编就等于让它造假行号。已由我自己实现，
并按同一套机械门验证（见上表）。教训记入优化工单候选项。
