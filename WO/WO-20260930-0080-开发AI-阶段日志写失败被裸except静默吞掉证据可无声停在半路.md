## 任务（单事项）

**已核实的代码事实**：`src/app/AsWish.MainForm.pas:1798-1812`，

```pascal
procedure TAsWishMainForm.LogProgress(const ADetail: string);
var
  LLine: string;
begin
  if FProgressFile = '' then Exit;
  LLine := Format('%s | pid=%d | %s', [...]);
  try
    TFile.AppendAllText(FProgressFile, LLine + sLineBreak, TEncoding.UTF8);
  except
  end;   // ← 任何写入失败都被吞掉，无计数、无告警、无痕迹
end;
```

`gui-verify-progress.txt` 是本仓 gui-verify 的**唯一过程证据**
（WO-0075 的全部价值都押在它身上）。`TFile.AppendAllText` 每次调用都要
重新打开文件，任何一次失败都会让这一段之后的日志**直接消失**，
而文件本身看起来仍然是一份格式完好、开头正常的时间戳序列——
读证据的人无法区分"跑到这就没了"和"后面本来就没内容"。

**可能的触发条件（未隔离复现，故标 suspected）**：
并发起第二份 `--gui-verify`（同目录同文件）、
`dogfood_gui` 所在卷写满、目录权限被收紧、杀软占用。
主控本轮单跑未触发，因此不给它高于 P3 的优先级。

**默认路线（按此实现，须说明理由）**：

1. **失败必须响一次，但不许把验证跑挂**。加一个失败计数，
   在**第一次**失败时输出一条
   `[PROGRESS-WARN] progress log write failed: <异常消息>`，
   走既有 `AddCaptureWarning`（它已在 0079 里接入进度文件与控制台告警），
   后续连续失败**不要**每行都刷（避免把日志本身刷爆）。
   理由：0075 的既有设计是"日志不许杀死验证"，这条要保留；
   但要让它从"哑"变"响"，否则等于没改。
2. **成功写入后把失败计数清零**：一次失败不构成永久残疾，
   恢复后应能继续正常落盘，并在计数归零时补一条恢复提示即可（可为空实现）。
3. **不要**为此把进度文件改成进程内一次性保持句柄（会改变
   WO-0075 已确认的"硬杀不丢行"语义——正是逐次 append 才保证硬杀也能落盘）。
4. **不要**改动 `LogProgress` 的行格式与 `LogStepProgress` 的
   `step=N | state=enter/exit` 结构（WO-0075 已确认语义，0079 判词第三条）。
