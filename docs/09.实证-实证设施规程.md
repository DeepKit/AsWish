## 1. 核心立场

> **AsWish 不是一台用来"证明理论"的机器，而是一个让理论衍生的主张可以被操作化、暴露于证据（包括反证）的设施。**

---

## 2. 反循环规则（硬性纪律）

必须避免：

```text
理论定义规则
→ 软件按规则实现
→ 软件满足规则
→ 因此理论被证明
```

这是**实现一致性**，不是实证验证。真正的实证回路必须允许：

```text
理论主张 → 操作化 → 真实案例 → 观察 → 意外结果 / 反例 → 质疑 → 修正 → 复测
```

**与预期相反的案例是有价值的证据，不得被埋掉。**

---

## 3. 什么不算实证证据

以下**单独**都不足以构成理论证据：

```text
架构看起来与理论一致
代码实现了该规则
界面上有要求的按钮
测试是绿的
开发者报告行为正确
人大概能看懂界面
产品团队同意该假设
```

这些可能是工程证据、设计证据或干系人判断，但**不是理论证据**。

一条理论相关的证据主张必须能指出：

```text
案例 / 产物或事件 / 可见对象 / 人或系统动作 / 记录的来源 / 解释
```

---

## 4. 双闸门仍是双闸门（裁定）

现有工程门禁保持不变：

```text
Engineering Green + Dogfood Green
```

**First Closed Loop 阶段不设第三道闸门。** 实证维度作为 Dogfood Green 内部的**记录项**（案例记录：什么有效、什么失败、不确定性出现在哪、可见对象在哪失效、差异在哪变模糊），不作为独立放行条件。

待进入真实案例积累阶段后，再评估是否引入独立的实证就绪判定。

---

## 5. 观察与解释必须分离

```text
观察：人拒绝了候选 #2，并写下真正的问题不是这个
解释：人拒绝了 AI 的问题框架
```

后者需要证据表明"人的原话否定的是框架本身"，否则只是解释。**证据层只记录，不偷偷解释。**

---

## 6. 证据质量等级（E0–E5）

| 等级 | 含义 |
|---|---|
| E0 | 有人陈述一个结果 |
| E1 | 被主张的对象确实落盘存在 |
| E2 | 产物链接到来源 / 动作 / 结果（可追溯） |
| E3 | 相关产物可被直接检视（可观察） |
| E4 | 证据路径可重放或重建（可复现） |
| E5 | 记录能支撑一条明确主张，并指出可能的反例（可用于理论） |

**First Closed Loop 目标：关键判断链达到 E3–E4。** E5 属长期目标。

---

## 7. 实证设施成熟度

| 级别 | 名称 | 含义 |
|---|---|---|
| L1 | 可追溯 | 产物与决策可追溯 |
| L2 | 可观察 | 判断对象有稳定的可见表现 |
| L3 | 可复现 | 同一案例可回访、证据可重建 |
| L4 | 可挑战 | 保留反例，支持理论修正 |

First Closed Loop 至少需要 **L1–L2**；**L3 是主要目标**；L4 是长期研究方向。

---

## 8. 理论主张 → 工程机制映射（指针）

产品仓库**只维护"哪个工程机制实现了哪个主张 ID"的映射**；主张本身的状态归理论母库（见 §9）。

| 主张 ID | 主张 | 工程机制 | 可见对象 | 可能的反例 |
|---|---|---|---|---|
| OJP-001 | 人类判断必须针对可见对象，而非系统内部状态 | 稳定渲染 + 追溯链（VC-01～06） | Review / Tree / SVG / Diff 视图 | 某个判断在目标对象仅内部可见时被接受 |
| BND-001 | Human Decision ≠ AI Understanding | Decision 独立落盘，与 ChangeSet 分离 | Decision 记录 + 目标可见对象 | 理解正确即自动产生 Accept |
| DS-001 | 探索与承诺分处两个界面 | Conversation / Decision 双界面 | 当前所处界面 + 事件轨迹 | 一句对话未经理式决策就改动了 Canonical Spec |
| DIF-001 | Difference ≠ Error | Difference 输出支持四类判断 | Difference 视图 | 所有差异都被自动归类为失败 |

---

## 9. 理论主张状态的归属（裁定）

```text
产品仓库：只留 claim → 工程机制 的映射指针（即本文件 §8）
理论母库 D:\_Progs\一元论：主张的状态（Proposed / Operationalized / Observed
                          / Supported / Challenged / Revised / Retested）
```

产品仓库**不得出现第二套主张状态**，以免与母库产生分叉。`Supported` 永远不等于 `Proven`。

---

## 10. 反例处理纪律

当案例与主张冲突时：

```text
1 保留原始证据
2 确认该案例确实满足操作化条件
3 排查实现缺陷
4 排查可见对象缺失或错误
5 排查解释歧义
6 再判断主张本身是否需要修正
7 记录推理过程
8 条件允许则复测
```

不得因为不便而埋掉反例，也不得把单次失败直接归因于理论——需先区分：理论问题 / 工程缺陷 / UX 与可见性缺陷 / 证据不足 / 人与情境差异。

---

## 11. First Closed Loop 的实证要求（裁定）

**第二轮 Revision 是硬要求：**

```text
v1 → Difference → Human Judgment → Revision → v2 → Difference v2 → 复验
```

只完成第一轮（Difference → 记录判断）**不构成** First Closed Loop 完成，仅可作为"若时间或资源不足时的阶段性成果"对待，且必须明确标注。

案例允许产生以下任一结果，按实际记录，不得为让理论好看而优化：

```text
No important difference / Acceptable difference /
Unacceptable difference / Unresolved
```

---

## 12. 最小新增原则

不为此建立研究官僚体系，不新建：

```text
研究数据库
新的 proposal 生命周期
新的决策系统
新的证据库
```

优先复用现有产物、快照、证据、决策、差异与 Dogfood 案例；只有当现有结构确实无法承载所需信息时，才最小新增。

---

## 13. 非目标

本规程不定义：科学发表方法论、统计推断要求、用户研究伦理程序、研究数据库、替代性决策或证据系统。
