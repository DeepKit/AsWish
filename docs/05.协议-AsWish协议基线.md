## AsWish SPEC

> Status: v1.2-draft  
> Scope: protocol and workflow baseline for `.AsWish/` workspaces

## 1. Objective

AsWish defines a project-local specification workspace that humans and AI agents can both read. The workspace must make generated requirements traceable, reviewable, fallible, and usable as input to downstream coding agents.

AsWish is not an agent orchestrator, an IDE, a coding agent, or a generic spec editor. It is Level 3 (engineering implementation) of the unified system (`Difference Monism → As We Wish → As I Wish → AsWish → .AsWish`), acting as the open engineering layer between **Human ↔ AI Coding Agent ↔ Software Implementation**.

> **Capability boundary (normative):** AsWish forms the confirmed representation **before** development, and in the First Closed Loop holds implementation evidence against that representation **afterward**. The post-development **Evidence / Difference / Human Judgment → Revision / Evolution → Re-verification** loop is **already shipped as a scoped capability（④–⑤ FACT，As of 2026-09-10）**. Current capability status follows [`17.产品-开发随心的六脉神剑与用户价值.md`](17.产品-开发随心的六脉神剑与用户价值.md) (**①–⑤ FACT, ⑥ VISION**).
>
> **Scope（必须与上句同时声明）**：已交付的该闭环**不包含** Pixel Diff / 全像素视觉比较，不覆盖全平台、全控件、全样式语义，且**不自动归因、不自动判定 Difference 是否为 Error、不自动接受、不自动修复**。**Difference ≠ Error**；AsWish 不是自动纠错系统。**FACT ≠ Universal Coverage。**

Product identity is defined in [`01.产品-AsWish产品身份与愿景蓝图.md`](01.产品-AsWish产品身份与愿景蓝图.md); documentation governance in [`13.治理-文档治理与工程纪律.md`](13.治理-文档治理与工程纪律.md); this document is the protocol baseline only.

## 2. Workspace

A AsWish-enabled project contains a `.AsWish/` directory.

```text
.AsWish/
  project-spec.yaml
  scan-report.yaml
  trees/
    function-tree.yaml
    module-tree.yaml
    view-tree.yaml
    data-tree.yaml
  bundles/
    semantic-bundles.yaml
  relations/
    requirement-relations.yaml
  evidence/
    source-evidence.yaml
  issues/
    doc-issues.yaml
  decisions/
    requirement-decisions.yaml
    review-decisions.yaml
  llm/
    candidate-intent.yaml
    change-set.yaml
  snapshots/
    <name>/snapshot.yaml        (accepted baseline snapshots, WO-20260830-0027E)
  agents/
    agent-results.yaml
  html/                         (generated review surface — derived, not fact source)
  prompts/                      (generated context packs — derived, not fact source)
```

`project-spec.yaml` is the index. YAML files are the fact source. HTML is a generated review surface and must not be treated as the source of truth.

## 3. Four Projections

AsWish represents a requirement through four weakly coupled projections.

| Projection | Question | Main risk it controls |
|---|---|---|
| function-tree | What should the system do? | missing or ambiguous behavior |
| module-tree | Where does the behavior live? | implementation ownership drift |
| view-tree | What does the user see or operate? | UI and workflow mismatch |
| data-tree | What data exists and how does it change? | schema, migration, persistence, and state drift |

The first three trees remain readable on their own. `data-tree` adds the data model projection and should not be replaced by a generic risk tree. Risk is a field and derived view, not the fourth tree.

## 4. Node State

New protocol work uses orthogonal states（与代码 `src/models/AsWish.Models.pas` 的 `TGenStatus` / `TReviewStatus` 一致）：

```yaml
gen_status: draft | generated | confirmed | skipped
review_status: unreviewed | accepted | rejected | deferred
```

Transitions（与代码 `TSpecEnums.CanTransitionGen / CanTransitionReview` 一致，代码为实现权威）：

```text
gen:    draft → generated | skipped;  generated → confirmed | skipped;  confirmed / skipped 为终态
review: unreviewed → accepted | rejected | deferred;  deferred → accepted | rejected;  accepted / rejected 为终态
```

Legacy `status` remains readable:

```yaml
status: candidate | confirmed | uncertain | rejected | superseded
```

Readers should map legacy status conservatively:

| legacy status | gen_status | review_status |
|---|---|---|
| candidate | generated | unreviewed |
| uncertain | generated | unreviewed |
| confirmed | generated | accepted |
| rejected | generated | rejected |
| superseded | generated | rejected |

Execution state does not belong to CTF/AsWish. Task execution state belongs to orchestration or ODD layers.

> **预留语义注记（原 C-5，已裁定）**：`failed`（生成失败）与 `locked`（INV-7：锁定节点防 AI 覆盖）为**预留语义，当前未实现**；将来出现真实需要（如对外开放、出现多写入方）时经 `protocol/GOVERNANCE.md` 治理流程加回，禁止自行实现。裁定记录见 [`07.工程-工程路线与Dogfood验收.md`](07.工程-工程路线与Dogfood验收.md) §十六 · C-5（2026-09-03，方向 (a) 协议追认代码）。

## 5. Traceability

Every accepted or high-confidence fact should be connected to at least one of:

- source evidence
- explicit human decision
- previous accepted snapshot
- generated result with recorded assumptions and coverage

Accepted nodes without evidence are allowed only as provisional decisions and must stay visible as trust gaps.

### 5.1 Source Evidence vs Implementation Evidence

两种「证据」必须区分，且**都不等于 Agent 的自述**：

- **Source Evidence（`source-evidence.yaml`）**：规格建构阶段，某条需求/节点的内容从哪里来（源码文件、位置、hash、excerpt）。
- **Implementation Evidence（0027F 已完成；原标注「待立」，属当时状态）**：Agent 实施之后，AsWish 从真实工作区**独立观察**到的结果（实际文件、hash、source location、symbol、structure）。

> **Agent Claim ≠ Implementation Evidence**：Agent 说「我完成了某功能」只是 Claim；Implementation Evidence 必须来自 AsWish 对真实工作区的独立观察，不得以 LLM 的自我总结作为底层事实。

## 6. Semantic Bundles

A semantic bundle groups the same requirement across projections.

```yaml
bundles:
  - id: bnd-login
    label: User login
    anchors:
      - tree: function
        node_ids: [func-login]
      - tree: module
        node_ids: [mod-auth-service]
      - tree: view
        node_ids: [view-login-form]
      - tree: data
        node_ids: [data-user, data-session]
    confidence: high
    completeness:
      has_function: true
      has_module: true
      has_view: true
      has_data: true
      has_evidence: true
      has_decision: false
```

Bundles support cross-tree review and detect projection gaps.

## 7. Agent Results

When an AI agent produces a proposal, AsWish should record more than the final answer.

Required review signals:

- assumptions
- tradeoffs
- unresolved questions
- blockers encountered
- alternatives considered and rejected
- coverage added
- coverage not added

This lets human reviewers judge whether the result is reasonable, not only whether it exists.

## 8. Review Decisions

Review decisions are facts, not UI state.

```yaml
decision_action: accept | reject | request_changes | lock | unlock
accept_level: low_risk | provisional | release | accountable
lock_status: unlocked | locked
```

Accept levels must be decided before implementation details are hardened because they affect schema, UI, audit logs, and downstream release gates.

### 8.1 Intent → Change Set → Decision Traceability (WO-20260830-0027A~D)

AsWish enforces a strict separation between human intent, AI interpretation, and authoritative specification changes:

```text
Human Intent (I said: TCandidateIntent -> .AsWish/llm/candidate-intent.yaml)
    ↓
AI Interpretation (AI understood: TChangeSet -> .AsWish/llm/change-set.yaml)
    ↓
Human Review (Accept / Reject / Clarify)
    ↓
Decision Authority (We decided: TSpecDecision -> .AsWish/decisions/requirement-decisions.yaml)
    ↓
Canonical Spec (.AsWish/trees/function-tree.yaml, etc.)
```

1. **`TCandidateIntent`**: Captures raw human utterance without mutating canonical spec nodes.
2. **`TChangeSet`**: Structured interpretation of proposed changes containing `before`, `after`, `reason`, and `source_type` (`explicit` / `inferred` / `unknown`), plus affected projections calculated via Semantic Bundles.
3. **`TSpecDecision`**: The **sole** authority that mutates Canonical Spec. Records `change_set_id` and `change_item_index` for end-to-end auditability. Reject and Clarify decisions leave Canonical Spec untouched.

### 8.2 Accepted Baseline（WO-20260830-0027E / WO-20260830-0028）

Accepted Baseline 是 **Human 正式接受后的历史工程参照状态**——它不是另一套 Spec，也不是与 `Snapshot` 平行的重复概念，而是对现有 `TAsWishSnapshotService` 快照的**不可变冻结**（落盘 `.AsWish/snapshots/<name>/snapshot.yaml`，扩展 `baseline:` 区块，编号 `B-0001` 起）。

```yaml
baseline:
  baseline_id: B-0001
  decision_id: dec-0001            # Human Decision 来源（Accept 决策）
  snapshot_name: <name>            # 快照子目录名
  tree_type: function | view | all
  content_hash: <sha>              # 内容哈希，含节点 summary/purpose + 内容
  relation_hash: <sha>             # 关系哈希，含 parent_id 层级 + relations
  created_at: <datetime>
  lineage:
    change_set_id: cs-func-001-01
    intent_id: ...                 # 可回溯到原始 Human Intent
  renderer_version: wireframe-v1.0 # 视觉基线（0028）可选
  visual_binding: html/visual-preview.html
```

必须保持的语义不变量：

- **ContentHash / RelationHash 严格分离**：改 `summary` 等业务字段只变 `content_hash`，`relation_hash` 不变；改 `parent_id` 等拓扑只变 `relation_hash`，`content_hash` 不变。
- **不可变**：历史 Baseline 只读；后续修改 live spec 不污染已固化的快照与树文件；旧 Baseline 不被静默覆盖。
- **Lineage 可回溯**：`change_set_id` + `intent_id` 闭环，能回答"这个基线是怎么来的"。
- **Fail-closed**：空快照 / 非法快照严禁晋升为 Accepted Baseline。
- **与视觉基线的关系**：`Accepted Visual Baseline`（0028）不是独立实体，而是**同一个 `TAsWishBaseline` record 上附加 `renderer_version` + `visual_binding`**——`Preview` 是规格表达（可确定性渲染），`Screenshot` 是实现证据（只能采集），二者不得混淆。

## 9. Invariants

AsWish implementations should enforce the protocol invariants in `protocol/invariants.md` and state transitions in `protocol/state-machine.md`.

Minimum invariants:

- node IDs are unique within a tree
- `parent_id` points to an existing node in the same tree or is null
- relations point to existing nodes
- accepted nodes have evidence or an explicit provisional/accountable decision
- generated content cannot silently overwrite locked human decisions
- stale evidence keeps historical value but must be visible

## 10. Extension Rules

Use `x_` for extension fields and kinds. Readers must ignore unknown `x_` fields and warn on unknown non-extension core fields.

```yaml
kind: x_workflow
x_vendor_score: 0.82
```

Do not use `x-` for kind names.

## 11. Public Message

Core research questions lead; the mechanism follows:

```text
Are we still building the same thing?
Where did the difference enter?

AsWish keeps what humans and agents confirmed visible before development,
and makes what was actually built comparable against it afterward —
so every difference is visible, traceable, and judged by a human.
```

Recommended comparison:

```text
Symphony makes every task runnable by agents.
AsWish keeps every agent task answerable to the thing humans confirmed.
ODD makes accepted outputs verifiable.
```

Public framing follows the propagation order: real problem → real experiment → engineering method → theory (see [01.产品-AsWish产品身份与愿景蓝图.md](01.产品-AsWish产品身份与愿景蓝图.md)).
