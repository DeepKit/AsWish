## 二、 重点模块架构规划

---

### Module 1：Accepted Baseline（基线锚定）

- **目标**：从已确认的 Canonical Spec 中生成一份不可变、可追溯、可重复比对的规格事实基线。
- **核心原则**：**禁止新建 `VisualBaselineEntity` 等平行实体**，完全复用既有 `TSpecSnapshot`。
- **数据模型**：
  * 在 `TSpecSnapshot` 中固化：
    * `SnapshotId`（如 `snap-baseline-20260901-01`）；
    * `IsBaseline: Boolean`（标记为主规格基线）；
    * `DecisionRefs: TArray<string>`（所绑定的正式决策 ID 列表）；
    * `ContentHash` 与 `RelationHash`（全局 SHA256 拓扑签名）；
    * `RendererVersion: string`（锁定渲染器版本，确保渲染确定性）；
    * `LineageParentSnapshotId: string`（谱系父版本，支持多轮修订对比）。
- **核心机制**：
  * 当人类通过 Decision 确认一组变更后，系统自动冻结当前四棵树，生成只读不可变的 Baseline 快照，落盘至 `.AsWish/snapshots/baseline-<id>.yaml`。
- **验证方式**：
  * 给定相同 Canonical Spec 文件，多次执行基线生成，产出的 `ContentHash` 与结构线框必须逐字节一致；禁止外部进程直接修改已封存的 Baseline。

---

### Module 2：Context Pack（只读任务导出）

- **目标**：将已确认的 Canonical Spec、Baseline 与 Decision 转换为外部 Coding Agent（Claude Code / Cursor / Codex）可无歧义理解的任务上下文包。
- **核心原则**：**Context 是纯派生物（Derived Artifact）**，只读，绝不允许 Agent 反向篡改 Canonical Spec。
- **核心内容**：
  * 组装导出 `.AsWish/prompts/context-pack.md`，包含：
    1. **Scope**：目标修改节点的 ID、Title、Summary 与所属投影；
    2. **Projections**：受影响的四投影关联关系（Function 行为、Module 归属、View 交互、Data 约束）；
    3. **Constraints (Invariants)**：明确系统底线与不可破坏的规则；
    4. **NotDoing 边界**：严格声明严禁 Agent 触碰或修改的外部无关文件；
    5. **Baseline Reference**：指向当前锁定的 Baseline 版本与预期产出物声明。
- **验证方式**：
  * 导出产物通过 Markdown Schema 校验，确保所有引用的 `NodeId` 均在主树中真实存在。

---

### Module 3：Implementation Evidence v0（客观实现证据采集）

- **目标**：建立独立于 Agent 对话流的代码物理事实观察探针，践行 **`Agent Claim ≠ Evidence`**。
- **核心原则**：**不搞重型全语言分析器，v0 实施极简确定性物理三层采集**。
- **数据模型** (`TSpecEvidence`)：
  * `EvidenceId`（如 `ev-code-cli-diff-01`）；
  * `SourceLayer: slParsedFromA`；
  * `FilePath: string`；
  * `FileHashAfter: string`（修改后 SHA256）；
  * `LineRange: string`（如 `L120-L185`）；
  * `SymbolName: string`（捕获的函数/类/字段声明）；
  * `BuildStatus: Boolean`（编译原始退出码是否为 0）；
  * `TestStatus: Boolean`（测试执行原始退出码是否为 0）；
  * `CapturedAt: TDateTime`。
- **采集算法**：
  1. **文件级**：扫描工作区 Git 工作树变动，提取 Modified / Added 文件列表与物理 Hash；
  2. **声明级**：利用现有的轻量级 Parser（如 `TPasParser` / `TDfmParser`）提取受影响文件中的顶层 Symbol；
  3. **构建级**：捕获编译器与测试运行的原始退出码。
  4. 最终原子写入 `.AsWish/evidence/source-evidence.yaml`。
- **验证方式**：
  * 外部 Agent 随意修改文件后，采集器能够准确无遗漏地提取出受影响文件列表与符号变迁。

---

### Module 4：Difference Engine v0（确定性差异计算引擎）

- **目标**：输入 `(Baseline, Evidence)`，通过确定性算法计算并输出结构性差异列表。
- **核心原则**：**零 LLM 介入，纯函数比对；严格遵守 `Difference ≠ Error`**。
- **差异数据模型** (`TSpecDifference`)：
  * `DiffId: string`；
  * `TargetNodeId: string`；
  * `Category: (dcMissing, dcMutation, dcBrokenReference)`；
  * `ComparisonLayer: (clFunction, clEntity, clSpatial, clVisual)`（对应四层比较中的 0/1 层）；
  * `ExpectedFact: string`（来自 Baseline）；
  * `ActualEvidence: string`（来自 Evidence）；
  * `Summary: string`。
- **三大确定性算子**：
  1. **`Missing`（规格存在，实现缺失）**：Baseline 声明了该能力或字段，但 Evidence 中找不到对应的 Symbol 或文件实现。
  2. **`Mutation`（未授权的实现漂移）**：Evidence 中检测到被修改的代码文件或函数，但在 ChangeSet 与 Baseline 中未被授权。
  3. **`Broken Reference`（关系断裂）**：Module 代码实现了新接口，但 View/Data 或关联 Module 的引用断裂。
- **输出载体**：
  * 落盘至 `.AsWish/llm/difference-report.yaml`，并可生成直观的 CLI 控制台对比表格。
- **验证方式**：
  * 构造标准 Fixture（含预设的缺失字段与越界修改），差异引擎必须 100% 精确捕获，无误报、无漏报。

---

### Module 5：Judgment & Revision Loop（裁决与修订闭环）

- **目标**：将 Difference 客观报告呈现在人类面前，支持人类行使裁决权，并无缝开启第二轮循环。
- **核心原则**：**AI 只呈现差异，人类独占裁决权；修订复用既有意向链路，严禁新建第二套流程**。
- **人类裁决的三种分支**：
  1. **`Accept Difference`（进化性差异）**：人类认为 Agent 的实现方式更好 ➔ 触发 Reverse Spec Ingestion ➔ 更新 Canonical Spec ➔ 固化为新 Baseline。
  2. **`Reject Difference`（不可接受偏离）**：人类判定实现违背初衷 ➔ 提出自然语言修正意向 ➔ **无缝重入 0027A（I said）**。
  3. **`Unresolved`（未决挂起）**：记录为探索 Ticket，保持当前状态不变。
- **多轮收敛机制**：
  * 新一轮修订自动派生新版本号（`Revision := Revision + 1`），谱系指针链接上一轮快照，确保历史可查、演进可控。

---

### Module 6：AsWish Protocol v0 工程收口

- **目标**：将协议草案（`protocol/`）与 Delphi 核心实现完成最终的严格对齐与自动化验证。
- **核心工作**：
  * 冻结 `difference.schema.json` 与 `evidence.schema.json`；
  * 实现 CLI 命令集：`aswish baseline export`、`aswish evidence harvest`、`aswish diff run`、`aswish protocol verify`；
  * 执行不变式全面自检（INV-1 ~ INV-10 全覆盖）；
  * 消除所有潜在的权限漏洞（严查是否存在任何未经 Human Decision 篡改 `trees/` 的旁路）。

### Task 1: WO-20260901-0028A · Baseline 固化与 Context Pack 导出

- **Problem**：当前只有实时规格，缺乏开发前不可变的基线快照与交付给 Agent 的标准上下文封包。
- **Why Now**：没有 Baseline 就无法度量后续实现的差异；没有 Context 就无法安全启动外部 Agent。
- **Depends On**：0027C（Decisions 写回）、`TSpecSnapshot` 基础服务。
- **Design Considerations**：复用 `TSpecSnapshot`，计算 `ContentHash`；Context Pack 保持纯只读。
- **Expected Output**：
  * `src/services/AsWish.Services.Baseline.pas`（生成不可变 Baseline 快照）；
  * `TAsWishPromptService.WriteContextPack` 升级（支持 Baseline 锚定与边界约束）；
  * CLI 子命令 `aswish baseline create`；
  * DUnitX 单元测试单元 `AsWish.Tests.Baseline.pas`。
- **Acceptance Criteria**：
  * 给定同一 Spec，生成的 Baseline 拓扑 Hash 严格一致；
  * Context Pack 包含明确的 NotDoing 约束；
  * DUnitX 全量回归通过，单 commit <= 200 行。

### Task 2: WO-20260901-0028B · Implementation Evidence 物理采集器 v0

- **Problem**：系统无法客观观察外部 Agent 在工作区修改了什么代码，存在被 AI 虚报误导的风险。
- **Why Now**：客观证据是计算差异的唯一物理输入。
- **Depends On**：Task 1、`TSpecEvidence` 数据模型、`TPasParser` 符号解析器。
- **Design Considerations**：不依赖 Agent 汇报，基于 Git 工作区物理扫描 + SHA256 + 语法符号表；不搞重型 AST。
- **Expected Output**：
  * `src/services/AsWish.Services.EvidenceCollector.pas`；

  * CLI 子命令 `aswish evidence collect`；

- **Acceptance Criteria**：
  * 模拟外部修改代码后，采集器能准确提取修改文件清单、行号、符号名与文件 Hash；
  * 编译失败时能准确记录错误退出码。

- **Problem**：系统无法自动比对 Baseline 与 Evidence 的结构差异，无法支持人类对差异进行裁决与二次修订。

## 四、 核心问题回答（研发计划验收准则）

1. **当前 AsWish 已经走到了哪里？**
   * 已彻底夯实前半段（自然语言意图承载 ➔ 结构化解释 ➔ 跨投影影响 ➔ 人类裁决写回 ➔ 协议与命令集成），DUnitX 149/149 稳固绿灯。
2. **First Closed Loop 缺少什么？**
   * 缺少开发前基线固化（Baseline）、实施后物理事实采集（Evidence）、确定性差异计算（Difference）以及差异驱动的第二轮修订（Revision）。
3. **下一步最值得投入的工程工作是什么？**
   * 严格按照 Task 1 ➔ Task 2 ➔ Task 3 ➔ Task 4 单链推进，绝不并发，打通后半段。
4. **每项工作如何验证？**
   * 采用“双闸门门禁”：各项开发任务不仅要通过 DUnitX 单元测试（Engineering Green），还要在 AsWish 自身工程上跑通真实步骤（Dogfood Green）。
5. **完成后 AsWish 是否真正证明了自己的核心价值？**
   * 是。当 Task 4 交付时，AsWish 将拥有全世界第一份完整的、可逐行核对哈希的**“人机协作意图演进与差异捕获实证案例”**，用无可辩驳的事实验证差异一元论与 AsWish 的核心假说。
