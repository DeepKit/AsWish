## 第一部分：AsWish 软件本质与非 UI 核心定位

### 1.1 软件定位定界（What It Is / What It Is Not）

接手或探索 AsWish 的核心前提，是彻底摒弃旧时代“Spec Editor / AI Requirement Tool / AI Coding Tool”的局限视角。

```text
       ┌──────────┐
       │  Human   │ (意向主体，终审裁决)
       └────┬─────┘
            │  I said / We decided
            ▼
┌─────────────────────────┐
│     AsWish 开放工程层     │ ◄── [本资料包探索的核心领域]
│  (.AsWish/ Protocol)    │     (显影 ➔ 确认 ➔ 建构 ➔ 看见 ➔ 生产 ➔ 验证)
└───────────┬─────────────┘
            │  Context Pack / Verified Baseline
            ▼
┌─────────────────────────┐
│  AI Coding Agent (外部)  │ (Claude Code / Codex / Cursor / Gemini CLI)
└───────────┬─────────────┘
            │  Code Execution / Artifacts
            ▼
┌─────────────────────────┐
│ Software Implementation │ (最终运行的代码与软件系统)
└─────────────────────────┘
```

- **What It Is**：
  AsWish 是位于人类、外部 AI 编码智能体与实际软件实现之间的**开放工程系统与可审计协议载体**。它解决的核心问题不是“需求规格是否写得漂亮”，而是：
  > **Are we still building the same thing?**（我们是否还在构建同一个东西？）  
  > **Where did the difference enter?**（差异究竟从哪里进入了系统？）
- **What It Is Not**：
  - 严禁将其简化为普通的需求管理系统（Jira/Linear 替代品）；
  - 严禁将其视为代码生成工具或 IDE 本身；
  - 严禁将其视为 Agent 编排调度器（Orchestrator）。开发执行始终由外部 Agent 完成，AsWish 负责确立可验证事实、采集实现证据并暴露差异。

### 1.2 理论母体在非 UI 工程层的映射

- **差异一元论 (Difference Monism, DM)**：
  - 核心命题：**差异 + 非任意约束性 = 产生结构的最低起点**。
  - 工程投射：需求不是凭空完美的先验文本，代码也不是无因生成的字符流。从人类原始愿望，到人机共同澄清的规格，再到编译出的二进制与代码 AST，每一个转化阶段都在注入“差异（Difference）”。
  - 目标追求：**不追求零差异（Zero Difference）**，而是追求：
    > **Difference made visible, traceable, and judgeable.**（让差异能够被看见、被追溯、被人类判断）。

### 1.3 核心处理主链

非 UI 视角下的主链压缩口径为六步递进：

```text
显影 (Manifest) ➔ 确认 (Confirm) ➔ 建构 (Construct) ➔ 看见 (See) ➔ 生产 (Build) ➔ 验证 (Verify)
```

1. **显影**：把隐藏在人类脑海或遗留代码中的断口、模糊、未知（Fog of War）暴露出来。
2. **确认**：AI 提出结构化候选理解（ChangeSet），人类以正式决策（Decision）予以裁决。
3. **建构**：将确认项安全并入单一事实源（Canonical Spec 规范树）。
4. **看见**：固化确定性的规格基线（Baseline），提供无可争辩的比对靶标。
5. **生产**：装配无歧义上下文，交付给外部 Coding Agent 独立执行编码。
6. **验证**：采集 Agent 的客观实现证据（Implementation Evidence），计算与基线的差异，闭环重入。

## 第二部分：全生命周期功能实现步骤（从零到闭环流水线）

整个软件在无 UI 介入下的完整自动化与半自动化流转共分为九个连续功能步骤：

```text
Step 1: 代码与文档扫描 (Level 0 Scanner)
   ↓
Step 2: 自然语言意向摄入 (Candidate Ingest)
   ↓
Step 3: 结构化候选解释 (Change Set Generation)
   ↓
Step 4: 人类决策与主规格写回 (Decisions & Canonical Merge)
   ↓
Step 5: 视觉/语义基线固化 (Accepted Baseline Anchoring)
   ↓
Step 6: 外部 Agent 任务封包交付 (Context Pack Export)
   ↓
Step 7: 实现事实证据客观采集 (Evidence Harvesting)
   ↓
Step 8: 结构与语义差异计算 (Difference Computation)
   ↓
Step 9: 人类差异裁决与修订循环 (Judgment & Revision Loop)
```

---

### Step 1：冷启动与四投影扫描（Level 0 Scanner & Tree Building）

- **功能目标**：
  在不依赖任何外部 LLM 的前提下，纯通过本地确定性规则与解析器，扫描项目目录，建立 `.AsWish/` 工程空间，并产出四棵投影树的冷启动骨架。
- **数据流与实现机制**：
  1. `TAsWishScanService.ScanDirectory`：分类遍历文件，归为 Documents, Code, UI, Config, AI Rules, Ignored 六大类。
  2. `TAsWishTreeBuilder.BuildFromScan`：
     - **Function Tree**：生成根节点存根 `func-<project>`，标记 `fog_state = unknown_unknowns`，自动解析 `docs/` 下的 Markdown H1/H2 作为子能力。
     - **Module Tree**：根据源码物理目录深度排序，按父子关系派生 `package` / `unit` 结构。
     - **View Tree**：根据 `.dfm` / `.html` / `.vue` / `.tsx` 文件识别窗体与页面，解析组件层级。
     - **Data Tree**：解析代码实体类或数据模式，提取实体、字段、状态转移。
  3. `TAsWishStoreService.WriteTreeFile`：原子落盘至 `.AsWish/trees/*.yaml`。

---

### Step 2：自然语言意向摄入（Candidate Ingest / I said）

- **功能目标**：
  承载人类非正规的、带有歧义或情感倾向的自然语言修改愿望，将其精确绑定到某个已有节点或新建上下文，**绝对禁止直接修改 Canonical Spec**。
- **数据流与实现机制**：
  1. 输入载荷：接收 `NodeId`, `TreeType`, `UserIntent`（如：“把库存列表加一个实时缺货预警字段”）。
  2. 清晰度检测：调用 `TAsWishCandidateIngest.CheckIntentClarity`：
     - 若输入极短（如“修改一下”、“优化”）或缺乏动宾结构，自动构造 `itGrillingTicket` 追问工作项。
  3. 独立持久化：调用 `SaveCandidateIntent`，原子写入 `.AsWish/llm/candidate-intent.yaml`。
  4. 节点注入：在内存 `TSpecNode` 中暂存 `UserIntent`，等待解释器介入。

---

### Step 3：结构化候选解释（Structured Change Set / AI understood）

- **功能目标**：
  AI 将人类的自然语言意图解释为不可混淆的、具备字段级对照的候选变更集（`TChangeSet`），明确区分“你明说的”、“我推断的”与“尚不知道的”。
- **数据流与实现机制**：
  1. 提示词生成：调用 `TAsWishPromptService.WriteChangeInterpretPrompt`，组装包含目标节点上下文、所属语义束与格式约束的解释提示词。
  2. 结构化构建：LLM（或内置解释模块）产出 YAML，反序列化为 `TChangeSet`：
     - `change_set_id`：全局唯一 ID（如 `cs-func-orders-01`）；
     - `raw_user_intent`：完整保留人类意向原文；
     - `items`：变更项数组，每项包含 `target_node_id`, `field`, `before`, `after`, `source_type`, `reason`。
  3. 来源三元分类：
     - `cstExplicit`：人类直接指明的修改（高可信）；
     - `cstInferred`：AI 根据上下文逻辑推导派生的变更（待定）；
     - `cstUnknown`：人类意图中存在模糊、需要反向追问的空缺项。
  4. 持久化隔离：保存于 `.AsWish/llm/change-set-<id>.yaml`，主规格树保持零改动。

---

### Step 4：跨投影影响扩散计算（Semantic Bundle Impact Calculation）

- **功能目标**：
  单一功能点的修改往往引发跨系统多层级震荡。本步骤负责基于语义绑定（Semantic Bundle），自动推导该意图将波及哪些投影。
- **数据流与实现机制**：
  1. 调用 `TAsWishCandidateIngest.ComputeAffectedProjections(ANodeId, ABundles)`。
  2. 检索 `bundles.yaml` 中包含该 `NodeId` 的所有 `TSemanticBundle`。
  3. 遍历 Bundle 内锚定的全部关联节点，推导其命中的投影集合：
     - 例如：修改 `func-orders`（Function）➔ 关联到 `mod-order-service`（Module）、`view-order-detail`（View）、`data-order-item`（Data）。
  4. 将派生结果记录进 `TChangeSet.AffectedProjections`，作为后续审阅与测试影响范围的基准。

---

### Step 5：人类决策收口与权威写回（Decisions Authority & Spec Writeback）

- **功能目标**：
  人类对 `TChangeSet` 行使终审裁决权。**只有人类的 Accept 决策拥有写入 Canonical Spec 的唯一权力**。
- **数据流与实现机制**：
  1. **三种裁决分支**：
     - **Accept**：
       - `TAsWishDecisionsService.RecordChangeSetDecision(LCS, rsAccepted, Rationale)` ➔ 生成 `TSpecDecision`（`Status = dsAccepted`，`DecisionType = dtConfirm`，写入 `requirement-decisions.yaml`）。
       - `TAsWishCandidateIngest.ApplyChangeSet` ➔ 将 `AfterValue` 写入内存节点，更新 `ReviewStatus := rsAccepted`、`GenStatus := gsConfirmed`、`Status := nsConfirmed`，追加 `decision_refs`。
       - 原子写回磁盘：`FSpecStore.WriteTreeFile` 写入 `.AsWish/trees/`。
       - 自动触发协议验证：`TYamlValidator.ValidateTreeFile`。
     - **Reject**：
       - 生成 `Status = dsRejected`、`DecisionType = dtReject` 决策，记录拒绝理由与 `ChangeSetId`。
       - `ApplyChangeSet` 检查状态后**立即 return**，Canonical Spec 变更数为 0。
     - **Clarify**：
       - 生成 `Status = dsProposed`、`DecisionType = dtClarify` 决策，记录待澄清细节，主规格完全不变，等待发起下一轮意向。
  2. **写前快照备份**：在覆盖任何 `trees/*.yaml` 之前，`BackupTreeFileIfExisting` 自动拷贝至 `snapshots/<tree>.bak.yaml`，防止历史丢失。

---

### Step 6：视觉与语义基线固化（Accepted Baseline Anchoring）

- **功能目标**：
  在外部 Agent 动手写代码之前，冻结并持久化一份“已确认事实与视觉规格基线”，形成后续比对不可篡改的锚点。
- **数据流与实现机制**：
  1. 架构纪律：**禁止新建平行的 `VisualBaseline` 实体**，完全复用现有 `TSpecSnapshot` 机制。
  2. 基线内容：包含当前已接受的所有 `view-tree` 节点、布局约束、字段定义及其关联的 `DecisionId`。
  3. 版本与哈希锚定：计算 `ContentHash` 与 `RelationHash`，记录固定的 `renderer_version`，保证相同规格在任何时候重放渲染均保持绝对确定性。

---

### Step 7：外部 Agent 任务封包交付（Context Pack Export）

- **功能目标**：
  AsWish 不替代 Agent（如 Claude Code / Cursor / Codex），而是为其生成高密度、无歧义、强约束的上下文任务包。
- **数据流与实现机制**：
  1. 调用 `TAsWishPromptService.WriteContextPack` 与 `WriteGenerationPrompt`。
  2. 导出产物：
     - `context-pack.md`：工程概貌、四投影关系、代码物理结构、已有权威决策。
     - 严格约束注入：明确声明禁止越界修改 `.AsWish/` 之外的受限目录，要求 Agent 输出实现证据。

---

### Step 8：客观实现事实证据采集（Implementation Evidence Harvesting v0）

- **功能目标**：
  **绝不相信 Agent 的自我陈述（“Agent 汇报说做完了”不等于事实）**。系统必须主动从代码仓库与文件系统中采集客观物理证据。
- **数据流与实现机制**：
  1. 变动采集器：扫描 Agent 执行后的工作区，采集受影响的文件列表、行号区间、类/函数声明 AST、数据迁移脚本。
  2. 结构化构建：生成 `TSpecEvidence` 实体：
     - `Id`：唯一证据 ID（如 `ev-code-order-discount`）；
     - `SourceLayer := slParsedFromA`；
     - `Path`、`Lines`、`Excerpt`；
     - `ContentHash` 与 `SourceFileHash`（用于未来检测证据是否失效/stale）。
  3. 原子持久化：写入 `.AsWish/evidence/source-evidence.yaml`。

---

### Step 9：差异计算引擎与修订闭环（Difference Computation & Revision）

- **功能目标**：
  比对“Step 6 固化的基线（What we confirmed）”与“Step 8 采集的客观证据（What was actually built）”，计算并输出结构性差异。
- **数据流与实现机制**：
  1. 差异计算（Difference v0 - 结构差异算子）：
     - **存在性差异**：基线声明的字段/函数在代码证据中缺失（Missing Implementation）。
     - **越界差异**：代码证据中出现了基线中声明 `not_doing` 或未声明的额外副作用（Unintended Mutation）。
     - **跨投影断裂**：数据树字段已改，但模块树中的调用方未感知（Broken Reference）。
  2. 产出 `Difference v0` 记录：列出差异项，**系统保持中立，不判定对错（Difference ≠ Error）**。
  3. 人类裁决重入：
     - 人类判定“此差异是好的进化” ➔ 触发 Accept ➔ 自动回补主规格（反向学习）。
     - 人类判定“此差异是 Bug” ➔ 提出自然语言修正 ➔ **无缝重新进入 Step 2（I said）**，开启第二轮循环。

## 第三部分：底层核心机制与工程实现要点

### 要点 1：四树正交投影与单一事实源（SSOT）

```text
               ┌──────────────────────┐
               │    project-spec      │ (索引与全局版本)
               └──────────┬───────────┘
     ┌──────────────┬─────┴────────┬──────────────┐
     ▼              ▼              ▼              ▼
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Function │  │  Module  │  │   View   │  │   Data   │
│   Tree   │  │   Tree   │  │   Tree   │  │   Tree   │
│ (做什么)  │  │ (在哪做)  │  │ (看见啥)  │  │(数据/状态)│
└──────────┘  └──────────┘  └──────────┘  └──────────┘
```

1. **投影单一职责**：
   - `function-tree`：纯语义功能能力，描述业务逻辑，无实现细节。
   - `module-tree`：代码所有权结构（Package, Unit, Class, Service）。
   - `view-tree`：用户可操作的工作流与视觉构件。
   - `data-tree`：**第四棵树绝非泛型风险树**，而是明确承载 Schema、实体、字段、状态转移、持久化与数据迁移风险。
2. **SSOT 原则**：
   - 唯一的真相源是 `.AsWish/trees/*.yaml`。
   - 任何导出的 Markdown、HTML、图表均为瞬态投影，**禁止从衍生视图反向反编译篡改主规格**。

---

### 要点 2：双正交状态机与战争迷雾（Fog of War）收敛机制

AsWish 摒弃了一维的 `Status` 字符串，采用严格解耦的正交状态模型：

```text
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│   gen_status    │   ×   │  review_status  │   ×   │    fog_state    │
├─────────────────┤       ├─────────────────┤       ├─────────────────┤
│ gsDraft         │       │ rsUnreviewed    │       │ fsUnknownUnknowns│
│ gsGenerated     │       │ rsAccepted      │       │ fsFoggy         │
│ gsConfirmed     │       │ rsRejected      │       │ fsMisty         │
│ gsSkipped       │       │ rsDeferred      │       │ fsClear         │
└─────────────────┘       └─────────────────┘       └─────────────────┘
```

1. **正交约束**：
   - `gen_status`：描述内容的**生成演进**（AI 算出来了没有）。
   - `review_status`：描述内容的**人类政治地位**（人类认不认可）。
   - 典型组合：`gen_status = gsGenerated` + `review_status = rsAccepted` ➔ 稳态事实；`gen_status = gsGenerated` + `review_status = rsUnreviewed` ➔ 待审候选。
2. **迷雾单向收敛纪律（Fog Monotonic Convergence）**：
   - 理论依据：来自 Wayfinder 与战争迷雾思想。大任务在动手前终点必定在雾里。
   - 状态转移单向不可逆：`fsUnknownUnknowns` ➔ `fsFoggy` ➔ `fsMisty` ➔ `fsClear`。
   - **禁止 LLM 一次性消除迷雾**：LLM 的单次生成只能将节点从存根推进到 `fsFoggy`；只有经过研究、原型或人类正式 Decision 裁决，才能逐步逼近 `fsClear`。

---

### 要点 3：严苛的人机权力边界（Human Control Boundary）

工程代码中硬编码了人机权力的绝对物理隔离：

| 权限领域 | AI / LLM 边界 | Human 边界 |
| :--- | :--- | :--- |
| **主张属性** | 只能生成 `source_layer: ai_inferred`，严禁伪造 `human_decision` | 独占 `source_layer: human_decision` |
| **状态擢升** | `gen_status` 最高只能到 `generated`，**严禁自行标记 `confirmed`** | 唯有人类可将节点置为 `confirmed` |
| **审阅状态** | `review_status` 强制重置为 `unreviewed`，无权自我标记 `accepted` | 唯有人类可做出 `accepted` / `rejected` |
| **落盘权限** | 仅允许写入 `.AsWish/llm/` 临时空间 | 独占写回 `.AsWish/trees/` Canonical Spec 权力 |

---

### 要点 4：CTF Semantic Bundle（跨投影语义束）与影响控制

- **定义**：语义束（`TSemanticBundle`）是将跨越四棵树、服务于同一个业务概念的一组节点锚定在一起的语义绳结。
- **作用**：
  1. 避免全局图遍历的高昂开销，以 $O(1)$ 的直接索引计算变更的影响扩散范围（Blast Radius）；
  2. 保证批量审阅的原子性（Batch Review）：对一个 Bundle 执行 Accept，其锚定的所有树节点同批次跃迁，防止出现“接口改了但界面未确认”的半吊子状态。

---

### 要点 5：协议不变式（Invariants INV-1 ~ INV-10）与原子写保护

所有非 UI 服务在修改磁盘状态时，必须接受协议不变式的物理约束：

1. **INV-1 & INV-2 (DAG 拓扑完整性)**：节点 ID 树内唯一；`parent_id` 必须指向同树中已存在的合法节点，防止悬挂孤儿。
2. **INV-5 (证据倒查)**：处于 Accepted 状态的节点，其 `source_refs` 或 `decision_refs` 至少有一个非空。
3. **INV-7 (锁保护)**：已锁定的节点，AI 再次生成时直接跳过，绝不静默覆盖。
4. **底层原子落盘机制 (`AtomicWriteTextFile`)**：
   - 绝不使用裸文件写流（防止断电或崩溃产生 0 字节半截文件）；
   - 算法：先写入临时文件 `.tmp-<UUID>` ➔ 调用 Win32 `ReplaceFileW` 实施原子置换 ➔ 失败时降级 `MoveFileExW` 保持原文件不灭。

## 第四部分：深水区核心问题与理论难题探讨

在脱离 UI 的工程与协议底层，存在五个极深的核心问题，是支撑 AsWish 持续演进的理论高地。

---

### 探讨 1：“Are we still building the same thing?” —— 语义同一性的判定困境

#### 问题的严峻性
传统软件工程假设“PRD 是一张图纸，代码是按图施工的砖瓦”。但在 AI 编程时代，自然语言意图极其灵活，代码实现极其多变，**我们如何证明代码实现与最初意图是“同一个东西”？**

#### 探索结论与解法
1. **直接比对的不可能性**：无法用自然语言和 AST 代码直接求 Diff。两者处于完全不同的表示空间（Representation Space）。
2. **正交投影作为度量中介**：
   AsWish 提出的解法是构建四投影规范（四棵树）。当用户说“增加折扣功能”时，系统将其分解为：
   - 行为空间（Function 是否增加能力？）
   - 归属空间（Module 是否在对应类中实现？）
   - 视图空间（View 是否增加折扣显示？）
   - 数据空间（Data 是否引入持久化字段？）
3. **同一性判据**：
   若且唯若这四个投影的预期事实与采集到的代码物理证据（Evidence）在关键断言上**满足非任意约束的一致性映射**，系统才宣布“我们还在构建同一个东西”。否则，差异发生。

---

### 2. 探讨 2：“Where did the difference enter?” —— 差异注入链与误差放大模型

#### 差异产生路径分析
差异不是在代码敲完那一刻突然出现的，而是在链路中逐级渗透放大的：

```text
[人类潜意识真实愿望]
   │  Δ1: 表达差异 (无法用语言完全说清)
   ▼
[I said: 原始意图文本]
   │  Δ2: 解释差异 (LLM 误解、幻觉或过度推断)
   ▼
[Change Set: 候选变更集]
   │  Δ3: 确认漂移 (人类不仔细看，误点了 Accept)
   ▼
[Canonical Spec: 固化规格]
   │  Δ4: 实施偏离 (外部 Agent 采用了不同的架构模式)
   ▼
[Actual Implementation: 最终代码]
```

#### 应对机制
AsWish 的非 UI 核心正是通过在每个转化节点设立“留痕哨卡”来锁定泄漏源头：
- `candidate-intent.yaml` 冻结原始输入（捕获 $\Delta 1$）；
- `change-set.yaml` 显式划分 `explicit` / `inferred` / `unknown`（隔离 $\Delta 2$）；
- `requirement-decisions.yaml` 记录每一次决策的裁决者与理由（锁定 $\Delta 3$）；
- `source-evidence.yaml` 捕获最终物理证据，通过结构比对暴露 $\Delta 4$。
由此，当最终结果不对劲时，系统可以精确回溯出：**差异究竟是在第几级被引入的**。

---

### 探讨 3：Difference ≠ Error 的本质与反向吸收

#### 核心洞察
在传统的编译器或测试框架中，差异即报错（Mismatch = Failure）。但在人机共创中，**外部 Agent 制造的差异，经常包含着更优秀的技术构想**。
- 例如：人类意图要求在数据库存一个浮点数字段，而 Agent 依据性能与货币精度考虑，在代码中采用了定点数 `Decimal` 并增加了幂等校验。
- 如果将此简单判为 Error 并强行回滚，AI 的智慧就被抹杀了。

#### 工程模型
AsWish 规定 Difference 是中性的“客观存在的事实差异”：
```text
                  ┌────────────────────┐
                  │ Computed Difference│
                  └─────────┬──────────┘
                            │
               Human Judgment / Review
                            │
           ┌────────────────┴────────────────┐
           ▼                                 ▼
   [Unacceptable Error]             [Acceptable Evolution]
           │                                 │
     进入 Revision                     触发 Reverse Writeback
  (提出修正，打回重做)               (主规格吸收该差异，提升为规范)
```
这种设计让系统具备了**反向学习（Reverse Specification Ingestion）**的能力。

---

### 探讨 4：客观实现证据采集困境（The Evidence Grounding Problem）

#### 为什么禁止 Agent “自说自话”？
目前几乎所有 AI Coding 流程最大的漏洞在于：**由负责写代码的 Agent 自己向人类汇报“我搞定了”**。
- LLM 会为了迎合人类而产生谄媚性输出（Sycophancy）；
- LLM 会认为自己改了代码，但实际上漏掉了核心边缘分支；
- LLM 自称“测试全通”，但实际上测试脚本本身被它偷梁换柱。

#### 事实接地（Fact Grounding）原则
AsWish 的非 UI 实现坚决将“证据采集”剥离给独立执行模块：
1. **独立探针**：绕过 Agent 的对话流，直接分析物理文件系统的差异；
2. **确定性哈希**：通过对文件内容计算 SHA256，与原代码基线比对，证明哪些文件发生了真实改变；
3. **AST 级事实提取**：直接解析源码符号表，提取类名、方法名、注解，作为无可辩驳的证据存入 `source-evidence.yaml`。

---

### 探讨 5：多轮修订（Revision）的循环收敛性定理

#### 陷入震荡的工程风险
当系统引入了 `Human Intent ➔ Implementation ➔ Difference ➔ Revision` 闭环后，最危险的工程灾难是**无限震荡**：
- 人类提要求 ➔ Agent 改偏了 ➔ 人类提修正 ➔ Agent 改对了局部但毁了全局 ➔ 规格文件碎片化膨胀。

#### 收敛性控制要点
为了保证循环必定收敛，系统设立了三大非 UI 纪律：
1. **版本快照强制滚动**：每一次进入新一轮 Revision，旧基线自动封存为不可修改的历史快照，新基线必须基于继承链演进；
2. **不变式守护网（Invariant Gate）**：新一轮的 ChangeSet 无论如何调整，必须在写入前跑通全量拓扑验证（`ValidateTreeFile`），阻断断裂引用；
3. **单一任务穿透（Dogfood Task Discipline）**：在闭环演进期间，禁止半途扩大业务范围，必须用同一个小任务贯彻始终，直至形成完全清楚的确认闭环。

## 5. Human Control Boundary

经代码审查，确认当前架构**严格保持了 Human Decision 的控制边界**：

```text
Human Intent (TCandidateIntent)
       ↓
AI Interpretation (Prompts / TChangeSet / CandidateIngest)
       ↓
Human Decision (GUI / CLI Accept/Reject/Clarify)
       ↓
Canonical State (.AsWish/trees/)
```

### 1. AI 能做什么
- 扫描工程文件并生成初始草稿节点（`gen_status: draft` / `generated`，`review_status: unreviewed`）。
- 解析人类自然语言意图并生成解释 Prompt 与候选 `TChangeSet`。
- 计算跨投影的潜在影响范围（`affected_projections`）。

### 2. 必须由 Human 决定的事项
- 审查 `TChangeSet` 的 Before / After 变更明细。
- 做出 `Accept`、`Reject` 或 `Clarify` 裁决。
- 确认将变更持久化写入 `trees/` 下的 Canonical Spec。

### 3. 哪些操作会改变 Canonical Spec？哪些不会？
- **会改变 Canonical Spec**：
  - `AcceptChangeSet`（或 CLI `changeset accept`）：当且仅当 Human 确认 Accept 时，调用 `ApplyChangeSet` 将变更合并进 Canonical Spec 节点，将节点提升为 `ReviewStatus = rsAccepted`、`GenStatus = gsConfirmed`，追加 `decision_refs`，并原子落盘到 `trees/*.yaml`。
  - `PromotePendingDecisions` / `ApplyBundleDecisions`：将确认后的决策写回树。
- **绝对不会改变 Canonical Spec**：
  - `SubmitUserIntent`（仅落盘至 `.AsWish/llm/candidate-intent.yaml`、`.AsWish/llm/change-set-*.yaml` 与 `.AsWish/prompts/`）。
  - `ReviewChangeSet`（纯只读格式化）。
  - `RejectChangeSet`（仅在 `requirement-decisions.yaml` 记录 Rejected 决策，`ApplyChangeSet` 立即 return，0 节点被修改）。
  - `ClarifyChangeSet`（仅在 `requirement-decisions.yaml` 记录 Clarify 决策，Canonical Spec 保持原样）。

### 4. 边界漏洞检查结论
在 0027A/B/C 的修订链路中，**未发现任何绕过 Human Decision 直接篡改 Canonical Spec 的漏洞路径**。所有针对 Canonical Spec 的写回入口均以 `ADecision.Status = dsAccepted` 为前提条件。

## 6. Accept / Reject / Clarify 行为调查

### (1) Accept
- **实际行为**：
  1. 调用 `TAsWishDecisionsService.RecordChangeSetDecision(LCS, rsAccepted, Rationale)`，在 `requirement-decisions.yaml` 中生成一条 `Status = dsAccepted`、`DecisionType = dtConfirm` 的决策记录，记录 `ChangeSetId`；
  2. 调用 `TAsWishCandidateIngest.ApplyChangeSet`，将各变更项的 `AfterValue` 写入对应内存树节点；
  3. 目标节点标记 `ReviewStatus := rsAccepted`，`GenStatus := gsConfirmed`，`Status := nsConfirmed`，追加 `decision_refs`；
  4. 调用 `FSpecStore.WriteTreeFile` 原子更新 `.AsWish/trees/` 下的 YAML 事实；
  5. 自动触发 `TYamlValidator.ValidateTreeFile` 进行规范验证；
  6. 重新执行 `RenderAll` 刷新 HTML。
- **状态机与关联**：具有完整的状态机转移（`rsUnreviewed -> rsAccepted`, `gsGenerated -> gsConfirmed`），且 Decision 与 ChangeSet/ChangeItem 双向可溯。

### (2) Reject
- **实际行为**：
  1. 调用 `RecordChangeSetDecision(LCS, rsRejected, Rationale)`，在 `requirement-decisions.yaml` 中生成一条 `Status = dsRejected`、`DecisionType = dtReject` 的决策记录，记录 `ChangeSetId` 与拒绝原因；
  2. `ApplyChangeSet` 检测到 Reject 状态，直接退出，**不修改任何内存节点，不触发任何 Canonical Spec 写入**；
  3. `.AsWish/trees/` 下的 Canonical Spec 完全保持原状。
- **状态机与关联**：ChangeSet 被标记归档，保留拒绝理由与历史追溯，但不污染主规格。

### (3) Clarify
- **实际行为**：
  1. 调用 `RecordChangeSetDecision(LCS, rsDeferred, ClarificationText)`，在 `requirement-decisions.yaml` 中生成一条 `Status = dsProposed`、`DecisionType = dtClarify` 的决策记录，记录追问/澄清需求；
  2. Canonical Spec 完全保持原状，0 节点被修改；
  3. 用户可以继续输入更详尽的自然语言开启下一轮修订。
- **当前状态评估**：
  数据层与逻辑层能力已完全成立，但在现有 GUI 中尚无专用对话式多轮澄清界面（目前通过 Controller 接口接收 Clarification 文本）。

## DeepBase 反馈：DeepSpec 接入过程中遇到的问题

> 日期：2026-05-15
> 来源：DeepSpec 首次接入 DeepBase/DeepShell

---

## 问题 1：FireDAC SQLite 驱动链接未在文档中明确

**现象**：运行时报 "Object factory for class {3E9B315B-...} is missing. To register it, you can drop component [TFDPhysSQLiteDriverLink] into your project"

**根因**：DeepBase 使用 FireDAC + SQLite 作为 ConfigDB，但接入指南（`76.vcl.DeepShell-新VCL程序接入指南.md`）只说了引用 `DeepBase.Persistence.Manager.FireDAC`，没有说明还需要在 .dpr 中加入 FireDAC SQLite 驱动单元。

**实际需要的 uses**：
```pascal
FireDAC.VCLUI.Wait,
FireDAC.Comp.UI,
FireDAC.Phys.SQLite,
FireDAC.Phys.SQLiteDef,
FireDAC.Stan.ExprFuncs,
FireDAC.Stan.Def,
FireDAC.DApt,
DeepBase.Manager,
DeepBase.Persistence.Manager.FireDAC,
```

**建议**：
1. 在 `76.vcl.DeepShell-新VCL程序接入指南.md` §3.1 标准初始化中，把完整的 FireDAC uses 列表写出来，不要只写 `DeepBase.Persistence.Manager.FireDAC`。
2. 或者让 `DeepBase.Persistence.Manager.FireDAC` 的 initialization 段自动注册 SQLite 驱动（内部 uses `FireDAC.Phys.SQLite`），这样下游不需要知道底层用的是什么数据库引擎。

---

## 问题 2：root.txt 位置和 DB 文件创建逻辑不清晰

**现象**：首次运行报 "ConfigDB Not Found"，即使 root.txt 存在。

**根因**：
1. 文档说 "root.txt 位于 EXE 同目录"，但没有说明 DeepBase 是否会自动创建 DB 文件。
2. 如果 DB 文件不存在，DeepBase 应该自动创建空 SQLite DB 并初始化 schema，而不是报错。
3. 如果手动创建了一个无效的 SQLite 文件（0 字节或格式错误），DeepBase 会把它标记为 corrupted 并重命名，但不会自动创建新的有效 DB。

**建议**：
1. 在接入指南中明确说明：首次运行时 DeepBase 是否自动创建 `{AppName}Config.db`？如果是，下游不需要预创建。如果不是，提供创建脚本。
2. 当 DB 文件不存在时，DeepBase.Manager.InitializeEx 应该自动创建空 DB 并返回成功，而不是返回错误。这是最常见的首次运行场景。

---

## 问题 3：.dproj 搜索路径配置对 AI 不友好

**现象**：AI 生成的 .dproj 在 msbuild 中编译通过，但 IDE 中报 "Unit not found"。

**根因**：
1. Delphi IDE 对 .dproj 中 PropertyGroup 的 Condition 匹配规则和 msbuild 不完全一致。
2. `DCC_UnitSearchPath` 放在 `Condition="'$(Base)'=='true'"` 中时 msbuild 能找到，但 IDE 可能需要它在 `Condition="'$(Base)'!=''"` 中。
3. `.dproj.local` 文件会覆盖 .dproj 中的设置，但 AI 不知道这个文件的存在。

**建议**：
1. 提供一个 `.dproj` 模板文件（或 scaffold 脚本），让新项目从模板生成，而不是让 AI 从零写 XML。
2. 在 VCLDeepShellDemo 的 README 中说明：如果 AI 生成 .dproj，应该参考 Demo 的格式，特别是 PropertyGroup Condition 的写法。
3. 考虑提供一个 `deepbase-scaffold.ps1` 脚本，输入项目名和路径，自动生成 .dpr + .dproj + root.txt。

---

## 问题 4：RegisterStructureProvider 等方法是 protected

**现象**：从外部单元调用 `TDeepMainForm.RegisterStructureProvider` 报 E2362 "Cannot access protected symbol"。

**根因**：接入指南 §5 示例代码把 Provider 注册写在 `RegisterProviders` override 内部（同类内可访问 protected），但如果下游把注册逻辑拆到独立单元，就需要用 class helper 或 type cast hack。

**建议**：
1. 把 `RegisterStructureProvider` / `RegisterMainViewProvider` / `RegisterInspectorProvider` 改为 public。它们是下游必须调用的 API，没有理由是 protected。
2. 或者在接入指南中明确说明：Provider 注册必须在 `RegisterProviders` override 内部完成，不能拆到外部单元。

---

## 问题 5：DeepShell Demo 中 Debug 是 Cfg_2 而非 Cfg_1

**现象**：AI 按常规假设 Debug=Cfg_1、Release=Cfg_2 生成 .dproj，但 DeepShell Demo 中 Release=Cfg_1、Debug=Cfg_2。

**根因**：Delphi IDE 生成 .dproj 时 Cfg 编号取决于创建顺序，不是固定的。但 AI 没有这个上下文。

**建议**：
1. 在 scaffold 模板中固定 Debug=Cfg_2、Release=Cfg_1（与 Demo 一致）。
2. 或者在文档中说明这个约定。

---

## 问题 6：DB protection 机制在首次创建 DB 后立即标记为 corrupted

**现象**：首次运行时 DeepBase 创建了 `DeepSpecConfig.db`（4096 字节有效 SQLite），但 DB protection 机制立即检测到"corruption"并重命名为 `.corrupted_*`，然后报错。

**根因**：DeepBase.Manager 的 DB protection 逻辑在 schema 初始化完成前就执行了完整性校验，导致刚创建的空 DB 被误判为 corrupted。

**影响**：不影响运行（in-memory fallback 正常工作），但每次首次启动都会弹出错误对话框，用户体验差。

**建议**：
1. 首次创建 DB 时跳过 protection 校验（因为还没有 schema 可以校验）。
2. 或者在 InitializeEx 中区分"DB 不存在需要创建"和"DB 存在但损坏"两种情况，前者不报错。
3. VCLDeepShellDemo 也有这个问题，说明不是 DeepSpec 特有的。

## 《雾中寻路：AI 怎么对付写不出 PRD 的大任务》对 DeepSpec 的启发

> 原文：葡萄边（前端开发），知乎专栏《Grapes的AI Agent学习笔记》，2026-07-07。
> 全文存档：[`15.参考-工程与外部参考资料.md`](./15.参考-工程与外部参考资料.md)
> 原始链接：https://zhuanlan.zhihu.com/p/2057862407343625873

这篇文章讲的是 Matt Pocock 的 **wayfinder** 技能——把"终点看不清的大任务"拆成 issue tracker 上一张会生长的探索地图，每张地图挂着若干探索型 ticket，一次只解一个，直到通往终点的路清晰。其核心概念是 **Fog of war（战争迷雾）** 与 **Frontier（前沿）**：只在前沿做决定，不在迷雾里做计划。

这与 DeepSpec 的设计是**同一思想谱系**——DeepSpec 已内置 `TFogState`（`fsClear/fsMisty/fsFoggy/fsUnknownUnknowns` 四态收敛）和 `TTicketType`（`itResearchTicket/itPrototypeTicket/itGrillingTicket/itFogUnknown`）。文章相当于给 DeepSpec 的模型做了一次外部校准，也照出了当前最关键的缺口。

---

## 一、思想对齐：DeepSpec 站在正确的谱系上

文章把 mattpocock 技能体系分两层：**找路层**（wayfinder：终点不清时拆 ticket 探索）与**走路层**（to-spec 把对话沉淀成 spec，to-tickets 把 spec 拆成可执行 ticket）。

DeepSpec 的产品定位恰好横跨这两层：
- **找路层**：`TFogState` 标记节点处于迷雾中（`fsUnknownUnknowns`→`fsFoggy`→`fsMisty`→`fsClear` 单向收敛），四类 ticket 是探索迷雾的工具。
- **走路层**：spec tree（function/module/view/data 四棵树 + problems/bundles 页）就是沉淀下来的 spec，决策（Decisions）是把候选 spec 确认/驳回的执行环节。

**结论**：DeepSpec 的骨架是对的。不要因为这篇文章去推翻模型，而是去**补全它承诺但还没接线的部分**。

---

## 二、文章照出的三个核心缺口（与 bugfix.md 高度重合）

### 缺口 1：探索型 ticket 有枚举、无入口（对应 BUG-11，P1）

文章描述的 wayfinder 主交互就是"画地图→拆 ticket→一次解一个"。DeepSpec 的 `TTicketType` 四值已定义，但：
- 没有 Controller 路径创建一张 wayfinder 地图 issue；
- 没有 UI 让用户从某个 `fsUnknownUnknowns` 节点出发，创建一张 `research_ticket` / `prototype_ticket` / `grilling_ticket`；
- problems 页的 `#fog-map` 区域只展示雾区节点，没有"为这个雾区开一张探索地图"的动作。

**文章给的最关键设计原则**：地图不是任务清单，而是**索引**；ticket 不是待办项，而是**待解的问题**。DeepSpec 落地时不要把它做成又一个 todo list——ticket 的标题必须是一个**可一句话精确问出的问题**，问不出的就留在"Not yet specified"区（即 `fsUnknownUnknowns`），不硬拆。

### 缺口 2：LLM 闭环断裂（对应 BUG-8，P1）

文章强调"一次只解一个 ticket"是在**保护 AI 的 context**——一个 ticket 解完，决策和结果写进地图，下一个 ticket 从新的稳定起点开始。这正是 DeepSpec `Controller.GenerateB` 该做的事，但现状是：写 `candidate-output.yaml` 后不解析、不合入树、不重渲染（BUG-8）。用户看到"LLM done"但地图没更新——等于 ticket 解完了结果没写回地图，下一个 session 从矛盾的状态起步。

**文章给的对齐标准**：一次 ticket session 的产出，必须让"地图收缩一点"（一个未知被回答）或"地图生长一点"（暴露新未知）。DeepSpec 的 GenerateB 闭环必须做到：candidate → 解析 → 合入对应树 → 更新该节点 fog_state（往 `fsClear` 方向收敛一步）→ `RenderAll` 重渲染，让用户**看见地图变了**。

### 缺口 3：Fog Map 的"Not yet specified"语义（对应 BUG-9，P1）

文章反复强调地图里那个 **Not yet specified** 区是刻意保留的迷雾——"你还不知道怎么描述的问题"。判断标准是"能不能用一句话精确地问出来"。

DeepSpec 当前 `RenderProblemsPage` 的 `#fog-map` 只按 fog_state 分组罗列雾区节点，没有体现"这个节点为什么在雾里、要问什么问题才能让它退雾"。**启发**：每个雾区节点应附带一句"待解问题"字段（即 ticket 的 question 文本），Fog Map 分组标题下应直接列出该雾区挂着的 ticket 及其状态。这样 Fog Map 才是真正的"探索地图"，而非只是"有问题的节点清单"。

---

## 三、可直接照搬的四个设计细节

1. **四种 ticket 的 HITL/AFK 属性**（文章原文）：
   - `research_ticket`：可 AFK（读文档/源码产出摘要，AI 自跑）。
   - `prototype_ticket`：必 HITL（粗糙原型，人要过来看一眼给反馈）——对应 DeepSpec 已有的 Tracer Bullet 思路。
   - `grilling_ticket`：默认 HITL（一问一答把模糊问题问清楚）——对应 DDD 的 Ubiquitous Language，产出通用词汇表。
   - `fog_unknown`：不是 ticket，是"还问不出来的问题"，留在雾里不硬拆。

   DeepSpec 可在 ticket 模型上加 `RequiresHuman: Boolean` 字段，UI 用它决定是自动跑还是等人。

2. **地图会生长也会收缩**：解完一个 ticket，可能让一个 `fsUnknownUnknowns` 退到 `fsFoggy`（收缩），也可能暴露新的 `fsUnknownUnknowns`（生长）。DeepSpec 的 `TFogState` 收敛是单向的（只能往 clear 走），但**新节点的 fog_state 可以是 `fsUnknownUnknowns`**——生长靠新雾区节点出现，收缩靠现节点退雾。这个机制已在数据模型里，需在闭环里实际触发。

3. **spec vs ticket 的层级**（文章原文）：spec 是跨多 session 的计划，ticket 是单 session 的计划。DeepSpec 的树节点（spec 层）和 ticket 应是父子关系——ticket 是某节点退雾的探索单元，挂在节点下。建议 `TTicket` 加 `ParentNodeId` 字段。

4. **晴天别开雾灯**：文章明确"终点明确就别绕路，直接 to-spec"。DeepSpec 不应给所有节点强标 fog——首次扫描只给真正"证据不足、靠推断"的 function 根标 fog（已是当前设计，见 bugfix.md #3 设计说明），其余从结构实打实推导的不算雾。

---

## 四、一句话总结

DeepSpec 已经内建了 wayfinder 的全部原语（fog 四态 + 四类探索 ticket），但**只建了数据模型，没建工作流**。文章给的路线图很清晰：先补 BUG-11（ticket 创建入口 + Fog Map 挂 ticket）和 BUG-8（GenerateB 闭环把 ticket 结果写回树、退雾、重渲染），DeepSpec 就从"静态 spec 浏览器"升级成"会生长的探索地图"——这正是 wayfinder 的核心价值，也是 DeepSpec 产品定位里最该兑现的那一层。

下一步建议优先级：**BUG-8（闭环）→ BUG-11（ticket 入口）→ BUG-9（Fog Map 展示 ticket）**，三者构成完整的"一次解一个 ticket"主循环。

你让 AI 帮你做个功能。

描述写得挺清楚，AI 也干劲十足，哗啦啦写了一大堆代码。跑起来一看——不是你要的。

换个方式再来。这次 AI 谨慎多了，每一步都问你。但问着问着，你发现自己也答不上来：用什么方案？做到哪步算完？这些选择取决于一些你还没验证过的假设。

你硬着头皮给了个方向，AI 跑完，发现方向是错的。退回来重做，又撞上新的未知。几个来回，AI 的上下文塞满了前后矛盾的尝试，开始重复劳动、忘记之前的决定、产出一堆语法对但架构全错的代码。

这些痛苦的共同点，不是“需求没写清楚”，也不是“AI 不够聪明”。

而是：**有些任务，你在动手之前就是想不清楚。**

用什么方案，取决于还没研究过的技术；做到什么程度，取决于没验证过的假设；甚至“到底要不要做这件事”，都取决于几个你现在还回答不了的问题。这些信息不存在于你的脑子里，也不存在于 AI 的训练数据里——它们得在你动手试探之后，才会浮现。

Matt Pocock——TypeScript 圈大神，开了个 [GitHub](https://zhida.zhihu.com/search?content_id=278506782&content_type=Article&match_order=1&q=GitHub&zhida_source=entity) 仓库 [mattpocock/skills](https://link.zhihu.com/?target=https%3A//github.com/mattpocock/skills)，把他日常 AI 编程用到的技能放出来，直接冲到 150k star——给这种情况起了个名字：**终点在雾里。** 隐约知道大概方向，但看不清路，更看不清终点。

他刚发布的 [wayfinder](https://zhida.zhihu.com/search?content_id=278506782&content_type=Article&match_order=1&q=wayfinder&zhida_source=entity) 技能，就是专门为这种任务做的。

### 想不清楚的需求

先把两种难任务分开。

一种是“大但明确”。你想做登录系统，细节很多，但终点是清楚的：用户能注册、登录、登出，密码错了有提示。这种任务哪怕代码量大，也写得出来 PRD。给它足够上下文，AI 能按部就班拆成模块，逐块实现。

另一种是“大且看不清”。你脑海里只有一个模糊的方向，比如“让我们的 CLI 工具支持插件生态”，或者“把这套内部数据流重构成可扩展的架构”。具体要支持哪些插件？扩展点在哪？现有代码能不能撑住？这些答案不在你脑子里，得先去翻源码、去试原型、去问人。

![](https://pic1.zhimg.com/v2-0b691736e50531e68101e94fdb256b8c_r.jpg)

两种任务的区别

Matt Pocock 在推特上把"大且看不清"拆成两个概念：Frontier（前沿）和 [Fog of war](https://zhida.zhihu.com/search?content_id=278506782&content_type=Article&match_order=1&q=Fog+of+war&zhida_source=entity)（战争迷雾）。前沿是已知的边界——你能做的决定，手里有的信息；迷雾是边界之外——你还看不清的部分。规则只有一条：只在前沿做决定，别在迷雾里做计划。

> Two new leading words for planning work with AI: Frontier, Fog of war. "Don't plan past the fog of war. Let's resolve just the decisions at the frontier first."
>
> 用 AI 规划工作时，有两个关键概念：Frontier（前沿）和 Fog of war（战争迷雾）。不要规划迷雾之外的部分，先解决前沿的决策。

我以前做重构，最喜欢先写一份"完整"的改造方案，越详细越好。结果常常写到一半发现：某个依赖的行为和文档不一致；某个看起来简单的改动会波及三个业务线；自以为能复用的抽象其实只覆盖了一半场景。方案越详细，推翻的时候越狼狈。而 O'Reilly 那篇文章说的更直接：

> 你往往是在往对话里塞了最多信息的时候，触发了上下文限制——这时丢失的信息，代价最大。

所以问题不是任务大，而是信息压根不存在。你没法在聊天框里一次性把它说清楚，因为连你自己都还不知道你需要什么。那些信息，要等你动手试探之后才会浮现。

### 一张会生长的地图

wayfinder 的解决办法，是别把整段探索塞进一个对话。它把任务变成 [issue tracker](https://zhida.zhihu.com/search?content_id=278506782&content_type=Article&match_order=1&q=issue+tracker&zhida_source=entity) 上的一张“地图”，每个未知拆成一个 ticket，一次只解决一个。

> Issue tracker 是像 [Linear](https://link.zhihu.com/?target=https%3A//linear.app/) 或 GitHub Issues 这样的产品。你可以把 issue/ticket 理解成中文项目管理工具里的“工作项”（需求、缺陷、任务等）。后文会交替使用 issue/ticket 英文术语和“工作项”来辅助理解。

Matt Pocock 给 wayfinder 的定位是：

> Plan a huge chunk of work — more than one agent session can hold — as a shared map of investigation tickets on your issue tracker, and resolve them one at a time until the way to the destination is clear.
>
> 如果工作大到一次会话塞不下，在 issue tracker 上创建一个探索型 issue，这个 issue 的内容是一张地图，里面贴着所有待探索的 ticket，一个一个解决，直到通往目的地的路清晰起来。

关键词是地图和探索型 issue。地图不是任务清单，而是索引；ticket 不是待办项，而是待解的问题。

wayfinder 的用法大概是：

1. 先创建一个 issue，标题写上目的地，比如“重构数据流以支持插件化扩展”。这个 issue 打上 `wayfinder:map` 标签，就是地图本身。
2. 然后和 wayfinder 一起“画地图”：把已知的未知拆成几个 ticket，每个 ticket 是一种具体动作，也打上对应的标签。

![](https://pic2.zhimg.com/v2-8ee07c1ce574f67205f3463b763a0bdf_r.jpg)

course-video-manager 的实际例子

![](https://picx.zhimg.com/v2-93d703902744e36991a21f80ed7e9273_r.jpg)

Wayfinder 怎么工作

这四种 ticket 分别是：

- **Research**：去读外部文档、源码、API，产出一份摘要。这种 ticket 可以 AFK（Away From Keyboard，挂机），让 AI 自己跑。
- **Prototype**：做一个粗糙原型，把模糊想法变成能讨论的东西。需要 HITL（Human In The Loop），你得过来看一眼、给反馈。
- **Grilling**：这其实就是著名的 grill-me 技能。跟 AI 一问一答，把一个模糊的问题问清楚。这是最常用的类型，默认 HITL。
- **Task**：纯体力活，比如批量重命名、跑测试、整理数据。HITL 或 AFK 都可以。
  这四种 ticket，每个都是这个探索型地图的 child issue（子工作项）。

![](https://pic2.zhimg.com/v2-3bb9931c297b342566cd8235df33d141_r.jpg)

四种探索 Ticket

地图 issue 大概长这样：

![](https://pic1.zhimg.com/v2-ef4f911f71f218c1ab64d74de2c0d062_r.jpg)

地图长什么样

注意那个 **Not yet specified** 区。它很关键：不是“还没分配的任务”，而是“我还不知道怎么描述的问题”。这就是刻意保留的战争迷雾。判断标准很简单：你现在的这个问题，能不能用一句话精确地问出来？如果不能，它就在雾里，不要硬拆成 ticket。
Pocock 的推特把这件事说得特别形象：

> I'm planning an entire course with it every minute of the last four days. Closing in on 100 separate grilling/prototyping/research sessions. All contributing back to a central map that: Grows as I learn more about the problem, Shrinks as I find answers to questions.
> 过去四天，我几乎每一分钟都在用它规划一门完整课程。已经接近 100 个独立的 grilling / prototyping / research session，全部汇总到一张中央地图里：问题越挖越多，答案越找越清晰。

地图会生长，也会收缩。你每找到一个答案，迷雾就退一点；每发现一个新未知，地图就长出新的边界。它不是一次画完的执行计划，而是一张随探索更新的认知地图。
它还有一条原则：一次只解一个 ticket。意思很简单——每个 session 只解决掉一个 wayfinder ticket。听起来很慢，其实是在保护 AI 的 context。一个 ticket 解完，决策和结果写进地图，下一个 ticket 从新的稳定起点开始。这样就不会出现一个 session 里前后矛盾、最后全烂掉的情况。

### 探索和执行的分界线

wayfinder 不是孤立存在的。它补的是 mattpocock 技能体系里长期缺的一块：探索。
整个技能体系可以分成两层。一层是“找路”，一层是“走路”。

**找路层：wayfinder**
任务终点不清楚，先用 wayfinder 拆 ticket、探索、更新地图。你不需要知道最终方案是什么，只需要知道“下一步该问什么问题”。

**走路层：to-spec + to-tickets**
等到路看清了——你知道要做什么、做成什么样——就该换技能。to-spec 把对话沉淀成一份 spec，to-tickets 把 spec 拆成可执行的 ticket。
spec 是跨多个 session 的计划，ticket 是单个 session 里的计划。spec 描述整体路径；ticket 描述单个 session 里要解决的具体任务。

![](https://pic3.zhimg.com/v2-69826c5373f54c9601229099c23d6f58_r.jpg)

找路层 vs 走路层

所以一个完整的工作流可能是这样：

1. 有个大任务，但终点不清楚。
2. 用 wayfinder 画地图，拆 Research / Prototype / Grilling ticket。
3. 一张张解，记录决策，迷雾退去。
4. 终点清晰了，切到 to-spec 写一份规格文档。
5. 用 to-tickets 把规格文档拆成 tickets.md 或真实 issue。
6. 逐个实现、review、合并。

![](https://pic2.zhimg.com/v2-901d0fcd73112fd267e7f35d57925ad7_r.jpg)

完整工作流

当然，如果一开局的 grilling 会话就很清晰，那根本不需要 wayfinder。终点明确就别绕路，直接 to-spec。wayfinder 不是银弹，它是雾天开雾灯。晴天还开雾灯，反而碍事。

### wayfinder 实质在做软件工程

写到这里，我想坦诚地说一句：wayfinder 不是 Matt Pocock 凭空想出来的概念。它背后有几条很扎实的工程思想渊源。

第一条渊源来自《程序员修炼之道：从小工到专家》里的 Tracer Bullets。军事上，每隔几发普通子弹混一发发光弹，用来观察弹道。软件开发中，它指端到端的薄片实现：先打通一条最小可行路径，获得反馈，再扩展。wayfinder 的 Prototype ticket 和 to-tickets 的 tracer-bullet 切片都直接继承了这个思路——反对“跑在前灯前面”，即计划速度超过反馈速度。

这个坑我踩过。有次做一个新功能的接入层，我先把配置模块、缓存模块、错误处理模块都写得漂漂亮亮，觉得每个局部都经得起 review。结果最后联调时发现：第一个端到端请求根本走不通，因为中间有一层数据格式没有对齐。局部都对，但链路死了。如果我当时先用 Tracer Bullet 打一个能从请求入口到响应出口的薄片，哪怕丑一点，也能在第一天就知道格式不对，而不是在最后一天才返工。

![](https://pic3.zhimg.com/v2-5fe139b840d36894e3028a867915a0d4_r.jpg)

Tracer Bullets 是什么

这种“先打通再打磨”的思路，在 wayfinder 里对应 Prototype ticket：不追求完美，先让未知变具体。

一条来自《领域驱动设计：软件核心复杂性应对之道》的 Ubiquitous Language（通用语言）。Grilling ticket 的核心价值，就是把“我觉得这里应该这样”变成“我们共同认可的词汇和规则”。

这个痛点我特别熟悉。我们项目里曾有两个完全不同的东西，但团队都叫“HTML 应用”。名称一样，指向不同，讨论时经常各说各话。AI 来探索分析时更惨：它看到“HTML 应用”这个词，根本没法判断当前语境是哪一个，推断自然出错。

通用语言的作用，就是把这些词一个一个钉死。Grilling ticket 很适合做这件事：跟 AI 反复确认，“你说的运行时是不是指渲染器执行阶段？”“发布态和预览态的区别是不是在于是否读取已保存的 schema？”直到形成一份通用语言文档。AI 后续读这份通用语言文档，大家交流也统一使用通用语言，当然也就不用猜了。

![](https://pic4.zhimg.com/v2-4676cc25a79943c0bd75347180374bef_r.jpg)

通用语言文档长什么样

一条来自《软件设计的哲学》的 Deep Module 概念。wayfinder 把一张大地图拆成很多小 ticket，但每个 ticket 本身有明确边界和产出。地图 issue 是浅接口（标题、几个区、依赖关系），内部却封装了几十上百个 session 的探索。

![](https://pic4.zhimg.com/v2-c038b90acab864f9d3b21aa486da3cb3_r.jpg)

什么是 Deep Module

这也说明，在 AI 时代，软件工程的很多思想变得更有用了，wayfinder 的每个设计选择都有软件工程根基。

### Matt Pocock 自己怎么用它

这些理论底色，在 Matt Pocock 自己的实践里看得最清楚。

> My new skill /wayfinder is letting me do stuff I've never considered trying. I'm planning an entire course with it every minute of the last four days. Closing in on 100 separate grilling/prototyping/research sessions. All contributing back to a central map that: Grows as I learn more about the problem, Shrinks as I find answers to questions. **It's the next evolution of /grill-me.** 我的新技能 /wayfinder 让我敢尝试以前从没想过的事。过去四天，我几乎每一分钟都在用它规划一门完整课程。已经接近 100 个独立的 grilling / prototyping / research session，全部汇总到一张中央地图里：我对问题了解越多，它就越生长；我找到的答案越多，它就越收缩。**这是 /grill-me 的下一阶段。**

一门课程的规划，不是“列出 20 节课的标题”就能做的。你得先想清楚：受众是谁、前置知识是什么、哪些概念必须放在一起、哪些案例能真正讲清楚、哪些内容看起来重要其实可以砍掉。这些问题的答案，你在第一版大纲里不可能全知道。

他用 wayfinder 的方式，不是一次把课程规划完，而是每次只解决一个“未知”：研究一个概念、做一个原型讲义、grilling 一轮确认边界。解完的 ticket 关闭归档，结论写回地图，新的 frontier 浮现出来。四天近 100 个 session，地图一直在长，也一直在缩。

这和我之前写大功能时的痛苦形成鲜明对比。我过去常常是：打开一个 session，让 AI 给我一份“完整”方案，然后试图照着执行。方案看起来专业，但执行到一半就碎。因为那份方案是在“迷雾”里画的，而迷雾中的路，根本还没被探出来。

在 Matt Pocock 的课程视频管理软件中，我们也可以看到他的使用方法：[#1181: Wayfinder map: Title-driven paths — derive Lesson & Section local paths from their titles](https://link.zhihu.com/?target=https%3A//github.com/mattpocock/course-video-manager/issues/1181)。

![](https://pic3.zhimg.com/v2-e244a5fae38c90b2c0382fed3c4e5d24_r.jpg)

真实项目里长什么样

wayfinder 不是让 AI 更聪明，而是让“探索”这件事变得可管理。它承认有些事你就是一开始想不清楚，然后给你一套方法：把未知切成小 ticket，一次解一个，每片都有记录，记录汇聚成地图，地图最终拨开迷雾，找到通往终点的道路。

说了这么多，不妨找个现在还看不清的任务试试：

```
npx skills@latest add mattpocock/skills
```

### 结尾：在雾中找路

写到这里，我想起自己曾在另一篇博客的评论区看过一个真实故事。那位开发者说，他曾经偷懒让 AI 直接重构一个巨大的后端文件，结果 AI 把逻辑改得面目全非，还删掉了 40% 的逻辑。当时他正在 vibe coding，连 Git 都还没设置好，最后花了 9 个小时手动重建自己都没完全理解的东西。

这种事的根源不是 AI 不会重构，而是他让 AI 在一个“看不清”的任务上直接执行。他不知道那 40% 的逻辑为什么存在，AI 也不知道。双方都在雾里开车，撞墙是迟早的事。

wayfinder 给这类任务提供了一个出口：不要硬写 PRD，不要硬拆执行计划，先承认终点在雾里，然后一张 ticket 一张 ticket 地探路。

它最后把“路”交给 to-spec 和 to-tickets，让你回到熟悉的执行轨道。但它真正的价值，是填补了 mattpocock 技能体系里最关键的空缺：从“我知道我要什么”到“我终于知道我要什么”之间的那段路。

雾不会散，但你可以学会在雾中寻路。
