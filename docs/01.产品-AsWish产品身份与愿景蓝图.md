## 1. What AsWish Is

AsWish 是一个开放的、免费的、理论驱动的实证工程系统，位于：

```text
Human  ↔  AI Coding Agent  ↔  Software Implementation
```

之间的**开放工程层**。

它解决的核心问题是：

> **Are we still building the same thing?**
> **Where did the difference enter?**

核心不是"Spec 是否正确"，而是：**人类意向、人机共同理解、表示、Agent 执行和最终实现之间发生了什么变化，以及这些变化能否被看见、追踪和由人判断。**

当前主要形态：Windows Desktop（Delphi/VCL + WebView2）/ Headless CLI / Open Source，以 `.AsWish/` 作为项目级协议工作空间。

## 2. What AsWish Is Not

禁止在任何当前有效文件中把 AsWish 表述为以下任何一种：

- Spec Tool / Spec Editor / WYSIWYG Spec Editor；
- AI Requirement Tool / 普通需求管理系统；
- AI Coding Tool / 代码生成平台；
- IDE / Coding Agent / LLM 本身；
- 帮助 AI 写代码的普通需求管理工具；
- 企业流程平台；
- Agent 编排器（orchestrator）；
- **AI Code Review / Bug Finder / 防错工具**；
- **AI 监督器 / 管控开发过程的系统**；
- **自动修复 / 自动纠错系统**。

这些表述不足以表达项目定位，均属旧 DeepSpec 时代的认知残留，或与「差异是常态、判断权在人」的新定位直接冲突（AsWish 让差异可见，而非消灭差异）。

## 3. Product Hierarchy

正式产品层级。**这不是四个独立产品，而是同一个理论—产品—工程体系的不同层级：**

```text
Level 0

        ↓
Level 1
As We Wish                 理论 / 方法层：人机共同理解的述事 / 建构机制
        ↓
Level 2
As I Wish                  产品概念：面向真实使用者的核心追问
        ↓
Level 3
AsWish                     工程实现 / 开源实现名称（本仓库）
        ↓
Project Workspace
.AsWish                    项目级可追踪工作空间 / 协议载体
```

解释链：

```text
Theory
   ↓
Human-AI co-construction
   ↓
Product concept
   ↓
Engineering implementation
   ↓
Project workspace / protocol
```

禁止使用降维版本（如 `Theory → Spec Tool → Code`）描述整体关系。

## 4. Difference Monism（Level 0）

理论母体，中文"差异一元论"。

核心起点：

> **差异 + 非任意约束性构成最低结构起点。**

相关推导链：Difference → Structure → Boundary → Inheritance Trace → Entity → Law / Causality → Emergence → Temporary Stability → Internality → …

与 AsWish 最相关的理论接口：`distinguishability`、`non_arbitrary_constraint`、`structure`、`boundary`、`inheritance_trace`。

必须保持既有理论强度。两条纪律：

> **DM 是存在条件论，不是宇宙生成论。**
> **DM 是可受损、可修订、可缩限的研究纲领。**

不得在产品文件中为营销而增强理论主张。理论归属细节见 [NOTICE](NOTICE) 与 [11.理论-理论归因与CTF.md](11.理论-理论归因与CTF.md)。

## 5. As We Wish（Level 1）

理论 / 方法层。**它不是当前 Desktop 软件的产品名称。**

它代表：人类与 AI 在问题显影、决策确认、表示、建构过程中形成共同理解的述事 / 建构机制。

- **I Wish**：我的初始意向。
- **We Wish**：人与 AI 经过沟通、显影、确认、建构之后形成的共同理解。

```text
I Wish
   ↓
AI interprets
   ↓
We clarify
   ↓
We decide
   ↓
We build
```

重点不是"AI 猜中我的愿望"，而是：**人与 AI 如何逐渐形成"我们现在到底在做什么"的共同理解。**

与 CTF 的关系：CTF 主张——需求的形式和粒度是人机协作的建构产物，必须可追溯，且始终可谬。CTF 当前主张强度保持 C2；涉及正式理论归因时必须使用完整限定词 **CTF Semantic Bundle**，不得扩大 CTF 的理论主张。

## 6. As I Wish（Level 2）

面向真实使用者的产品概念。它表达：

> **经过显影、确认、共同建构、视觉确认和 Agent 开发之后，最终得到的东西，是否仍然是"我真正想要的东西"。**

As I Wish 不是"AI 按我的愿望写代码"。它关注的主链：

```text
I Wish
   ↓
Problem Manifestation
   ↓
Decision Confirmation
   ↓
Shared / Current Understanding
   ↓
Representation
   ↓
Visual Baseline
   ↓
Agent Development
   ↓
Actual Software
   ↓
Implementation Evidence
   ↓
Difference
   ↓
Human Confirmation
   ↓
Revision
```

产品价值不是"生成 Spec"，而是帮助人类保持对**自己究竟在构建什么**的可见、可确认、可追踪状态。

## 7. AsWish（Level 3）

实际工程产品 / 开源实现名称（本仓库，`D:\_Progs\02Business\AsWish`）。

工程使命：

> **把 As I Wish 的核心思想变成任何开发者可以下载、运行、使用、检验、质疑和复现的真实工程系统。**

AsWish 不应该成为：IDE、Coding Agent、LLM 本身、传统 Spec 编辑器、企业流程平台。

它应该尽可能成为：**位于 Human ↔ AI Coding Agent ↔ Software Implementation 之间的开放工程层**。

## 8. .AsWish（Project Workspace）

`.AsWish` 是项目级工作空间 / 协议载体。**它不是第五个产品。**

它表示：一个 AsWish 项目在实际工程中的可追踪工作空间，承载实际项目运行所需的 protocol、state、decisions、evidence、representations、render、bundle、ingest、validation 等已有工程机制。

不得重新发明平行协议体系。协议权威来源：[05.协议-AsWish协议基线.md](05.协议-AsWish协议基线.md) 与 [protocol/](protocol/)。

## 11. Human / AI Boundary

### Human 负责

- 意向；
- 判断；
- 决策；
- 接受 / 拒绝差异；
- 最终确认。

### AI 可以

- 发现；
- 提问；
- 解释；
- 生成；
- 建议；
- 转换；
- 检查；
- 提示差异。

### 两条边界

> **AI 不拥有最终决策权。**
> **人类不直接编辑 Spec。** 人类使用自然语言表达和确认。

## 12. Difference

Difference 是当前产品最重要的研究对象之一。

- 不要把它简单定义成"Spec 和代码不同"。
- 不要为了工程方便提前给它一个未经裁定的强定义。
- 当前可用的表述：**Difference 是在人类意向 / 共同理解 / 表示 / Agent 执行 / 实际实现之间发生的、值得被看见和判断的变化。** 具体操作定义尚待后续实验和研究确定。

### Difference ≠ Error

```text
Difference
    ↓
Human reviews
    ↓
Accept / Reject / Uncertain
```

一个实现可能与此前理解不同，但人类认为"这样更好"——这仍然是有效的研究结果。

AsWish 追求的不是 Zero Difference，而是：

> **Difference made visible, traceable, and judgeable.**

并且，**即使 Difference = 0 也有价值**——它给出 Confidence「我知道现实与我确认的东西一致」。这是 Reality Visibility（现实可见性）的结果之一，权威见 [`17.产品-开发随心的六脉神剑与用户价值.md`](17.产品-开发随心的六脉神剑与用户价值.md) §五。

当前愿景（禁止写成"成为最好的 Spec Tool / AI Coding Platform"）：

> **让理论真正进入真实世界，形成一个可以被真实开发者使用、产生工程证据、接受第三方检验、发现失败和反例，并反过来推动理论修正的开放工程系统。**

```text
Theory
 ↓
Protocol
 ↓
Reference Implementation
 ↓
Real Use
 ↓
Evidence
 ↓
Critique

```

核心原则：

> **真实使用证据 > 功能数量**
> **第三方反馈 > 内部自嗨**

> **传播一个问题 > 宣传一堆功能**

## 14. Open Source Purpose

开源不是单纯"源码免费"，真正目的：

> **让第三方可以下载、运行、使用、检查、复现、质疑这个理论工程化过程。**

开源的核心传播不是 "Try my tool."，而是：

> **Test my claim.**

伴随的核心问题：**Are we still building the same thing?** 与 **Where did the difference enter?**

## 16. First-Stage Goals

第一阶段重点不是：SaaS、收费、企业销售、用户规模、功能数量。

第一阶段真正目标：

> **让陌生开发者能够下载、运行、完成第一次真实实验，并愿意把 AsWish 带入自己的真实开发工作。**

优先路径：

```text
First User → First Experiment → First Real Project → First Difference
→ First Case → First Critique → More Experiments
```

重要指标不是 GitHub Star 数量，而是：

- 完成过真实实验的人数；
- 实际使用 AsWish 的真实项目数量；
- Difference 案例；
- 用户主动形成的 Case；
- 用户主动提出的失败；
- 第三方复现实验。

### 下载即用原则

第一阶段优先保持：**Download → Run → Create Project → Start**（Windows Desktop / Local-first）。不强制：注册、登录、云端账号、SaaS Workspace、团队权限、SSO、企业部署。未来是否增加这些能力，由真实使用证据决定。

## 17. Strategic Non-Goals

- 不做商业化第一阶段的推进（SaaS / 收费 / 企业销售）；
- 不替代任何 Coding Agent，不做 IDE；
- 不追求 Zero Difference；
- 不为营销增强理论主张；
- 不重新发明平行协议体系；
- 不为功能数量牺牲真实使用证据。

## 18. Relationship to AI Coding Agents

AsWish 允许并欢迎外部 Agent 存在：Codex、Claude Code、Cursor、Gemini CLI 及其他 Agent。

> **AsWish 不需要替代这些 Agent。**

AsWish 的边界是：告诉 Agent 应该做什么、已经确认的东西长什么样，并在 Agent 完成后用实现证据支持人类验证"做出来的还是不是那个东西"。开发执行本身始终由用户选择的 Agent / CLI / IDE 承担。

## 19. Relationship to Spec

Spec 在 AsWish 中的性质：**当前被人类接受、具有来源与证据、允许未来被推翻的共同规格状态**——traceable、reviewable、fallible。

Spec 不是目的，是主链中的一环（Representation / Specification → Visual Baseline → Agent Development → … → Difference → Revision）。因此：

- AsWish 需要 Spec，因为主链需要一个可追踪、可审阅、可谬的共同理解载体；
- AsWish 不只是 Spec Tool，因为 Spec 之外还有：问题显影、决策确认、视觉基线、Agent 交付、实现证据、差异裁决与修订闭环。

### 所见即所得（WYSIWYG）的正式含义

全仓必须消除旧理解。AsWish 所说的 WYSIWYG **不是** "WYSIWYG Spec Editor"，**不是**人类直接编辑 Spec。真正含义：

> **开发前，人类与 Agent 沟通、确认时所看到的视觉对象 / 表示，与开发后实际软件产生的视觉 / 实现结果之间，应该能够进行可验证的对应与差异检查。**

```text
Before: Human + Agent understanding
        ↓
Visual / Representation Baseline
        ↓
Development
        ↓
Actual Software
        ↓
Evidence
        ↓
Compare
```

## 一、产品一句话

AsWish 让人类与 AI Agent 在开发前看见、确认同一个软件应该是什么；开发后再验证，做出来的是否还是那个东西。

更完整的产品定义：

AsWish 是 AI 原生软件开发的 **Specification Control Layer（规格控制层）**：它把模糊问题显影、关键决策确认后的共同理解固化为可追溯的规格，以视觉化对象交给开发 Agent，并在开发完成后用真实实现证据验证规格是否仍然成立。

### 产品层级（正式口径）

AsWish 不是一个孤立产品，而是同一个理论—产品—工程体系的 Level 3 层：

```text
Difference Monism   理论母体
        ↓
As We Wish          理论 / 方法层：人机共同理解的述事 / 建构机制
        ↓
As I Wish           产品概念：最终得到的是否仍然是我真正想要的
        ↓
AsWish              工程实现（本文档描述的对象）
        ↓
.AsWish             项目级可追踪工作空间 / 协议载体
```

层级定义、核心研究问题（Are we still building the same thing? / Where did the difference enter?）、人机边界与 Difference 战略地位的权威表述见 [`01.产品-AsWish产品身份与愿景蓝图.md`](01.产品-AsWish产品身份与愿景蓝图.md)，本文不复述。

- WYSIWYG Spec 编辑器；

## 三、AsWish 要解决的根问题

AI Coding 带来的核心变化不是"代码写得更快"这么简单，而是：

> **软件生产速度开始超过人类检查需求理解和实现偏差的速度。**

传统流程：

```text
需求 → 文档 → 开发 → 代码 → 人工验收
```

AI 原生开发逐渐变成：

```text
自然语言 → Agent 理解 → Agent 规划 → Agent 编码 → Agent 修改 → Agent 再编码
```

问题由此变成：

> **人在什么时候真正确认过"我们到底要做什么"？**
> **开发完成以后，做出来的到底是不是前面确认的那个东西？**

AsWish 针对的就是这两个断口。

---

## 四、核心产品闭环

AsWish 的完整主链：

```text
① 问题显影
↓
② 决策确认
↓
③ 规格建构
↓
④ 视觉确认
↓
⑤ Agent 开发
↓
⑥ 成品验证
↓
⑦ 证据回流
```

压缩成一句话：

```text
显影 → 确认 → 建构 → 看见 → 生产 → 验证
```

---

## 五、第一环：问题显影

### 5.1 目的

在进入正式规格之前，先处理：

- 模糊需求；
- 说不清的问题；
- 互相矛盾的表达；
- 弱信号；
- 规格断口；
- 证据不足；
- 当前未知。

这一层对应 **PFM** 的核心思想：

> 让说不清的问题，变得可说、可见、可承接。

### 5.2 AsWish 中的表现

项目材料经过：

```text
scan → ingest → generate
```

形成初步规格。

对于无法确定的内容：

```text
clear / misty / foggy / unknown_unknowns
```

等机制用于表达当前不确定状态。

> 注意：fog_state 当前属于 AsWish 的工程构造，理论归属继续保持"待确权"口径（详见 `11.理论-理论归因与CTF.md`）。

---

## 六、第二环：决策确认

### 6.1 核心问题

问题显影之后，真正的困难通常不是"AI 不会生成"，而是：

> **哪些关键决策其实还没有确认？**

因此 AsWish 不追求让 AI 一次性猜完整，而是：

> 找到当前最关键的未决断口，一次解决一个。

### 6.2 与外部 Wayfinder / Grilling 的关系

AsWish 可以吸收外部实践中的：

- frontier；
- fog of war；
- 一次一个决策；
- 代码优先查证；
- 人类确认；

等工作方式。

但 AsWish 的产品机制不等于 Wayfinder，也不把其概念强归为一元论理论。

AsWish 自己的核心表达是：

```text
Decision Confirmation
```

即：

```text
发现未决断口 → 提供证据 → 提出当前判断/选项 → 人类确认 → 继续下一个断口
```

---

## 七、第三环：规格建构

这是 AsWish 的核心产品层。

### 7.1 四投影

AsWish 使用四个核心投影：

```text
Function / Module / View / Data
```

它们不是四份互相独立的需求文档，而是：

> 同一需求在行为、架构、界面、数据四个维度上的投影。

### 7.2 Semantic Bundle

跨四投影描述同一个事项时，通过：

```text
CTF Semantic Bundle
```

进行绑定。

> 禁止另建一套跨投影关系系统。

### 7.3 Spec 的性质

AsWish 中的 Spec 不是永久真理，而是：

> 当前被人类接受、具有来源与证据、允许未来被推翻的共同规格状态。

因此它具备：

```text
traceable；
reviewable；
fallible。
```

---

## 八、第四环：视觉确认

这是 AsWish 区别于传统 Spec 工具的关键产品能力之一。

### 8.1 不是"编辑 Spec"

人类不直接修改 YAML、节点或 View Tree。人类通过自然语言表达：

- "登录页应该先显示账号，再显示验证码。"
- "提交按钮放到页面底部。"
- "这个页面不应该出现删除按钮。"

AsWish 根据现有 CandidateIngest / Decisions 机制形成新的规格判断。

### 8.2 View Spec 必须能够被"看见"

View Tree 不应只告诉 Agent"页面有一个按钮"，而应该进一步形成：

> 开发前可以直接看到的软件视觉对象。

即：

```text
View Spec → Visual Renderer → Visual Preview
```

这个 Preview 是规格的可观察结果，不是孤立设计稿。

### 8.3 Visual Baseline

当人类确认"这就是我们准备开发的样子"时，AsWish 保存：

```text
Accepted Visual Baseline
```

它与：

```text
View Spec；
Spec snapshot；
relevant semantic bundle；
Human Decision；
```

形成可追溯关联。

---

## 九、第五环：Agent 开发

AsWish 不自己成为 Coding Agent，而是将：

```text
Accepted Spec + View Spec + Visual Baseline + Relevant Decisions + Evidence
```

交给用户选择的 Agent / CLI / IDE。

因此 AsWish 的边界是：

> 告诉 Agent 应该做什么，以及已经确认的东西长什么样。

而不是：

> 自己接管整个开发环境。

---

## 十、第六环：成品验证

这是"开发所见即所得"的真正终点。

开发完成后，得到：

```text
Implementation Evidence
```

第一阶段最重要的形态就是：

- 实际软件截图；
- 实际页面状态截图；
- 必要时多个交互状态的截图。

然后：

```text
Accepted Visual Baseline → Actual Implementation → Visual Comparison
```

比较关注：

- **Structural Match**：页面、区域、组件、状态、主要层级是否一致。
- **Semantic Match**：界面表达的功能与交互含义是否一致。
- **Visual Match**：布局、位置、层级、主要视觉结构是否一致。

> Pixel-perfect 不是第一阶段硬门槛。

---

## 十一、视觉差异不是自动裁决

AsWish 发现"前后不一致"不意味着"开发错误"，因为开发者可能有正当理由进行修改。

因此：

```text
Difference → Human Review → Existing Decisions → Accepted / Rejected
```

仍由人类做最终裁决。

---

## 十二、第七环：证据回流

AsWish 的最终价值不只是"检查页面"，而是逐渐形成：

```text
问题 → 决策 → 规格 → 开发 → 成品 → 验证 → 差异 → 新决策 → 新规格
```

这形成：

```text
Specification Feedback Loop
```

> 规格不是静态文档，而是一个可以接受现实反作用的对象。

---

AsWish 的功能可以分为七层：

```text

```

承载。

## 十五、理论与产品的关系

AsWish 不是简单"贴了一层理论品牌"，它是部分理论构造的工程化实现。

**DM —— 差异一元论**

主要贡献：可追溯性与来源意识。

对应：

```text
traceability；
evidence；
source；
snapshot；
inheritance trace。
```

**ASTO —— 属集变迁存在论**

主要贡献：状态、变迁、边界和多投影结构。

对应：

```text
state；
transition；
actor；
boundary；
four projections；
runtime invariants。
```

**ODD —— 产出物驱动开发**

主要贡献：契约、验证、证据、封存与人类裁决的工程骨架。

AsWish 位于：

> 开发产出发生之前的规格控制层。

**CTF —— 建构追溯可谬规格方法论**

这是 AsWish 最直接、最核心的方法论来源。

核心思想：

> 需求的形式和粒度是人机协作的建构产物，必须可追溯，且始终可谬。

AsWish 的：

```text
traceable；
reviewable；
fallible；
四投影；
CTF Semantic Bundle；
review decision；
```

都与此直接相关。

> 当前 CTF 仍按 C2 候选研究纲领表述，不提高主张强度。

**PFM —— 问题显影方法论**

主要负责：规格形成以前，让模糊问题和问题断口出现。

它回答：

> "我们为什么知道这里值得继续问？"

而不是：

> "这里最终应该怎么解决？"

## 二十、最终产品愿景

AsWish 最终不是一个"AI 需求文档工具"，而应该成为：

> **AI 原生软件开发中的规格控制层。**

更根本的愿景（权威表述见 [`01.产品-AsWish产品身份与愿景蓝图.md`](01.产品-AsWish产品身份与愿景蓝图.md) §13）：

> **让理论真正进入真实世界，形成一个可以被真实开发者使用、产生工程证据、接受第三方检验、发现失败和反例，并反过来推动理论修正的开放工程系统。**

开源的核心传播是 **Test my claim**，而不是 Try my tool。核心原则：真实使用证据 > 功能数量；第三方反馈 > 内部自嗨；理论可证伪 > 理论包装；传播一个问题 > 宣传一堆功能。

其最终闭环：

```text
人类的问题
→ 问题显影
→ 决策确认
→ 共同理解
→ 可追溯 Spec
→ 视觉规格
→ 人类确认
→ Agent
→ 实际软件
→ 实现证据
→ 规格验证
→ 人类裁决
→ 新的共同理解
```

最终形成：

```text
Human Intent → Specification → Agent → Software → Evidence → Verification
```

而 AsWish 的核心承诺可以压缩成：

> **先让人和 Agent 对同一个东西达成可见的共识，再让 Agent 去做；做完以后，再证明它做的还是那个东西。**

## 二十一、当前工程阶段：First Contact → First Closed Loop

```text
Stage 1  First Contact     陌生开发者能下载、运行、理解、完成第一次实验
   ↓
Stage 2  First Closed Loop  AsWish 自己完成一次完整闭环
```

Stage 2 的第一目标不是"功能变多"，而是：

> **让 AsWish 成为自己的第一个真实用户，亲自用 AsWish 完成一次完整闭环。**

即：

> **AsWish 自己开发 AsWish，同时使用 AsWish 验证 AsWish。**

理由与验收：Stage 2 之前，主链后半段（实现证据 → 差异 → 人类裁决 → 修订）在代码层仍为空白；未跑通整条链，"Difference 被看见"就只是设计稿而非工程证据。由 AsWish 自己先承担第一次实验，失败成本最低、反例发现最早。

### 双闸门

工程推进不再以"代码完成 + 测试通过"为唯一放行条件：

```text
Engineering Green  +  Dogfood Green  →  方可进入下一票
```

| 闸门 | 回答的问题 |
|---|---|
| **Engineering Green** | 代码是否正确、可回归、可交付？ |
| **Dogfood Green** | 该能力在真实使用中真的被用起来了吗？ |

> 测试全绿只是 Engineering Green，**不是 Dogfood Green**。

依赖顺序、每票双闸门验收与 Dogfood 要求见 [`07.工程-工程路线与Dogfood验收.md`](07.工程-工程路线与Dogfood验收.md)。

## 二十二、所见即所得的工程原则

主链：

```text
显影 → 确认 → 建构 → 看见 → 生产 → 验证
```

完整闭环：

```text
Intent → Interpret → Confirm → Baseline → Agent → Evidence → Difference → Human Judgment → Revision → Rebuild → Re-verify
```

其中的 **See / 看见** 不是一个孤立阶段，而是一条贯穿性要求：

> **每一次人类需要确认"这就是我要的东西"时，AsWish 都必须提供一个可直接观察的表现。**

因此：

> **SVG / Visual Representation 是闭环基础设施的一部分，而不是装饰性 UI。**

### 正式表达（产品交互原则）

> **凡是要求 Human 作判断的对象，都必须具有稳定、可观察、可重复查看的表现。**

也就是说，AsWish 的"所见即所得"**不是传统 UI 意义上的即时渲染**。Visual Render / SVG 是当前阶段的工程实现载体——属于实现选择，**不等于产品定义**；实现载体未来可以替换，上述原则本身不变。

分工：

```text
文本   负责表达
结构   负责承载
SVG    负责让人看见
Human  负责判断
```

> **性质声明**：以上四条是**产品交互原则与工程设计原则**，**不是理论主张**，不构成对 Difference Monism / ASTO / ODD / CTF / PFM 的任何增强、削弱或重新解释。理论口径以 [`11.理论-理论归因与CTF.md`](11.理论-理论归因与CTF.md) 与 [`../NOTICE`](../NOTICE) 为准。

---

## 二十三、SVG / Visual Representation 的阶段

SVG 不是每个阶段都重新生成一张图。**哪些阶段需要新的视觉基线，哪些只是复用已有 Render**，由 §二十四 的矩阵裁定。

### 第一阶段：Problem / Current State

人类描述问题后，把当前相关结构以可视方式呈现。

目的不是美化，而是：

> **让人看见当前对象，而不是只阅读 YAML / 文本。**

### 第二阶段：Confirmed Understanding / Baseline

当人确认"对，这就是我想要的"，必须形成**可重复查看的视觉基线**：

```text
Human → 看到 → 确认 → Baseline
```

Baseline 不等于 Spec 文本本身。它是：

> **当前已确认理解的可见表现。**

> 承载机制沿用现有 `SpecSnapshot` + 视觉绑定（view-tree 引用 + `renderer_version` + decision 引用），**不新建名为 `VisualState` 的实体**。

### 第三阶段：After Agent Implementation

Agent 实施后，再次把 Implementation Result 以可视形式呈现：

```text
Baseline SVG → Agent → Actual Result SVG
```

这样人才有条件回答：

> "Agent 做出来的东西，看起来是不是刚才确认的那个东西？"

> 依据：`Screenshot = Implementation Evidence`；`Visual Preview = Specification Representation`。实现结果是**证据**，不是规格渲染产物，因此不能由 Render 生成，必须采集。

### 第四阶段：Difference View

Difference v0 初期先做结构差异，至少需要一种：

```text
Baseline  vs  Actual Result
```

的视觉比较。目的不是宣布 Error，而是：

> **让差异被看见。**

判断仍由 Human 完成：

```text
No important difference / Acceptable difference / Unacceptable difference / Unresolved
```

### 第五阶段：Revision / Rebuild

人类判断"这里不对，我要改"后，重新经过：

```text
Intent → Candidate → Confirm → Baseline → Agent
```

再次产生可视结果：

```text
Baseline v1 → Implementation v1 → Difference v1
    ↓
Human Revision
    ↓
Baseline / Confirmed Revision → Implementation v2 → Difference v2
```

整个循环都必须可以通过视觉结果观察。

### 保真度边界（第一阶段）

`TSpecNode` 无布局字段（layout / position / bounds 均缺），View Tree 是需求侧结构树。因此第一阶段 Visual Preview = **结构线框（wireframe）**，确定性渲染「页面 → 区域 → 组件 → 层级」，**不承诺相对位置与尺寸**。

渲染必须确定性：

```text
相同 View Spec + Renderer Version → 相同 Preview
```

第一阶段为纯确定性映射渲染，**不引入 LLM 视觉解释**。若要表达位置 / 尺寸，需先扩展 View Spec 布局 schema（**另立协议票**）。

## 二十四、AsWish Visual Checkpoint Matrix v0

### 关于 Current State 与 Confirmed Baseline 的语义差别

两者**有可能视觉上完全相同，但语义不同**，必须在产品与工程上区分：

```text
Current State      = "现在是什么"
Confirmed Baseline = "我们确认要的是什么"
```

相同的图像，前者是观察结果，后者是人类承诺。混淆二者会使 Difference 失去比较基准。

### Visual Checkpoint Matrix v0

> VC 编号以 [`03.规范-可见判断与交互规范.md`](03.规范-可见判断与交互规范.md) §十四为准（**6 个，覆盖历史 5 检查点版本**）。本节为速览，详细定义见 OJP。

| Checkpoint | Human 要看到什么 | Human 要判断什么 | 数据来源 | 是否形成稳定基线 | 是否参与 Difference |
|---|---|---|---|---|---|
| **VC-01 Current State** | 当前真实结构（view-tree 结构线框） | "现在是什么？" | 现有 Spec / Render（**复用**） | 否 | 否 |
| **VC-02 Problem Manifestation** | 当前结构 + 问题标记（fog / unknown / 断口） | "这是不是我要解决的问题？" | VC-01 + Overlay（**不独立 SVG**） | 否 | 否 |
| **VC-03 Confirmed Baseline** | 已确认目标（与 VC-01 可能同图、语义不同） | "这就是我要的吗？" | Confirmed Understanding（经 Decision 固化） | **是**（固定 `renderer_version` 保证可复现） | **是**（作为比较基准） |
| **VC-04 Implementation Result** | Agent 实际结果（截图 / 实际页面状态） | "做出来了吗？做成什么样？" | Implementation Evidence（**采集**，非 Render 生成） | 可复现保存 | **是** |
| **VC-05 Difference** | Baseline vs Result 的可见变化 | "哪里不同？" | VC-03 vs VC-04 **比较**，不生成新图 | 否 | **是** |
| **VC-06 Revised Result** | 修改后的结果 | "这次对了吗？" | Revision 重跑 VC-03 / 04 / 05 | 是 | 再比较 |

> Difference 的结构比较按**四层**（0 功能 / 1 实体 / 2 相对位置 / 3 配色，挂 OCGS），0/1 层平台无关用通用比较器、2/3 层用平台插件；详见 OJP §十九。
> **不机械要求每个 checkpoint 新生成独立 SVG**。生成策略见下方结论；承载机制只复用现有 `Render` / `Snapshot` / `SpecStore`，**不新增** `VisualState` / `VisualObject` / 新 Baseline 实体。

### 生成策略结论

```text
复用现有 Render             → VC-01 Current State
复用现有 Render + Overlay   → VC-02 Problem Manifestation（不独立 SVG）
复用现有 Snapshot + 视觉绑定  → VC-03 Confirmed Baseline（不新建 Baseline 实体）
必须新增采集能力             → VC-04 Implementation Result（Render 生成不了证据）
只比较，不生成新视觉          → VC-05 Difference（四层比较 0/1 通用、2/3 插件）
零新机制，整轮复用           → VC-06 Revised Result
```

> 因此**不需要**"每个步骤一张新 SVG"。真正需要新增能力的只有 VC-04（采集）与 VC-05（比较）两处。

## 二十五、产品判断：不是更复杂的 Spec 编辑器

AsWish 不应被做成：

> 一个更加复杂的 Spec 编辑器。

而应保持：

> **人类用自然语言表达，AI 协助显影、理解、建构和实现；人类在关键节点通过"看见"来确认。**

因此：

```text
Human 不会直接编辑 Spec
Human 不会直接编辑复杂结构
Human 主要通过自然语言 + 可见结果进行判断
```

这条判断直接约束工程实现：不提供 YAML 编辑器、不提供字段编辑器、不提供节点拖拽式编辑。所有规格变更都经 `CandidateIngest` 自然语言入口进入，经 `Decisions` 裁决后才写回。

### 禁止新增的平行实体

```text
VisualState / Proposal / ParallelCandidate / ChangeObject
NewDecisionSystem / NewImpactGraph
VisualDecision / VisualApproval / VisualProposal / VisualReviewState
独立 Baseline 实体 / 第二套状态机 / 第五棵树
```

优先复用：

```text
CandidateIngest / Decisions / SpecSnapshot / Render / TreeBuilder / SpecStore / Prompts
现有 Semantic Bundles / gen_status / review_status
```

> 只有现有协议确实无法表达、且经主控裁定后，才允许新增最小结构。

## AsWish 用户上手说明

## 一句话定位

AsWish 让你与 AI Agent 在开发前看见并确认同一个软件应该是什么；开发后验证做出来的是否还是那个东西。它把项目材料转成可追溯、可审阅、可决策的四投影规格，供人和 AI 共同使用。

产品身份与核心研究问题见 [`01.产品-AsWish产品身份与愿景蓝图.md`](01.产品-AsWish产品身份与愿景蓝图.md)；协议字段和状态以 [`05.协议-AsWish协议基线.md`](05.协议-AsWish协议基线.md) 为准；本文只保留首次使用所需的操作路径。

## 桌面端首次运行

1. 启动 `bin\AsWish.exe`。界面会按系统语言选择 `zh-CN`、`zh-TW` 或 `en-US`。
2. 打开 **Tools → Setup LLM (ModelScope)**，输入 API Key 和模型名。默认模型是 `Qwen/Qwen2.5-72B-Instruct`，默认 OpenAI-compatible endpoint 是 `https://api-inference.modelscope.cn/v1`。API Key 只保存到本机受保护配置，不要写入项目文件或提交到仓库。
3. 在目录面板选择项目，点击 **Visualize**。AsWish 会扫描材料、生成 `.AsWish/` 事实文件，并打开 HTML 审阅界面。
4. 依次查看四个投影页面；优先处理低置信度、`foggy`/`unknown_unknowns` 和 `unreviewed` 节点，并沿来源引用回到原文件。
5. 在界面中确认或拒绝候选项。决策写入 `.AsWish/decisions/`；完成后执行 **Promote Pending Decisions**，再重新渲染检查结果。
6. 使用 **Export Prompt** 生成给原 AI/IDE 的上下文。保留 `.AsWish/` 和 HTML 产物，作为下一轮开发的共同基线。

## 四投影怎么用

| 投影 | 主要回答的问题 | 首次查看重点 |
|---|---|---|
| `function-tree` | 系统应该做什么？ | 能力、需求、规则和未澄清目标 |
| `module-tree` | 行为由哪里承载？ | 单元、组件、命名空间和责任边界 |
| `view-tree` | 用户看见并操作什么？ | 窗体、页面、控件和交互路径 |
| `data-tree` | 数据是什么、如何持久化和迁移？ | 实体、字段、关系、状态、约束和迁移 |

四个投影是同一份规格的不同观察面，不是四套互相独立的需求。`risk_score` 是节点属性或派生视图，不是第五个投影。

## CTF 的四个操作概念

- **CTF**：先把材料整理成可追溯事实，再让 AI 生成候选规格。
- **四投影**：分别审阅行为、结构、界面和数据，并通过来源与关系交叉核对。
- **Fog 探索**：`foggy` 与 `unknown_unknowns` 表示仍需探索的需求端点；一次只推进一个明确问题。
- **正交状态**：`gen_status` 表示生成进度，`review_status` 表示人类审阅结果，二者不能互相替代。

## 无界面路径

在没有 Delphi 运行环境的机器上，可先用标准库初始化协议工作区：

```bash
python protocol/tools/init_workspace.py /path/to/project --project-name "MyProject"
```

构建 CLI 后，常用流程是：

```bat
AsWish.CLI init <dir>
AsWish.CLI scan <dir>
AsWish.CLI validate <dir>
AsWish.CLI render <dir>
AsWish.CLI health <dir> --json
AsWish.CLI ingest <dir> <candidate.yaml>
```

`scan` 会生成四投影和 HTML；`validate` 只报告协议问题；`ingest` 会校验候选 YAML，再按节点 ID 合并，保留已有的人类审阅状态。CLI 的完整参数以 [`../cli/AsWish.CLI.dpr`](../cli/AsWish.CLI.dpr) 顶部说明和 `README.md` 为准。
