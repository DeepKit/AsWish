# 一、规范目的

AsWish 的核心交互并不是让人直接编辑复杂结构，而是：

```text
Human Intent → AI Interpretation → Human Judgment → Confirmed Understanding
→ Implementation → Evidence → Difference → Human Judgment → Revision
```

因此，AsWish 必须保证：

> **人类的判断不是针对系统内部不可见的状态发生，而是针对一个人能够实际观察到的对象发生。**

本规范用于规定：什么必须被人看见；什么必须具有可观察表现；什么情况下必须形成稳定视觉表现；SVG 在整个系统中的位置；Observable、Artifact、Judgment 三者的边界；可见对象如何与事实、Decision、Snapshot、Evidence、Difference 建立追溯关系；后续工程票如何以本规范作为共同开发门禁。

---

# 二、核心原则

## OJP-01：可见判断原则

> **凡是要求 Human 进行确认、接受、拒绝、比较、判断或修订的对象，必须具有与该判断对象对应的、稳定、可观察、可重复查看的表现。**

```text
需要 Human Judgment → 必须存在 Observable → Human 对 Observable 作 Judgment
```

禁止：

```text
Hidden State → AI says "已经正确" → Human 点击确认
```

也禁止：

```text
Internal Structure → AI 自动判断 → Human 只看到"通过"
```

---

# 三、OJP 的真正含义

OJP 不等于"每一步都生成一张图"，也不等于"所有对象都必须使用 SVG"。OJP 真正要求的是：

```text
Human Judgment → Observable Object → Human Judgment
```

因此：**Observable ≠ SVG**。SVG 只是 AsWish 当前最重要的结构可视化实现方式之一。

---

# 四、三个必须分开的概念

## 4.1 Artifact
系统产生、保存或引用的事实 / 数据 / 结构化对象。例如：Human Intent、Candidate、Change Set、Decision、SpecSnapshot、Implementation Evidence、Difference。

## 4.2 Observable
Artifact 或多个 Artifact 对人的可观察表现。例如：文字、表格、Tree、结构化 Review、SVG、Preview、Overlay、Difference View。Observable 是**人实际看到的东西**。

## 4.3 Judgment
Human 针对 Observable 所作的判断。例如：Accept、Reject、Unresolved、Acceptable、Unacceptable、Revision。

三者关系：

```text
Artifact → Observable → Human Judgment
```

禁止把三者混成一个状态。

---

# 五、OJP-02：判断必须有对象

任何 Human Judgment 必须能够回答"你究竟在判断什么？"，因此每一次判断必须能够定位到对应 Observable。

禁止出现 `Human: "通过"` 而系统无法回答"通过了什么、依据什么、人看到了什么"。

---

# 六、OJP-03：需要判断的对象必须可观察

以下操作都属于 Human Judgment：确认、接受、拒绝、比较、是否正确、是否符合预期、是否存在重要差异、是否接受某项 Difference、是否需要修订。

> **只要工程流程要求 Human 作上述动作，就必须首先提供相应 Observable。**

---

# 七、OJP-04：Observable 必须与判断对象语义对应

"有界面"不等于"可判断"。必须满足：**Human 通过当前 Observable 能够理解自己正在判断的对象。**

错误：`Change Set → 显示"AI 建议已生成" → [确认]`
正确：`Change Set → 显示 原始意图 + 目标节点 + Before + After + explicit/inferred/unknown → Human Judgment`

---

# 八、OJP-05：需要结构判断时必须存在稳定结构表现

当 Human 需要判断"这个结构现在是什么样"，必须提供稳定的结构表现。当前 AsWish 优先采用 `Render + SVG`。SVG 的作用是**把结构变成人能够直接观察的对象**。

---

# 九、OJP-06：Current State 与 Confirmed Baseline 必须区分

两者可以共享同一视觉结果，但语义绝不能混淆：

```text
Current State = 现在是什么
Confirmed Baseline = 我们已经确认要的是什么
```

因此允许 `Current State SVG → Human Confirmation → Confirmed Baseline` 而无需机械生成第二张完全相同的 SVG。

---

# 十、OJP-07：Visual Baseline 必须可重复


> **FACT**: 本限制属于 First Closed Loop / Visual Baseline v0 的保真度边界，不构成后续 Platform Profile 的永久上限。

```text
Accepted Visual Baseline = SpecSnapshot + 视觉绑定 + 确定的 Renderer Version
```

不允许为实现 Baseline 新建 `VisualState / VisualBaselineEntity / VisualApproval / VisualReviewState` 等平行实体。

> **保真度边界（0028 钉死，v0 必须遵守）**：第一阶段 Baseline 是**结构线框（wireframe）**，`TSpecNode` 无布局字段（layout/position/bounds 均缺），确定性渲染「页面→区域→组件→层级」，**不承诺相对位置与尺寸**。

---

# 十一、OJP-08：可见对象必须可追溯

最低追溯原则：

```text
Observable → Artifact / Snapshot → Decision / Change Set → Human Intent
```

例如：`Baseline SVG → SpecSnapshot #42 → Decision #18 → ChangeSet #07 → Intent #03`。系统必须能够回答"这张图为什么是这个样子？"。

---

# 十二、OJP-09：可重复查看必须获得一致结果

相同输入 + 相同 Renderer Version + 相同视觉规则 → 可重复的同一视觉结果。禁止同一个 Baseline 第一次长这样、第二次自动变样，除非变更本身有明确记录。

---

# 十三、OJP-10：SVG 是实现载体，不是产品定义

产品标准定义的是"Human 必须能够观察并判断"，不是"Human 必须看到 SVG"。未来允许 SVG、Canvas、HTML、Interactive Tree、Other Visual Representation，只要满足 OJP。

---

# 十四、OJP-11：Visual Checkpoint v0

> **本节定义 First Closed Loop 的规范语义与验收要求，不声明各能力当前均已实现；当前工程实现状态以 [`07.工程-工程路线与Dogfood验收.md`](07.工程-工程路线与Dogfood验收.md) 为准，产品事实等级以 [`17.产品-开发随心的六脉神剑与用户价值.md`](17.产品-开发随心的六脉神剑与用户价值.md) 为准。**
> English: *This section defines normative semantics and acceptance requirements, not current implementation status.*

First Closed Loop 当前正式定义以下视觉检查点（**以此为准，覆盖历史 5 检查点版本**）：

```text
VC-01 Current State
VC-02 Problem Manifestation
VC-03 Confirmed Baseline
VC-04 Implementation Result
VC-05 Difference
VC-06 Revised Result
```

---

# 十五、VC-01 Current State
问题"现在是什么？"；必须看到当前真实结构；优先实现 `Spec → Render → Current State SVG`；验收：Human 能指出当前对象是什么、结构是什么、与当前任务有关的部分在哪。

---

# 十六、VC-02 Problem Manifestation
问题"问题 / 断口 / 未知在哪里？"。**不要求独立 SVG**，优先 `Current State SVG + Problem Overlay / Marker`（Fog、Unknown、Issue、Ambiguity、Missing Relation）。作用是显影问题，而不是代替 Human 解决问题。

> 落地口径：问题标记优先映射现有 `fog_state` / `grilling_ticket`，不新造问题标记体系；`fog_state` 属"待确权工程构造"（见理论确权清单）。

---

# 十七、VC-03 Confirmed Baseline
问题"我们确认的东西到底是什么？"。要求 `Human → 看见 → 确认 → Accepted Visual Baseline`。Baseline 必须可重复查看、可追溯、不被静默覆盖、能与后续 Implementation Result 比较。

---

# 十八、VC-04 Implementation Result
问题"Agent 实际做出来的东西是什么？"。必须区分：

```text
Implementation Evidence = Agent 实际做了什么
Implementation Result  = 实际产生了什么
```

结果不能只通过"Agent 已完成"来表示。

> 落地点：Implementation Result 是**具体平台产物**（有布局、有尺寸），其可视呈现依赖平台提取（见 §19 插件系统），不是 Render 直接生成。

---

# 十九、VC-05 Difference

问题"实际结果和确认结果哪里不同？"。

### 19.1 比较语义：四层比较（2026-08-31 老板钉死，挂 OCGS）

Difference 的结构比较按**四层**进行，由本质到表象：

```text
0 功能    为什么它存在，用它来干什么         —— OCGS：为（Purpose）
1 实体    有没有、叫什么、谁包含谁、数量对不对 —— OCGS：能（Ability）+ 属集结构
2 相对位置 谁在谁上 / 下 / 左 / 右 / 里 / 外   —— 空间关系（ASTO 属集 / 边界）
3 配色    看起来像什么                       —— 感知表象
```

判定顺序 = 编号顺序（0 → 3）：**高层差异是本质差异（0 层几乎总是不接受），低层差异是表象差异（3 层通常可接受），阈值由人裁**。

纪律（BJ-2「为≠当」）：**"看起来像"（3 层表象）≠ "还是那个东西"（0 层功能）**。

### 19.2 实现架构：插件系统

```text
0 / 1 层   平台无关 → 一套通用比较器（所有平台共用）
2 / 3 层   平台相关 → 平台插件（VCL / FMX / HB / WEB 各提供一个提取器）
```

每个平台插件首先提供**功能提取器**（从本平台产物反推"这是干嘛的"：Delphi 靠方法名/注释/控件 caption，WEB 靠 DOM/aria，HB 靠控件类型）。

### 19.3 可比性断层（v0 必须写死）

**Baseline 是结构线框（无位置尺寸），Implementation Result 是有布局的实际产物，两者不能直接 Side-by-side / Overlay 硬比。** 比较必须落在**共同比较层**上——即四层比较的 0/1 层（平台无关）——而不是拿线框和截图硬叠。v0 先做 0 + 1 层，2 / 3 作为插件逐步接。

### 19.4 表现方式

可用 Side-by-side、Overlay、Highlight、Structural Change List；Difference 的职责只有"让变化被看见"。

# 二十、Difference 不等于 Error

严格保持 `Difference ≠ Error`。Difference 可以是：No important difference / Acceptable difference / Unacceptable difference / Unresolved。禁止 `Difference detected → System automatically marks Error`。

---

# 二十一、VC-06 Revised Result

Revision 后不能只通过"已经调整"结束。必须重新进入 `Revision → Implementation → Evidence → Result → Difference → Human Judgment`，至少产生 `Result v2 / Difference v2` 并再次由 Human 判断。

> **双出口**：Human Judgment 后除 Revision 外，还有一个同样有效的出口——**Evolution**（人判断「这个差异更好，我接受」，接受现实并更新确认，产生 Decision + New Baseline）。二者的权威定义与映射见 [`07.工程-工程路线与Dogfood验收.md`](07.工程-工程路线与Dogfood验收.md) §八 / §十一。

---

# 二十二、六个 Checkpoint 的最低标准

| Checkpoint | Human 需要看到什么 | Human 需要判断什么 | 是否必须独立 SVG |
|---|---|---|---|
| VC-01 Current State | 当前真实结构 | 现在是什么 | 是 |
| VC-02 Problem | 当前结构 + 问题标记 | 这是不是我要解决的问题 | 否，优先 Overlay |
| VC-03 Baseline | 已确认目标结构 | 这就是我要的吗 | 是 / 可复用 Current |
| VC-04 Result | Agent 实际结果 | 做出来是什么 | 是 |
| VC-05 Difference | Baseline 与 Result 的变化 | 哪里不同 | 比较视图 |
| VC-06 Revised Result | 修正后的结果 | 这次对了吗 | 是 |

---

# 二十三、Candidate / Decision / Evidence 不要求独立 SVG

**可见 ≠ 必须视觉化。** Candidate、Change Set、Decision、Evidence、Intent 可以采用语义化 UI（文本 / 语义化 Review / 裁决界面 / 事实记录界面）。只有当对象本身涉及结构空间、布局、视图状态等内容时，才需要进入结构视觉表现。

---

# 二十四、所有"确认"必须经过 Observable

任何 `Confirm / Approve / Accept / Reject / Judge` 实现都必须检查：①判断对象是谁 ②人看到了什么 ③Observable 来自哪里 ④人的判断记录在哪里 ⑤能否回溯到对应 Artifact。缺一项不得宣称完成。

---

# 二十五、Human / AI Boundary

## Human owns
Intent、Judgment、Decision、Accept、Reject、Unresolved、Difference Judgment、Revision Decision、Final Confirmation。

## AI may
Discover、Ask、Explain、Suggest、Transform、Generate、Render、Implement、Inspect、Surface Difference。

## AI must not
把猜测当确认、把 Candidate 当 Decision、把 Difference 当 Error、未经确认修改 Canonical Spec、替 Human 做最终判断、替 Human 宣布闭环完成。

---

# 二十六、OJP 与 First Closed Loop 的关系

完整链条（Human Intent → Problem Manifestation → Candidate/Interpretation → Human Confirmation → Confirmed Understanding → Visual Baseline → Agent Development → Implementation Evidence → Implementation Result → Difference → Human Judgment → Revision → Rebuild → Re-verification）中，每一次 Human Judgment 都必须能够找到对应 Observable。

---

# 二十七、OJP 与 Dogfood 的关系

第一个 Dogfood Task 必须真实产生：Current State、Problem Manifestation、Candidate、Human Confirmation、Confirmed Baseline、Implementation Evidence、Implementation Result、Difference、Human Judgment、Revision、Result v2、Difference v2、Human Re-verification。**不要求 13 张图**，要求的是每个真正需要 Human 判断的对象都真实出现并被 Human 观察。

---

# 二十八、工程票必须增加 OJP Acceptance

任何涉及 Human Confirmation / Decision / Visual Baseline / Difference / Revision 的工单，必须加入 OJP Acceptance：

```text
□ Human 判断对象明确
□ 对象具有 Observable
□ Observable 与判断对象语义对应
□ Human 能直接观察
□ Observable 可以追溯
□ 可重复查看
□ AI 没有代替 Human 判断
□ 没有为了视觉功能增加平行实体
```

任何一项违反 → RETURNED，不得 CLOSE。

---

# 二十九、禁止模式

29.1 Hidden Approval（AI 内部完成判断 → Human 只点 OK）禁止。29.2 Blind Decision（Human 不知道具体对象 → Accept）禁止。29.3 Status-as-Observation（`status=completed` 不能替代 Actual Result）禁止。29.4 AI-as-Judge（AI"Difference 不重要"+Human[确认]）禁止。29.5 SVG-as-Product 禁止。29.6 One-SVG-per-Stage 禁止（优先判断是否可复用、是否只是 Overlay、是否只是比较、是否真的需要新视觉结果）。

---

# 三十、Artifact / Observable / Judgment 的基本链

```text
Artifact（系统事实/对象）→ Observable（人可观察表现）→ Judgment（人类判断）→ 新的 Artifact
```

AsWish 的真正闭环不是 `Data → UI → Done`，而是 `Artifact → Observable → Human Judgment → New Artifact`。

---

# 三十一、视觉表现的最小要求

视觉表现首先必须：准确、稳定、可读、可比较、可追溯；其次才考虑美观、动画、交互效果、视觉风格。First Closed Loop 阶段：**正确看见优先于漂亮看见。**

---

# 三十二、OJP 不要求自动解释一切

可观察不等于必须解释。例如 Difference View 可直接显示 `Node A title Before:X After:Y`，而不必自动生成"这意味着 Agent 误解了你的需求"（后者属于判断）。OJP 要求的是把事实和变化呈现出来，让 Human 有条件判断。

---

# 三十三、第一版能力边界

OJP v1 不要求 Pixel Diff、视觉 AI 自动评分、自动审美评价、自动差异归因、自动调整、自动接受 Difference、自动回滚。当前只要求：可见、可追溯、可重复、可比较、可判断。

---

# 三十四、与现有 AsWish 架构的关系

OJP 不新增独立架构层，优先复用 CandidateIngest、Decisions、Snapshot、Render、TreeBuilder、SpecStore、Prompts、Semantic Bundles、Evidence、Difference；不新增 VisualState、VisualDecision、VisualApproval、VisualProposal、VisualBaselineEntity、VisualReviewState。

# 三十五、开发设计时的五个问题

① Human 在这里需要判断什么？② Human 判断的具体对象是什么？③ Human 在哪里看见这个对象？④ 这个 Observable 从哪个 Artifact / Snapshot 得到？⑤ Human 的判断如何与这个 Observable 建立追溯关系？回答不了 → 该交互尚未达到可验收标准。

---

# 三十六、First Closed Loop 的最终 OJP 验收

Intent / Candidate / Baseline / Implementation / Difference / Revision 六段各自必须形成 `Observable → Judgment`，且同一真实任务至少完整经历 `v1 → Difference → Human Judgment → Revision → v2 → Difference v2 → Human Re-verification`。

---

# 三十七、最终原则

> **Human does not judge what the system knows internally; Human judges what AsWish makes observable.**

中文：**人类不判断系统内部不可见的状态；人类判断 AsWish 显现出来的对象。**

```text
没有可见对象 → 没有有效判断
没有人类判断 → 没有最终确认
没有可追溯的判断 → 没有完整闭环
```

---

# 三十八、与"所见即所得"的关系

AsWish 的"所见即所得"在 OJP 下应理解为：**不是"看到什么就保存什么"，而是"需要人确认的东西必须先被可靠地显现出来，人类的判断针对显现对象发生，并成为后续状态的依据"**。

```text
See → Judge → Confirm → Build → See Again → Compare → Judge Again
```

---

# 三十九、规范优先级

当工程实现与 OJP 冲突时：`OJP > 单票工程便利 > 当前 UI 实现`。但 OJP 本身不覆盖产品身份、理论定义、协议法源、工单具体 AC（仍遵循既有 SSOT 与文档治理规则）。若 OJP 与既有 SSOT 冲突：标记冲突，不自行裁决。

---

# 四十、版本演进

OJP v1 只建立"可见、可判断、可追溯的最小闭环"。未来 v2/v3/v4 可扩展更丰富视觉比较、跨版本比较、交互式可视化等，但任何扩展都不得破坏 `Human Judgment + Observable + Traceability` 三个核心约束。

# 分册二：AsWish-双界面交互规范-DualSurface-v1

# AsWish 双界面交互规范（Dual-Surface）

**English Title:** AsWish Dual-Surface Interaction Standard  
**中文名称：** AsWish 双界面交互规范  
**版本：** v1.0  
**状态：** Normative / Frozen（2026-08-31 落库，含老板裁定：Conversation Surface 为新增层、多角色 AI 推迟、0–9 抽离为子规范）  
**适用范围：** AsWish Desktop / WebView / GUI / 后续兼容客户端  
**关联：** [`03.规范-可见判断与交互规范.md`](#分册三aswish-统一选择交互标准-v1)（0–9 子规范）、[`03.规范-可见判断与交互规范.md`](#分册一aswish-可见判断规范ojp-v1)  
**核心原则：** Human Exploration / Human Decision Separation  

---

# 1. Purpose

本规范定义 AsWish 的基础人机交互结构。AsWish 将人机交互明确划分为两个平行的交互界面：

```text
Conversation Surface  自然对话界面（探索）
Decision Surface      交互决策界面（判断）
```

> **Conversation Surface 用于开放式探索、讨论、推演与共同理解。**

> **Decision Surface 用于在 Human 主动要求的情况下，将当前理解收敛为明确的人类判断。**

两个界面不得被混合为单一交互模式。

---

# 2. Core Principle

## 2.1 Dual-Surface Principle

```text
              AsWish
                 │
        ┌────────┴────────┐
        ▼                 ▼
Conversation Surface   Decision Surface
     自然对话             交互决策
        └────── Human ──────┘
```

二者平行、可相互切换、不同职责、不同交互密度、不同约束程度。**不得将 Decision Surface 设计成 Conversation Surface 的常驻替代物。**

---

# 3. Conversation Surface

## 3.1 Purpose
用于：Human 表达意图、发散思考、修改想法、提出尚未成熟的想法、讨论问题、与不同角色 AI 交流、AI 之间讨论质疑解释补充、形成共同理解、暂时保持不确定性。默认状态：**Open-ended / Non-committal**。

## 3.2 Human Freedom
不强迫 Human 在固定选项中选择、尽快形成决定、接受 AI 框架、对每句话结构化确认、把探索性表达立即转化为 Canonical State。Human 可以说"我还没想清楚""这个方向可能不对""刚才的说法作废"——这些默认属于 **Exploration Context**，不是 Canonical Decision。

## 3.3 AI Roles
Conversation Surface 可以存在多个 AI 角色（Product / Engineering / UX / Risk / Research AI 等），各角色可提出观点、互相质疑、提供证据、发现遗漏、解释差异、提供候选、帮助显影。但 **AI 角色不能因为参与 Conversation 就获得 Canonical Decision 权限**。

> **【落库裁定 2026-08-31】**：Conversation Surface 是**新增、尚未实现**的界面层（当前 AsWish 只有 CLI + 表单式 Review，无对话界面）。First Closed Loop 阶段：**多角色 AI 对话推迟**；Conversation Surface 先做"单人 + 单 AI 的开放对话"最小版（可先复用现有 grilling / 澄清机制）。

---

# 4. Decision Surface

## 4.1 Purpose
目的不是继续开放讨论，而是**帮助 Human 对当前已经形成的理解进行明确判断**。它是 **Constrained Human Judgment Space**，可用结构化选项，但结构化选项不得被视为 Human 思考的完整空间。

## 4.2 Activation
Decision Surface 必须由 Human 主动进入：`Conversation → Human 判断"现在需要做决定" → 进入 Decision Surface`。UI 必须提供明确入口（如"进入决定 / Decide"）。**AI 不得因为自己认为"应该做决定了"而强制切换。**

---

# 5. Separation Rule

```text
Conversation ≠ Decision
Decision ≠ Canonical Spec
```

完整表示：`Conversation → Context/Interpretation → Decision Surface → Human Decision → Canonical State`。

> **Conversation 本身默认不改变 Canonical Spec。只有正式 Human Decision 才可以成为 Canonical State 变更的授权边界。**

---

# 6. Decision Interaction Standard

Decision Surface 使用统一的数字交互协议。**0–9 的完整语义以子规范 [`03.规范-可见判断与交互规范.md`](#分册三aswish-统一选择交互标准-v1) 为唯一来源，本规范不重复定义**（治理 §3.1 禁止信息复制）。速记：

```text
1–7   当前候选选项
8     重新生成候选
9     自己输入文字
0     返回
```

该协议适用于鼠标、键盘、数字键及后续兼容输入方式。

---

# 7. 1–7 Candidate Options
最多 7 项，不要求满 7 项，禁止为凑 7 项生成低价值/虚构选项。`1` 可作为 AI 当前最推荐候选，但**不拥有更高决策权**，不得通过视觉/位置/动画制造"1 就是正确答案"的暗示。**`1–7` 不构成封闭选择空间**——任何时候 Human 都可用 `9` 超出候选。

---

# 8. 8 — Regenerate
`8` 固定语义：根据当前 Decision Context 重新生成一组候选。`8` 本身不得修改 Canonical Spec、不得产生 Accept/Reject/Clarify Decision，只是候选重构操作。

## 8.2 Context Anchor
重新生成时，**原始 Human Intent 与当前 Decision Context 必须保持为主要约束**，禁止候选漂移以致无法判断新候选是否仍属原始 Intent。

---

# 9. 9 — Human Natural Language Input
`9` 固定语义："我自己说"，是 **Human Open Expression**，不是"其他"。它允许 Human 否定整个候选框架、修改部分内容、组合多候选、加新条件、引入全新方向、重新定义问题。**`9` 输入的文字不能直接成为 Canonical Spec**，仍须 `Human Input → AI Interpretation → Human Review → Decision`。

---

# 10. 0 — Back
`0` 固定语义：返回上一交互层（Decision → Conversation）。它是 **Navigation Action**，不是 Reject、不是 Cancel、不是 Delete、不是 Undo。按下 `0` 不得创建 Decision、修改 Canonical Spec、自动 Reject/Clarify、生成新 Candidate。

---

# 11. Decision Semantics

Decision Surface 的交互选择与领域 Decision 必须语义分离。当前正式 Decision Semantics：**Accept / Reject / Clarify**。

## 11.1 Accept
Human 同意当前理解/变更，并授权其成为 Canonical State 的一部分：`Accept → Decision → Apply → Canonical Spec`。

## 11.2 Reject
Human 明确不同意当前 ChangeSet：`Reject → Decision → Canonical Spec 不变`。**Reject 不得与 `0 Back` 混淆。**

## 11.3 Clarify
Human 认为当前理解/变更尚不足以作最终决定，需进一步澄清：`Clarify → Decision → Canonical Spec 不变 → 继续自然语言交流/下一轮理解`。Clarify 不等于 Reject。

> **【落库裁定 2026-08-31 · Clarify 双重性钉死】**：Clarify 是一个**合法 Decision（落盘，如 `dsProposed`/`dtClarify`）**，其**下一步动作**是触发回到 Conversation Surface 继续显影。它"既是 Decision、又触发回对话"，实现上两件事都必须成立：落盘一条 Decision + 返回到对话，缺一不可。

---

# 12. Understanding and Decision

> **Understanding ≠ Decision**

AI 正确理解 Human Intent ≠ Human 一定同意采用该方案（`Understanding=Correct, Decision=Reject` 完全合法）。"AI 理解得对吗？"与"采用这个变更吗？"是两个不同的问题。

---

# 13. Conversation-to-Decision Transition

`Conversation → Human 主动进入 Decision → Decision Context → AI 提供候选 → Human 1–7/8/9/0 → Human Decision → Accept/Reject/Clarify`。任何环节 Human 都不应因 AI 提供候选而被视为已同意。

---

# 14. Decision-to-Conversation Transition

- Accept → Canonical State → 返回 Conversation
- Reject → Canonical State 不变 → 返回 Conversation
- Clarify → Canonical State 不变 → 返回 Conversation / 进入下一轮澄清

---

# 15. Conversation UI 不得被 Decision UI 污染

Conversation Surface 不应常驻显示 `1.–0.`，也不应频繁强迫结构化选择（`1–7` 是 Decision Interaction Protocol，不是 General Conversation Protocol；自然对话中偶然的普通数字列表不受限）。

---

# 16. Decision UI 不得假装成开放对话

Decision Surface 可允许 `9` 输入文字，但 `9` 的输入仍属于当前 Decision Context，不得绕过 Human Decision Boundary。

---

# 17. Mouse + Keyboard Equivalence
同一 Decision Action 必须同时支持 Mouse 与 Keyboard（鼠标点 [1] = 键盘按 1，余同）。两种方式不得有不同业务语义。

---

# 18. Semantic Color Standard
采用语义颜色 Token，不固定具体 RGB。Token：`Choice.Option(1–7) / Choice.Regenerate(8) / Choice.Input(9) / Choice.Back(0)`。必须同时支持 Light / Dark Theme，颜色值可不同，**语义 Token 不得改变**。不得仅用颜色表达语义——每个交互项至少"数字 + 文字"。

---

# 19. Visual Priority Rules
颜色只表达**交互类别**，不得表达 AI 判断的真伪或价值等级。`1` 可作默认焦点但不得像"绝对正确"，`8` 不得像错误，`9` 不得像低级备用入口，`0` 不得被误认为 Reject。

---

# 20. Human Judgment Protection

> **Simplicity of operation must never become simplification of human judgment.**
> **操作可以极简，判断不能被简化。**

AI 的作用是帮助显影、整理、比较、解释，不是替 Human 定义唯一合理答案。

---

# 21. Open Candidate Principle
`1–7` 是判断材料，不是封闭决策空间。任何 Decision Surface 必须保留 `9`。`AI Candidate Space ≠ Human Intent Space`。

---

# 22. AI Uncertainty
AI 不得为满足 `1–7` 格式强行制造候选。无法可靠给候选时可直说"当前无法可靠形成候选，请直接描述你的意思"，只提供 `9 / 0`。**"无法可靠给出候选"是合法状态。**

---

# 23. Frame Rejection
Human 可以拒绝的不只是某个选项，还可以拒绝**整个 AI 定义的问题框架**（如 `9` 输入"你给的选项都不是我真正要解决的问题"）。系统应理解为 **Human rejects the frame**，而非 "selected Other"。

---

# 24. Canonical Boundary
严格保持 `Conversation → AI Interpretation → Human Decision → Canonical Spec`。禁止 `Conversation → AI → Automatic Canonical Mutation`，也禁止 `Decision Candidate → Automatic Canonical Mutation`。只有正式 Human Decision 才可触发 Canonical State 变更。

---

# 25. What This Standard Does Not Define
本规范暂不规定：AI 模型选择、ChangeSet 生成、Semantic Bundle 计算、Canonical Spec 数据模型、Difference 算法、Visual Baseline、Implementation Evidence、Agent Orchestration、理论模型最终定义、具体 HTML/CSS/VCL 实现、具体 RGB 色值。

---

# 26. Minimal Reference Model

```text
                HUMAN
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 Conversation Surface   Decision Surface
   自然对话/多角色/探索      1–7/8/9/0 → Accept/Reject/Clarify
        └────────┬─────────┘
                 ▼
          Human Decision
        ┌────┬────┬────┐
      Accept Reject Clarify
        │     │      │
        ▼     ▼      ▼
   Canonical  不变   下一轮
     State
```

---

# 27. Normative Summary

- Conversation Surface：**负责探索，不负责承诺。**
- Decision Surface：**负责判断，不负责替人思考。**
- Human：**可以自由探索，并主动决定何时进入决策。**
- AI：**可以帮助显影、整理和提供候选，但不能取得最终决策权。**
- 0–9：`1–7 候选判断 / 8 重新生成 / 9 自己输入 / 0 返回`（详见于子规范）。
- Decision：`Accept / Reject / Clarify`。
- Canonical Spec：**只能通过正式 Human Decision 改变。**

---

# 28. Frozen Principle

> **Let Human think openly. Let AI help clarify. Let Human decide explicitly.**

中文：**让人自由思考，让 AI 帮助显影，让人明确决定。**

---

## 1. 全局固定规则

```text
1–7   当前上下文提供的候选选项
8     重新生成候选
9     自己输入文字
0     返回上一步
```

其中：

> **1–7 是动态语义；8、9、0 是全局固定语义。**

交互方式：鼠标点击与键盘数字键**完全等价**——用户不需要学习复杂快捷键，只需要记住 `1–9、0`。

---

## 2. `1–7`：候选选项

每个需要 Human 判断的地方，AI 最多提供 **7 个候选项**。

规则：

- `1`：默认推荐项；
- `2–7`：其他合理候选；
- 不要求必须有 7 项，可以只有 2、3、4……项；
- 不足 7 项时，不虚构选项；
- `1` 只是推荐，不代表正确答案；
- UI 不得暗示"你应该选 1"；措辞用"推荐方案"，不用"最佳方案"。

核心原则：

> **AI 提供候选空间，Human 选择。**

**AI 给不出候选是合法状态**（老板裁定 2026-08-31）：当 AI 无法可靠形成有意义的候选时，**不得为满足 `1–7` 格式强行制造候选**；可直接说明"当前无法可靠形成候选，请直接描述你的意思"，只提供 `9 / 0`。AI 不需要伪装确定。

---

## 3. `8`：重新生成候选

`8` 永远表示：

> **在当前上下文和约束下，让 AI 重新生成一组候选。**

行为：

```text
8 → AI 重新生成候选 → 新的 1–7
```

重要：

> **`8` 本身不是 Decision。**

不会修改 Canonical Spec，不产生 Accept / Reject / Clarify Decision。

**上下文锚**：重新生成时，**原始 Human Intent 与当前 Decision Context 必须保持为主要约束**；禁止候选逐轮漂移，以致无法判断新候选是否仍属于原始 Intent。

---

## 4. `9`：自己输入文字

`9` 永远表示：

> **我不想从 AI 提供的候选中选择，我自己描述。**

进入自然语言输入：

```text
9 → Human Natural Language → 当前上下文继续处理
```

因此：

> **`9` 不是"其他"。**

而是：

# Human Override / Natural Language Escape Hatch

它保证：

> **AI 的候选空间永远不会限制 Human Intent。**

这与 Human / AI Boundary 直接对应：`1–7 = AI 提供的候选空间`，`9 = Human 打破候选空间`。

**拒绝整个框架（Frame Rejection，老板裁定 2026-08-31）**：`9` 允许 Human 拒绝的不只是某个选项，而是**整个 AI 定义的问题框架**——例如"你给的选项都不是我真正要解决的问题"。系统应理解为 **Human rejects the frame**，而不是 "selected Other"。

---

## 5. `0`：返回上一步

`0` 永远表示：

> **返回上一层交互。**

它是 **UI Navigation，不是业务 Decision**。

```text
0 → Back
```

不产生 Candidate、ChangeSet、Decision，不修改 Canonical Spec。

**特别禁止**把 `0` 等同于 `Reject`：

> `0 = Back（导航）`；`Reject = Human Decision（裁决）`。两者是完全不同的语义，不得混用。

---

## 6. 视觉规范：语义色 Token

统一使用**语义色 Token**，而不是固定 RGB。四类：

```text
Choice.Option      1–7 普通候选色
Choice.Regenerate  8 重新生成语义色
Choice.Input       9 自定义输入语义色
Choice.Back        0 返回语义色
```

规则：

- **Light Theme / Dark Theme 各自定义颜色值，但语义 Token 不变**；
- `1–7` 中的默认推荐项（`1`）与 `8` / `9` / `0` 行的配色必须彼此区分；
- 同一套语义适用于所有客户端：VCL、WebView2、HTML、CLI、未来其他客户端；
- **不要让颜色只表达装饰，而要让颜色成为交互语义**——用户使用数次后形成肌肉记忆。

---

## 7. 与 Accept / Reject / Clarify 的关系

**0–9 是统一交互机制，不等于所有页面必须机械显示 10 个按钮。**

例如 ChangeSet Review 的呈现：

```text
AI 理解了你的意图：

1  接受这个理解
2  接受，但需要调整
…
7  …

8  重新生成理解
9  我自己说明
0  返回
```

但在**最终裁决层**，仍然保留 AsWish 的正式语义：

```text
Accept
Reject
Clarify
```

因此正式区分：

> **0–9 是 Interaction Protocol（交互协议）；Accept / Reject / Clarify 是 Decision Semantics（决策语义）。**

两个层级不能混淆。数字选择最终映射为哪种 Decision，由当前交互上下文决定。

---

## 8. 总原则

以后所有 AsWish GUI 交互设计，优先遵循：

```text
Human
  ↓
简单选择 / 自然语言
  ↓
AI 提供候选
  ↓
Human 判断
```

而不是：

```text
Human
  ↓
学习复杂软件操作
  ↓
编辑各种结构
  ↓
告诉 AI 应该怎么做
```

### 四条冻结原则

**① `1` 是默认推荐项，但不是强制项。**

**② `8 / 9 / 0` 是全局固定语义。**

**③ `0` 是导航，不是 Reject。**

**④ `9` 是 Human Override / Natural Language Escape Hatch，不是简单的"其他"。**

---

## 9. 与 Clarify 的配合（非聊天窗口）

AsWish 不是 ChatGPT。第一阶段的 Clarify 只需要：

```text
AI：
我无法确定你说的"深色模式"是否意味着：
1. 仅页面背景
2. 整个应用主题
…

[输入澄清内容____________]
[提交澄清]
```

然后重新进入：

```text
Candidate → ChangeSet → Review
```

> **Clarify 不是开启一个聊天系统，而是让当前意图继续显影。**

`8 / 9 / 0` 在此同样适用：`8` 换一批澄清候选，`9` 自己说明，`0` 返回不产生任何 Decision。

---

## 10. 术语呈现纪律

工程字段（如 `explicit` / `inferred` / `unknown`）不得作为术语直接教育用户。用户真正需要理解的是：

```text
你明确提出
AI 推断
尚未确定
```

具体文案由实际 ChangeSet 数据驱动，在 GUI 票中定稿。

## 13. 理解 ≠ 决定（Understanding ≠ Decision）

> **AI 正确理解了 Human Intent，不等于 Human 一定同意采用该方案。**

`Understanding = Correct, Decision = Reject` 完全合法。"AI 理解得对吗？"与"采用这个变更吗？"是两个不同的问题，本协议不得把二者合并。

- AI 提供候选（`1–7`）只代表"这是我的理解/建议"，**不构成 Human 已同意**；
- Human 在 Decision Surface 的明确裁决（Accept / Reject / Clarify）才是唯一的决定；
- 即便 AI 的候选完全正确，Human 仍有权 Reject。

## 14. 消费 HB “UI 四自”交付质量标准（AsWish 规约与评审交付门禁 · 2026-09-07 裁定收口）

> **单一母稿指针**：通用 UI 四自检查规范母稿详见 [`DeepBase/docs/ui/DeepBase-HB-AI-Delivery-Four-Self-Inspection-Standard.md`](file:///d:/_Progs/02Business/DeepBase/docs/ui/DeepBase-HB-AI-Delivery-Four-Self-Inspection-Standard.md)。  
> **消费定位**：AsWish 是 HB 交互基础设施的下游消费者，负责将四自标准严格落实到 ChangeSet Review、Diff 视觉比对、SpecNode 规约推演与 Decision Surface 流程中。

### 14.1 AsWish 视角下的“AI 交付”本质
在 AsWish 研发规约体系中，AI 交付绝不是后端生成了 AST 或打印出 ChangeSet JSON，而是：
> **AsWish 把工程代码差异与规约推演整理到：开发者一眼能看懂结构变更价值（自营销）、在 Decision Surface 能立刻按键进行裁决（自承接）、遇到差异冲突与报错现场能明白原因和自愈途径（低客服），且开发者的每一次裁决都能让 AsWish 越用越懂团队的工程规范（自成长）。**

### 14.2 四自大白话在 AsWish 核心场景的具体映射

1. **自营销（Self-Marketing · 结构价值第一眼显影）**：
   * **反面禁用**：“ChangeSet 分析完毕”、“AST 遍历成功”、“Spec 生成完毕”；
   * **AsWish 规范**：“发现 2 处影响最终界面的布局差异”、“本次重构减少 4 个冗余参数并解耦了循环依赖”、“检测到 1 处隐藏类型风险，已提供兼容方案”。
2. **自承接（Self-Onboarding · 评审决策顺畅流动）**：
   * 结果显影后，Decision Surface 必须立刻提供明确的 `1–7` 候选采纳操作，辅以 `8` 重新生成、`9` 人类手动覆写、`0` 返回放弃，严禁只展示代码 Diff 而无明确决策出路。
3. **自成长（Self-Growth · 工程偏好闭环）**：
   * 裁决完成后面向用户提供 `[让我学习]` 原语，AI 自动提炼刚才被采纳方案的工程特征（如组件更精炼、类型更严格），开发者轻量确认后沉淀为项目级工程偏好。
4. **低客服（Low-Service · 差异现场透明释疑）**：
   * 现场回答：“为什么此处判定为 Diff 差异？”、“依据哪一条规约节点进行推断？”、“如何一键回滚到上一安全快照？”，消除开发者对生成代码的黑盒恐惧。

### 14.3 AsWish 交互验收自检卡（Review Surface 门禁）
所有涉及 Human Review 与 Decision 的 AsWish GUI 界面，必须通过以下自检卡打分：
* **自营销**：开发者能否在 3 秒内看懂该变更带来的架构价值与影响面？（0分没做到 / 1分费脑 / 2分一眼看懂）
* **自承接**：开发者看懂后能否通过 0–9 按键立刻拍板下一步？（0分没做到 / 1分费脑 / 2分顺畅完成）
* **自成长**：本次选择能否沉淀为 AsWish 后续代码生成的偏好约束？（0分没做到 / 1分费脑 / 2分自动沉淀）
* **低客服**：发生规约冲突或语法推演失败时，界面能否现场讲清原因并给出解决建议？（0分没做到 / 1分费脑 / 2分现场说明）

> [!CAUTION]
> **硬门禁约束**：AsWish 所有评审界面，**自营销与自承接必须 $\ge 1$ 分；任意一项为 0 分一票否决，禁止发布！**

### 16.1 AsWish 具体学什么（业务语义清单）

## 17. 遵循 DeepBase《AI Human-Cognition Philosophy v1.0》（第一层工程哲学消费映射）

> **单一母稿指针**：第一层 AI 人机认知哲学母稿详见 [`DeepBase/docs/DeepBase-AI-Human-Cognition-Philosophy-v1.md`](file:///d:/_Progs/02Business/DeepBase/docs/DeepBase-AI-Human-Cognition-Philosophy-v1.md)。  
> **法源地位声明**：AsWish 及其 Decision/Conversation 双界面系统，严格遵循 DeepBase 《AI Human-Cognition Philosophy v1.0》（源于 ASTO.P03）作为第一层最高上游工程哲学约束。

AsWish 将该第一层认知哲学具象化消费为以下三大核心工程支柱：

### 17.1 Difference（差异显影）与哲学映射
* **消费 P6（AI 首先帮助人看见差异）**：AsWish 的本质不是代写代码的黑盒机器人，而是“差异显影设施”。Difference 不等于 Error，代码结构的演进、规约的偏离、界面的微调，首先作为可见差异呈现给人类，唤醒人类开发者的重新审阅；
* **消费 P11（认知必须允许进入现实反馈）**：ChangeSet 与 SpecNode 规约推演只有在通过真实编译、测试与运行回看后，才构成闭环认识，禁止未经现实检验的虚假完成。

### 17.2 Observable Judgment（可见判断 OJP）与哲学映射
* **消费 P1（保护人的有限注意力）**：AsWish 严禁将底层 AST 遍历与复杂的未决状态直接抛给人类，机器承担代码检索、依赖解耦与重复推演劳动，把开发者的注意力聚焦于关键决策；
* **消费 P5（认知必须诚实显影）**：凡是要求人类进行 Accept / Reject / Clarify 的对象，必须具备稳定、可追溯的视觉表现，并严格区分确定事实、推断假设与当前置信度。

### 17.3 Human Decision（人类裁决主权）与哲学映射
* **消费 P3（事实判断与价值判断必须分开）**：AI 可以推断“某组件存在 3 处结构重复并可抽取为公共函数”（事实与规则推断），但“是否值得在此阶段重构”由开发者根据项目进度与工程诉求决定（价值判断）；
* **消费 P8（价值判断归人但人也可能修正）**：开发者拥有最高裁决权（Human Authority），但并不意味开发者不会失误（Not Infallibility）；AsWish 通过快照对比与差异追溯，辅助开发者在后续工程演变中反思与校准历史判断；
* **消费 P10（人永远可以否定 AI 给出的框架）**：开发者在 Decision Surface 中始终保有按键 `9`（我自己说明 / 框架否定），可随时推翻 AI 归纳的候选方案并重新定义问题。

### 17.4 对第二层《AI 交付原则》的消费映射
* **母稿指针**：第二层 AI 交付原则母稿详见 [`DeepBase/docs/DeepBase-AI-Delivery-Principles-v1.md`](file:///d:/_Progs/02Business/DeepBase/docs/DeepBase-AI-Delivery-Principles-v1.md)；
* **Observable Judgment 消费 D1~D3**：可见判断必须针对明确的 D1 结论与 D2 确定事实展开，严禁要求开发者对黑盒隐状态作裁决，且必须支持一键下钻追溯至 D3 原始规约与 AST 证据；
* **Difference 消费 D5**：AsWish 核心比对引擎严格对应 D5 Difference 层（坚守 $\text{Difference} \neq \text{Error}$），负责清晰呈现 Baseline 与实际执行产物之间的结构差异；
* **Baseline / Result 消费 D2 与 D6**：已确认基线与生成产物作为 D2 事实，在 D6 展开为明晰的分叉路径（接受当前实现 / 回滚原基线 / 重新确立新基线），并讲清各自代价；
* **Human Judgment 消费 D7 与价值分叉不隐藏原则**：AI 负责把路照亮并提供倾向建议，但最终架构取舍权在 D7 明确交还开发者。
