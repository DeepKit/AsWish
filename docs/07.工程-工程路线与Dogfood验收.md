## 一、为什么现在进入 First Closed Loop（历史决策记录，As of 2026-08-30）

> ⚠️ 本节记录 2026-08-30 首次建立路线时"进入 First Closed Loop"的决策与阶段判定，**为历史文档**。当前阶段与目标见文首 `Current Engineering Status`。

当时阶段判定：

```text
Stage 1  First Contact    —— 陌生开发者能下载、运行、理解、完成第一次实验
        ↓
Stage 2  First Closed Loop —— AsWish 自己完成一次完整闭环
```

进入 Stage 2 的理由是工程性的，不是市场性的（**As of 2026-08-30 当时的判断，非当前现状**）：

- 当时主链**前半段**（意图承载 → 结构化解释 → 决策）已有真实代码，但**当时后半段**（实现证据 → 差异 → 人类裁决 → 修订）在代码层仍为空白；
- 未跑通整条链之前，任何"Difference 被看见"的主张都只是设计稿，不构成工程证据（该条为长期工程原则，依然有效）；
- 公开发布的第一个实验若由第三方完成，失败成本与解释成本都由第三方承担；由 AsWish 自己先承担，才能确定链本身是否成立。

> 后续进展：该"自己先承担"的决策已由后续 First Closed Loop 相关工单执行（0027F/G/H 及 0033/0034 Dogfood 等，均已 DONE）。当前状态见文首 `Current Engineering Status`。

因此 Stage 2 的第一目标不是"功能变多"，而是：

> **让 AsWish 成为自己的第一个真实用户，亲自用 AsWish 完成一次完整闭环。**

即：

> **AsWish 自己开发 AsWish，同时使用 AsWish 验证 AsWish。**

## 二、为什么 AsWish 必须自己 Dogfood

三条工程理由：

1. **可信度**：`Test my claim` 的前提是 claim 先在自己身上被检验。自己不跑，无权邀请第三方跑。
2. **反例优先权**：最有可能推翻 AsWish 主张的，是真实使用中的失败。Dogfood 让失败先发生在内部，成本最低。
3. **链的完整性不可分段证明**：单独证明"能生成 Change Set"或"能渲染"都不等于闭环。只有同一任务贯穿全程，才能证明链是连通的。

Dogfood 不是演示，不是营销，是**主张的自检验**。

## 三、双闸门：Engineering Green + Dogfood Green

工程推进不再以"代码完成 + 测试通过"为唯一放行条件。每一票必须过两道门：

```text
Engineering Acceptance → Engineering Green
Dogfood Acceptance     → Dogfood Green

Engineering Green + Dogfood Green  →  方可进入下一票
```

两者的分工：

| 闸门                    | 回答的问题                 | 证明方式                                |
| --------------------- | --------------------- | ----------------------------------- |
| **Engineering Green** | 这一票的代码是否正确、可回归、可交付？   | build 原始输出存档 + DUnitX 全量通过 + 主控独立复核 |
| **Dogfood Green**     | 这一票的能力在真实使用中真的被用起来了吗？ | 用 AsWish 自身任务跑通本票环节，产生真实工程证据        |

> 只过 Engineering Green **不等于完工**。  
> `172/172` 只是 Engineering Green，不是 Dogfood Green。

### Engineering Green 检查单

```text
Build        构建成功，原始输出存档
Tests        DUnitX 全量通过，原始输出存档
CLI / GUI    涉及入口可手动走通
Protocol     落盘产物符合现有协议，通过 schema / validation 校验
Regression   受影响模块测试 + 全量测试通过
Git diff     变更范围与本票声明一致，无越界修改
```

### Dogfood Green 检查单（"五真实"，缺一不可）

```text
真实任务     选定的 Dogfood Task，不是构造样例
真实人类     由人做出真实判断；否决与修正同样算真实判断
真实 AsWish  使用当前 AsWish 本体（CLI / GUI / 协议落盘）
真实 Agent   实施由外部 Agent（Claude Code / Codex / Cursor 等）完成
真实结果     产出真实的 Evidence / Difference / Revision 记录
```

> 自动化测试通过**不能替代**以上任何一项。

门禁执行细则（build/test 证据存档、单 commit 规模、APPROVED/RETURNED）以 [`../AGENTS.md`](../AGENTS.md) 与《非睿智轻量门禁规范-v1》为准。

### 6.8b.1 Q1 · Difference v0 比什么 —— 结论

**一句话**：v0 的 Difference 只做「**同一投影树的结构差异**」，用现成的 ContentHash / RelationHash 判定，不比视觉、不比颜色、不比文字。

**依据（已核实）**：
- `tree.schema.json` 的 node 已含 `content_hash`（内容，含 summary/purpose）与 `relation_hash`（拓扑，含 parent_id + relations）；
- `AsWish.Hash.pas` 的 `NodeContentHash` / `NodeRelationHash` 已实现、可稳定复算；
- `05.协议 §8.2` 已声明「ContentHash / RelationHash 严格分离」。

**v0 差异判定规则（三条，全可程序化判定）**：
1. **缺失**：Baseline 里有、Evidence 里没有的 `node.id` → Missing；
2. **多余**：Evidence 里有、Baseline 里没有的 `node.id` → Extra；
3. **变化**：同一 `node.id` 的 ContentHash 或 RelationHash 与 Baseline 不一致 → Changed（细分：ContentChanged / RelationChanged，按哪个哈希变了判定）。

**明确不做的（v0）**：四层全部铺开（只做功能投影一层）；视觉像素 Diff；措辞/语义级 Diff；任何需要 NLP 才能判定的"差异"。

**关键前提（必须修 P2）**：当前 `SnapshotContentHash(四树)` 把 function/view/module/data 合并后哈希，导致 B-0001(function) 与 B-0002(view) 的 Baseline 哈希完全相同。**Q1 落地前必须先修**：让基线哈希按「单树粒度」计算（`CreateBaseline` 传单树而非合并四树），否则差异计算无法定位到具体投影。

> **P2 裁定（2026-09-03 老板拍板）**：`tree_type` 语义 = 「触发冻结的那棵树」，基线哈希按**单树粒度**计算（非四树合并）。P2 修复纳入 0027G 立票前提。

### 6.8b.3 Q3 · Evolution 在数据结构上是什么 —— 结论

**一句话**：**Evolution 不引入任何新结构，纯语义区分。** 它就是「人类判断为可接受/更好 → 用现有 `Decisions` 记录一条"接受"决策 → 用现有 `CreateBaseline` 以该决策冻结 New Baseline」。

**依据（已核实）**：
- `Snapshot.CreateBaseline(ADecision, ...)` 已存在，且 `TAsWishBaseline` 含 `Lineage`（可指向 parent）；
- `Decisions` 服务已存在（通用决策机制）。

**Revision vs Evolution 的数据结构差异（仅一处语义字段）**：

| 维度 | Revision | Evolution |
|---|---|---|
| 人类判断 | 我要调整（Unacceptable） | 更好，我接受（Acceptable / 更好实现） |
| Decision 类型 | 记「修订」决策 | 记「接受差异」决策 |
| New Baseline | 从**新的 Human Intent** 重走链后冻结 | 从**当前实现现实**直接冻结（lineage parent = 当前 Baseline） |
| 是否新建结构 | 否 | 否 |

**红线**：二者都只复用现有 `Decisions` + `CreateBaseline`，**禁止新增第二套状态机或独立 Baseline 实体**（违 §十禁令）。

## 八、First Closed Loop v0 · 正式验收

> **工程链 SSOT**：本节是 First Closed Loop 主链（含 Revision / Evolution 双出口）的**唯一真相源**。`01.产品` §十、`03.规范` VC-06 等处的链只作指针引用、不复制；冲突时以本节为准。

**定义**：First Closed Loop v0 是一个**可实现、可观察、可验收的最小产品闭环**——不是理论解释，而是可以逐阶段打勾的验收对象。

必须真实完整跑通以下主链（同一任务、同一项目）：

```text
Human Intent
    ↓
Problem Manifestation
    ↓
AI Interpretation / Candidate
    ↓
Human Confirmation
    ↓
Confirmed Understanding
    ↓
Visual Baseline
    ↓
Agent Development
    ↓
Implementation Evidence
    ↓
Implementation Result
    ↓
Difference
    ↓
Human Judgment
    ├── 更好，我接受 ──► Evolution：接受现实 → 产生 Decision → 冻结 New Baseline
    └── 我要调整 ──────► Revision：回到 Human Intent → Rebuild → Re-verification
```

硬性条件：

1. 全程使用**同一个真实任务**；
2. 每一环节都产生**真实工程证据**，不是构造样例；
3. 人类判断是**真实的**，允许出现否决与修正；
4. **至少真实完整跑通一次第二轮**——Revision（回到 Intent 重来）或 Evolution（接受差异、更新确认）皆可；**Evolution 尤其重要**，因为它证明 AsWish 不是防错工具。

### 不完成条件（出现任何一条，即不得宣布成功）

```text
Human 没有明确确认
没有稳定 Baseline
Agent 修改无法追踪
没有 Implementation Evidence
无法看到 Implementation Result
没有 Difference
Difference 没有 Human Judgment
Human 无法发起 Revision
Revision 没有重新进入流程
没有第二轮验证
```

以下情况**单独或合计均不构成验收**：

```text
Build 成功
Tests 全绿
Agent 说 Done
Human 看一眼
```

> 阶段逐项标准（输入 / AI 职责 / Human 职责 / 必须可见什么 / 产物 / 完成条件）见 §十一阶段标准表。

## 十二、Human / AI Boundary（共同门禁）

### Human owns

```text
Intention              意图
Judgment               判断
Decision               决策
Accept / Reject        接受 / 拒绝
Difference Judgment    差异判断
Final Confirmation     最终确认
Revision Decision      修订决定
```

### AI may

```text
Discover               发现
Ask                    提问
Explain                解释
Suggest                建议
Transform              转换
Generate               生成
Render                 渲染
Implement              实施
Inspect                检查
Surface Difference     让差异可见
```

### AI must not

```text
把推测当确认
把 Candidate 当 Decision
把 Difference 当 Error
未经确认修改 Canonical Spec
未经确认结束闭环
代替 Human 完成最终判断
```

> **本边界是所有后续工程票的共同门禁**：每张工单的 AC 必须包含"不违反边界"的检查项；违反即 RETURNED，不得 CLOSE。

Human must see          人必须能看见
