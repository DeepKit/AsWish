## CTF in AsWish

CTF means Constructive Traceable Fallibilist Method.

It is the method used by AsWish to turn project material and AI output into specifications that humans can inspect and repair.

## One Sentence

A requirement's form and granularity are constructed through human-AI dialogue, traceable to evidence, and always open to correction. Underlying constraints (compliance, safety, performance) may be objective.

## Boundary

CTF belongs before execution.

```text
CTF / AsWish: form a trustworthy specification
Symphony-style orchestration: keep agents working on tasks
ODD: verify, seal, and rework implementation outputs
```

Do not put execution lifecycle state inside CTF. Once an objective is ready for execution, orchestration or ODD owns it.

## Core Workflow

```text
messy project material
        -> four projections
        -> semantic bundles
        -> evidence links
        -> trust signals
        -> human review decision
        -> SpecSnapshot / ContractCandidate
```

## Four Projections

```text
function-tree: behavior and capability
module-tree: implementation ownership and structure
view-tree: user-visible workflow and UI
data-tree: schema, state, persistence, migrations, and boundaries
```

The fourth tree is `data-tree`, not `risk-tree`. Risk is derived from all projections, with data drift often being the highest-risk source.

## Trust Signals

A reviewer should be able to see:

- evidence source status
- confidence
- generation status
- review status
- semantic bundle completeness
- conflicts with previous decisions
- stale source evidence
- agent assumptions, blockers, alternatives, and coverage

## State Model

Node states are orthogonal; the authoritative definitions live in [`05.协议-AsWish协议基线.md`](05.协议-AsWish协议基线.md) §4 and `protocol/state-machine.md`（2026-09-03 C-5 裁定后与代码一致）：

```yaml
gen_status: draft | generated | confirmed | skipped
review_status: unreviewed | accepted | rejected | deferred
```

`failed`（生成失败）与 `locked`（人类锁定、防 AI 覆盖）为预留语义，当前未实现；出现真实需要时经 `protocol/GOVERNANCE.md` 治理流程加回。

Legacy `status` is only a compatibility field.

## Review Discipline

Accept should be deliberate. Reject should be easy.

`accept_level` records responsibility:

```text
low_risk      acceptable local inference
provisional   usable but must be revisited
release       suitable for release gating
accountable   reviewer accepts responsibility for high-impact use
```

## Three Health Signals

Monitor only three signals, each tied to a core axiom:

| Signal | Axiom | Trigger |
|--------|-------|---------|
| Review backlog | A3 Fallibilism | pending ratio > 30% |
| Confidence drift | A2 Traceability | new output confidence drops below reviewed average |
| Confirmation bias | A6 Problem-First | accept:reject ratio > 10:1 |

No composite "health index". Each signal speaks for itself.

## Review Ceremony (Three Tiers)

Not every review needs 20 minutes.

| Tier | When | Time | What |
|------|------|------|------|
| Light | single node, confidence > 0.85 | 3 min | problem-first + accept/reject |
| Standard | semantic bundle, 3+ nodes changed | 10 min | problem-first + selective deep-dive + generation instructions |
| Deep | cross-tree impact, architecture decision | 20 min | full four-phase ceremony |

System suggests tier based on change scope. Reviewer can always escalate.

## Decision Log (Exception-Driven)

Record only:

- Reject decisions (reason required)
- Accept with confidence < 0.7 (reason required)
- Deviations from standard review flow

Auto-collect (no human input needed):

- time spent per node
- accept/reject counts
- average confidence
- session length and node count

Remove manual `reasoning_type` selection. Infer automatically from evidence presence.

## Checklist Automation

Machine-checkable items (A2 traceable, A3 fallible, A5 minimal context, A7 partial success) belong in `aswish_validate`, not in a human checklist.

Only A6 (problem-first) requires human judgment. Present as a non-blocking prompt, not a blocking dialog.

## Tool Protocol

```text
aswish_read     -- read tree data or summary
aswish_validate -- check invariants, schema, cross-tree consistency
aswish_query    -- RAG over four projection trees
aswish_update   -- write nodes and decisions with conflict detection
```

Day-one minimum: `aswish_read` + `aswish_validate`. The other two can follow.

All `.AsWish/` content is human-readable YAML. If every AI tool disappears, a reviewer can still open the files in a text editor.

## Why It Helps AI Engineering

AI engineering fails when generated work looks plausible but cannot be traced, reviewed, or corrected. CTF adds the missing quality gate between agent output and human acceptance.

It does not promise that the AI is correct. It makes incorrectness discoverable and recoverable.

## 第二部分：科学论证链条：假说、操作化与观察（破除“唯一证明”陷阱）

在学术与工程哲学上，**必须高度警惕“AsWish 是理论体系的唯一下行实证载体”这种绝对化表述**。

### 1. 为什么“唯一”在科学论证上是致命的？

“唯一”会悄然滑向逻辑谬误：
- 它会把客观的 **“这是理论的一个工程实现（An Operationalization）”**；
- 偷偷偷换成封闭循环的 **“只有我的实现才能证明我的理论（Only my implementation proves my theory）”**。

一旦陷入后者，理论在科学方法论上将遭受毁灭性攻击：
- **循环论证（Circular Reasoning）**：自己写软件证明自己的假说，若软件行为被硬编码以迎合结论，则不具备独立验证效力；
- **不可证伪性（Unfalsifiability）**：若声称只有这一款软件才能检验理论，第三方若用其他方式复现失败，作者就会辩解“因为你没有使用我的软件”，从而使理论丧失作为严肃科学研究纲领的资格；
- **排他独占陷阱**：剥夺了开源社区和第三方根据 `.AsWish/` 协议开发其他语言实现（如 Rust、Python 版）来共同检验理论的可能性。

### 2. 正确且严谨的科学假说论证链

科学的、可证伪的、开放的认识论结构必须是：

```text
Theory (差异一元论 / CTF / ODD 理论母体)
  │
  ▼ generates (派生出)
Engineering Hypotheses (可测试的工程假说)
  │  例：自然语言无法与代码直接对齐，必须通过正交投影作为中介；
  │  例：显式划分 explicit/inferred 能显著降低人机协作漂移。
  ▼ operationalizes (将其操作化为代码与协议)
AsWish Reference Implementation (作为可操作化工具运行)
  │
  ▼ produces (产出客观事实)
Empirical Observations & Evidences (经验观察与物理证据)
  │  (真实项目的差异报告、决策记录、漂移统计、失败反例)
  ▼
Observations may SUPPORT or WEAKEN hypotheses (观察事实可能支持、也可能削弱假说)
  │
  ▼ feeds back into
Theory Revision (理论修正与演进)
```

**坚决反对并杜绝以下封闭论证**：
```text
[错误/被动链条] Theory ➔ AsWish ➔ therefore theory is true. (因 AsWish 存在，故理论为真)
```

AsWish 从来不是理论的“真理宣称机”，它是理论走向真实世界时的**“测量探针与证伪试验场”**。如果实验产出了反例，理论必须能够根据观察事实进行修正和缩限。

## 第三部分：“它能不能宣传我的理论？”的根本逻辑研判

### 1. 核心论断：**能，而且可能是最好的载体，但前提是走“特洛伊木马”式的工程实证路线。**

- **为什么它是最好的载体？**
  - **理论的“实证土壤”困境**：在当代，纯本体论哲学（如差异一元论）或方法论论文，无论逻辑多么严密，若没有大型产业或工程场景支撑，极易被学术界或工业界归类为“抽象哲学推演”，缺乏证伪与验证的闭环。
  - **解决 AI Coding 的行业级真痛点**：当前全行业（Cursor、Claude Code、Codex、Gemini CLI 用户）正面临巨大痛苦：
    > *“AI 明明代码写完了，测试也绿了，但做出来的根本不是我想要的东西。”*  
    > *“AI 产生幻觉了，代码越改越乱，但不知道它从哪一步开始偏航的。”*
  - **理论自带直击灵魂的问答框架**：
    AsWish 抛出的两个核心问句：
    > **“Are we still building the same thing?”（我们是否还在构建同一个东西？）**  
    > **“Where did the difference enter?”（差异究竟是从哪里进入系统的？）**
    这两个问句完全不是工具层面的功能叫卖，而是直接把开发者引向了**差异（Difference）、表示（Representation）与建构（Construction）的本体论思考**。

### 2. 警惕三大致命陷阱（为什么绝对不能走“传统的理论炒作/宣讲路线”？）

在探讨“宣传理论”时，必须清醒认识到开源社区与开发者人群的心理防御机制：

#### 陷阱一：触发程序员对“民哲/概念包装”的本能抵触
- 程序员天然相信代码与现实输出（*“Talk is cheap, show me the code”*）。
- 如果官网、README 或宣发文案一上来就大谈“差异一元论存在条件论”、“属集变迁五态六阶”、“本体论革新”，用户会立刻产生极强的警惕心，将其视为**学术包装、概念炒作或“内部自嗨”**，甚至直接放弃下载。

#### 陷阱二：买椟还珠与主次颠倒
- 真实开发者下载 AsWish 是为了**解决自己代码被 AI 改烂、需求对不齐的问题**，而不是为了找一套哲学来信仰。
- 工具必须先在工程上极其好用、逻辑极度自洽、运行极度稳定。当用户惊叹于“这个工具竟然能把差异抓得这么准、证据链这么严密”时，他们才会反过来好奇：*“这套软件背后的架构哲学到底是什么？”*

#### 陷阱三：理论不可证伪的捧杀反噬
- 《01.产品-AsWish产品身份与愿景蓝图.md》§4 明确规定：
  > **“DM 是存在条件论，不是宇宙生成论；DM 是可受损、可修订、可缩限的研究纲领。”**
- 如果为了营销把理论包装成“包治百病的绝对真理”，一旦软件在某个边缘场景（如复杂的动态反射代码分析）出现破绽，反对方就会借此否定理论本身的学术严肃性。
